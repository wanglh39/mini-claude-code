## 一、前置知识：token、上下文窗口、为什么有限制

### 1.1 什么是 token

在和大语言模型（LLM）打交道时，我们常说"这段话占多少 token"。token 到底是什么？

**token 是模型处理文本的最小单位**，但它不等于"字"，也不等于"词"。它介于两者之间，是模型分词器（tokenizer）切出来的片段。一个 token 可能是：

- 一个完整的小词：`cat`、`run`、`the` 都是单个 token。
- 一个词的一部分：`hamburger` 会被切成 `ham` + `burger` 两个 token。
- 一个标点：`,`、`.`、`!` 通常是单独的 token。
- 一个子词：罕见词、专有名词、错别字会被拆成多个常见子词。

**对中文来说情况更复杂**：一个汉字通常占 1~2 个 token，因为大多数模型的词表是以英文为主训练的，中文需要用 UTF-8 字节再切。比如"你好"两个字，在 Claude 的 tokenizer 下大约是 2~4 个 token，具体取决于上下文和分词算法。

### 1.2 token 和字符的关系（粗略换算）

没有精确的"1 字符 = X token"公式，因为不同语言、不同内容差异很大。但有一个被广泛引用的粗略换算表：

| 内容类型 | 大致比例 |
|----------|----------|
| 纯英文 | 1 token ≈ 4 字符（约 0.75 个英文单词） |
| 纯中文 | 1 token ≈ 1.5~2 字符（一个汉字约 0.5~0.7 token） |
| 代码 | 1 token ≈ 3~4 字符（变量名、符号多） |
| JSON / 结构化数据 | 1 token ≈ 2~3 字符（大量引号、括号） |

**实用估算口诀**：

- 英文：4 字符 ≈ 1 token。
- 中文：1 字 ≈ 0.6 token，或者说 1000 字 ≈ 600 token。
- 代码：按英文算，但符号密集时偏多。

为什么要会估算？因为我们在本地没有官方 tokenizer 时，得用 `字符串长度 / 4` 这种粗略公式来判断"这段内容会不会超限"。后面讲 token 计数方式时还会再提。

### 1.3 为什么有上下文窗口限制

LLM 的核心架构是 Transformer，它有一个**自注意力机制**（self-attention）。自注意力的计算量随序列长度**平方增长**——序列长度翻倍，计算量变四倍。再加上：

- **显存占用**：序列越长，KV cache 越大。一个 200K token 的上下文，KV cache 就要占好几 GB 显存。
- **计算时间**：每生成一个 token，都要对前面所有 token 做一次注意力。上下文越长，生成越慢。
- **训练长度**：模型训练时见过的最大序列长度是固定的（比如 8K、32K、200K）。超过训练长度，模型行为不可预测。

所以厂商会设一个**上下文窗口**（context window）：一次请求里所有 token（输入 + 输出）的总和不能超过这个数。这是硬限制，超了直接报错。

### 1.4 不同模型的上下文窗口限制

| 模型 | 上下文窗口 | 备注 |
|------|-----------|------|
| GPT-3.5 | 4K / 16K | 早期很小 |
| GPT-4 | 8K / 32K | 标准版 |
| GPT-4 Turbo | 128K | 大幅提升 |
| GPT-4o | 128K | 当前主流 |
| Claude 2 | 100K | 早期就很大 |
| Claude 3 Haiku | 200K | 小模型也大窗口 |
| Claude 3 Sonnet | 200K | 本章用的 |
| Claude 3.5 Sonnet | 200K | 当前主力 |
| Claude 3 Opus | 200K | 最强但贵 |
| Gemini 1.5 Pro | 1M | 目前最大 |
| Gemini 1.5 Flash | 1M | 小模型也 1M |

**Claude 系列统一是 200K**，这也是本章代码假设的值。注意 200K 是**输入 + 输出总和**，不是只算输入。Claude API 还有一个 `max_tokens` 参数控制单次输出上限，输入 token + `max_tokens` 不能超过 200K。

**200K 听起来很大，但实际很快就用完**。下面详细讲。

## 二、上下文增长的四个来源

每轮对话，`messages` 数组都会变长。增长来自四个地方，理解它们对选择策略至关重要。

### 2.1 来源一：用户输入

用户每轮敲一行命令，比如"帮我读一下 main.ts"。这一条消息会被加进 `messages`：

```typescript
{ role: "user", content: "帮我读一下 main.ts" }
```

**量级**：每轮几十到几百 token。用户一句话通常不长。

**特点**：增长缓慢、可预测。用户打字速度有限，一轮最多几百 token，几十轮下来也就一两万 token，远没到 200K。

**结论**：用户输入**不是主要矛盾**，基本可以忽略。

### 2.2 来源二：模型回复

模型每轮返回一段文本（可能还带 tool_use）。比如：

```typescript
{ role: "assistant", content: "我来帮你读 main.ts。先调用 read_file 工具..." }
```

**量级**：几百到几千 token。模型解释自己在干什么、思考过程、代码块，都可能比较长。

**特点**：比用户输入大一个量级，但仍然可控。一轮对话模型回复通常不超过 2000 token。

**结论**：模型回复**也不是主要矛盾**，但比用户输入值得留意。

### 2.3 来源三：工具调用请求

模型决定调工具时，会返回一个 `tool_use` 块：

```typescript
{
  role: "assistant",
  content: [{
    type: "tool_use",
    id: "toolu_xxx",
    name: "read_file",
    input: { path: "main.ts" }
  }]
}
```

**量级**：很小。工具名 + 参数，通常几十到一两百 token。

**特点**：参数可能包含大字符串（比如 `write_file` 的 `content`），但大多数工具调用参数都不大。

**结论**：工具调用请求**可以忽略**。

### 2.4 来源四：工具执行结果（主要矛盾！）

工具执行完，结果会以 `tool_result` 形式加进 `messages`：

```typescript
{
  role: "user",
  content: [{
    type: "tool_result",
    tool_use_id: "toolu_xxx",
    content: "（这里是工具返回的内容，可能非常长）"
  }]
}
```

**量级**：可能**非常大**。举几个真实例子：

| 工具 | 操作 | 结果大小 |
|------|------|----------|
| `read_file` | 读一个 2000 行的源文件 | ~20K token |
| `list_files` | 列一个有 500 个文件的目录 | ~10K token |
| `run_command` | 跑 `npm install` 输出 | ~30K token |
| `grep` | 在大仓库里搜一个常见词 | ~50K token |
| `read_file` | 读一个打包后的 bundle.js | ~100K+ token |

**一次 `read_file` 读大文件，可能就占了几万 token。两三次这样的操作，200K 就用完了。**

**特点**：

- 爆发性增长——一次工具调用就可能涨好几万 token，不像用户输入那样线性增长。
- 不可预测——用户可能突然让模型读一个巨大的文件。
- 信息密度低——工具结果里大量内容是模型不需要逐字记住的（比如文件的大部分行、命令的大部分日志）。

**结论**：工具结果是上下文膨胀的**主要来源**，所有优化策略都要优先针对它。

### 2.5 四个来源的对比

```
来源              量级/轮      增长方式      是否主要矛盾
─────────────────────────────────────────────────────────
用户输入          几十~几百     线性、缓慢    否
模型回复          几百~几千     线性、中速    否
工具调用请求      几十~几百     线性、缓慢    否
工具执行结果      几千~几万     爆发、不可测  是 ★★★★★
```

**记住这张表**。后面所有策略的设计动机都源于"工具结果是主要矛盾"这个判断。

## 三、超限会发生什么

### 3.1 API 报错

当 `messages` 数组总 token 数超过 200K，Claude API 会直接返回一个错误：

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "prompt is too long: 234567 tokens > 200000 maximum"
  }
}
```

HTTP 状态码通常是 400。这是一个**硬错误**——不是模型回答得不好，是请求直接被拒收，模型根本没机会处理。

### 3.2 对话崩溃

如果我们的 CLI 不处理这个错误，会发生什么？

```
你: 帮我读一下 src/big_file.ts
（模型调用 read_file，结果 5 万 token 加进 messages）
你: 再读一下 src/another_big_file.ts
（又加 5 万 token）
...
你: 现在帮我总结一下
（API 调用 → 报错 prompt is too long → CLI 抛出未捕获异常 → 进程崩溃）
```

用户看到的就是：聊着聊着突然挂了，前面的上下文全丢了。这是**最差的用户体验**。

### 3.3 为什么不能"自动从前面删一点"

你可能会想：超了就自动从前面删几条消息呗，干嘛要专门写一章？

问题在于：

1. **删哪些消息**是有讲究 的。删错了关键信息，模型会答非所问。
2. **什么时候开始删**要提前预判。等到超限再删，用户已经看到报错了。
3. **删了之后要不要保留要点**？直接删和先总结再删，效果差很多。
4. **工具结果要不要特殊处理**？一个 5 万 token 的工具结果，和一个 100 token 的用户消息，删法不一样。

这些问题就是这一章要解决的。核心思路：**在超限之前主动管理上下文**，而不是等超限了再被动救火。

## 四、三种策略深入

我们有三种武器，从轻到重排列：

### 4.1 策略一：工具结果截断（最轻、最高频）

**做什么**：每次工具执行完，检查结果是不是太长。太长就只保留头部和尾部，中间用省略号代替。

**为什么保留头尾**：

- **头部**通常是最重要的：文件的开头（import、类定义、函数签名）、命令的开头（错误信息、第一个输出）。
- **尾部**通常是次重要的：文件的结尾（最后的函数、export）、命令的结尾（最终结果、退出码）。
- **中间**往往是重复的、可以推断的、或者当前不需要的：文件中间的实现细节、命令中间的进度日志。

**代码**：

```typescript
truncateToolResults(maxResultLength = 10000) {
  for (const msg of this.messages) {
    if (msg.role !== "user") continue;
    if (typeof msg.content === "string") continue;

    for (const block of msg.content) {
      if (block.type !== "tool_result") continue;
      if (typeof block.content !== "string") continue;
      if (block.content.length <= maxResultLength) continue;

      // 超长，截断保留头尾
      const head = block.content.slice(0, maxResultLength / 2);
      const tail = block.content.slice(-maxResultLength / 2);
      const truncated = head.length + tail.length;
      const original = block.content.length;

      block.content =
        head +
        `\n\n...(已截断，原 ${original} 字符，保留头尾各 ${truncated / 2} 字符)...\n\n` +
        tail;
    }
  }
}
```

**参数选择**：`maxResultLength = 10000` 字符。为什么是 1 万字符？

- 1 万字符 ≈ 2500 token（按英文 4 字符/token 算）。
- 一次工具结果 2500 token，可接受。
- 头尾各 5000 字符，对大多数文件来说够看开头和结尾。
- 如果一个对话有 20 次工具调用，截断后总共 5 万 token，还在可控范围。

**触发时机**：每次工具执行后立即调用。这是**预防性**的——不等接近限制，一开始就压住工具结果。

**优点**：简单、快、无额外 API 调用。

**缺点**：丢失中间内容。如果模型正好需要中间某一行，就尴尬了。

### 4.2 策略二：历史截断（中等、低频）

**做什么**：当上下文接近限制时，直接丢弃最旧的几条消息，只保留最近的 N 条。

**代码**：

```typescript
truncateHistory(keepRecent = 10) {
  if (this.messages.length <= keepRecent) return;
  this.messages = this.messages.slice(-keepRecent);
}
```

**参数选择**：`keepRecent = 10`。为什么是 10 条？

- 10 条消息大约覆盖 5 轮对话（每轮一问一答 = 2 条）。
- 5 轮对话通常够模型理解"当前在干什么"。
- 太少（比如 4 条）可能丢掉关键上下文。
- 太多（比如 30 条）可能截了等于没截。

**触发时机**：当 token 数超过阈值（比如 95%）时调用。这是**被动救火**——已经接近危险线，必须快速减负。

**优点**：简单、快、立竿见影——直接砍掉一大块。

**缺点**：**粗暴**。完全丢失旧上下文。如果旧上下文里有关键信息（比如用户一开始说"我要用 TypeScript"），截断后模型就忘了，可能开始用 Python。

### 4.3 策略三：对话压缩（最重、最低频）

**做什么**：当上下文接近限制时，用模型自己来总结前面的对话，然后用这段总结替换旧消息。

**代码**：

```typescript
async compress(client, model): Promise<boolean> {
  if (this.messages.length < 10) return false;

  // 把前面的大部分消息拿出来压缩
  const oldMessages = this.messages.slice(0, -4);
  const recentMessages = this.messages.slice(-4);

  // 把旧消息拼成文本
  const conversationText = oldMessages
    .map(m => `${m.role}: ${JSON.stringify(m.content)}`)
    .join("\n");

  // 调用模型总结
  const summaryResponse = await client.messages.create({
    model,
    max_tokens: 1000,
    messages: [{
      role: "user",
      content: `请把以下对话历史总结成一段简洁的上下文摘要，保留关键信息（用户意图、已做的决定、已读的文件、已发现的问题），丢弃冗余细节:\n\n${conversationText}`
    }]
  });

  const summary = summaryResponse.content[0].text;

  // 用总结替换旧消息
  this.messages = [
    {
      role: "user",
      content: `[以下是之前对话的摘要]\n${summary}\n[摘要结束]`
    },
    ...recentMessages
  ];

  return true;
}
```

**触发时机**：当 token 数超过预警阈值（比如 80%）时调用。比历史截断更早触发，因为它更温和——不会完全丢失信息。

**优点**：**保留关键信息**。模型总结出来的摘要包含了"用户想干什么、已经做了什么、发现了什么"，这些正是后续对话需要的。

**缺点**：

1. **多一次 API 调用**——费钱、费时间。一次总结调用可能花几百 token 的费用，增加一两秒延迟。
2. **总结可能不准**——模型可能漏掉关键信息，或者总结偏题。
3. **格式变化**——总结后的消息结构和原来不一样，某些工具调用上下文会丢失。

### 4.4 三种策略对比

| 维度 | 工具结果截断 | 历史截断 | 对话压缩 |
|------|-------------|---------|---------|
| 何时触发 | 每次工具执行后 | 95% 强制 | 80% 预警 |
| 信息损失 | 中间部分 | 完全丢失旧消息 | 细节丢失，要点保留 |
| 额外开销 | 无 | 无 | 一次 API 调用 |
| 实现难度 | 低 | 低 | 中 |
| 效果 | 好（针对主要矛盾） | 粗暴但有效 | 最好 |

**实际使用**：三者**组合使用**，不是三选一。工具结果截断一直在做，压缩在 80% 时触发，历史截断在 95% 时兜底。

## 五、什么时候用哪种策略：阈值设计

### 5.1 为什么要多级阈值

如果只用一个阈值（比如 95%），问题是：

- 到 95% 才动手，此时余量已经很小，可选策略受限。
- 用户可能正好处在 94%，下一轮直接超限，来不及处理。
- 没有预警，用户不知道上下文快满了。

多级阈值解决这些问题：

```
0% ──────── 80% ──────── 95% ──────── 100%
             │             │
             │             └─ 强制历史截断（兜底）
             └─ 预警 + 尝试压缩
```

### 5.2 阈值设计

```typescript
private readonly WARN_THRESHOLD  = 0.80;  // 80% 预警
private readonly FORCE_THRESHOLD = 0.95;  // 95% 强制
```

**80% 预警**（`isNearLimit`）：

- 此时还有 20% 余量（约 4 万 token），来得及做温和处理。
- 触发**对话压缩**——用模型总结旧对话，保留关键信息。
- 同时在状态栏显示警告颜色（比如黄色）。

**95% 强制**（`isOverLimit`）：

- 此时只剩 5% 余量（约 1 万 token），下一轮可能就超限。
- 触发**历史截断**——直接砍掉旧消息，保命要紧。
- 状态栏显示危险颜色（比如红色）。

### 5.3 为什么是 80% 和 95%，不是 70% 和 90%

- **80% 而不是 70%**：70% 时上下文还很宽裕，过早压缩浪费 API 调用。80% 是"开始要留意"的点。
- **95% 而不是 90%**：90% 时还有 2 万 token，通常还能撑一两轮，没必要立刻暴力截断。95% 是"真的要爆了"的点。
- **两个阈值之间有 15% 缓冲**（约 3 万 token）：给压缩失败、压缩后仍然超限等意外留余地。

### 5.4 主循环里的策略编排

```typescript
// 每轮对话后：

// 1. 更新 usage（API 返回的真实 token 数）
if (usage) ctx.updateUsage(usage);

// 2. 截断大工具结果（每次都做，预防性）
ctx.truncateToolResults();

// 3. 接近限制时先尝试压缩
if (ctx.isNearLimit()) {
  console.log("⚠ 上下文接近限制，尝试压缩...");
  const compressed = await ctx.compress(client, model);
  if (compressed) {
    console.log("✓ 压缩完成");
  } else {
    // 压缩失败（比如消息太少），退而求其次
    ctx.truncateHistory(10);
  }
}

// 4. 如果压缩后仍然超限，强制截断
if (ctx.isOverLimit()) {
  console.log("✗ 上下文仍超限，强制截断历史");
  ctx.truncateHistory(10);
}

// 5. 显示当前状态
console.log(ctx.getStatus());
```

注意顺序：**先压缩，压缩不够再截断**。因为压缩更温和，截断是兜底。

### 6.2 类骨架和字段

```typescript
import { Anthropic } from "@anthropic-ai/sdk";
import { MessageParam } from "@anthropic-ai/sdk/resources/messages";

class ContextManager {
  private messages: MessageParam[] = [];
  private maxTokens: number;
  private lastUsage: { input_tokens: number; output_tokens: number } | null = null;

  private readonly WARN_THRESHOLD  = 0.80;
  private readonly FORCE_THRESHOLD = 0.95;

  constructor(maxTokens: number = 200000) {
    this.maxTokens = maxTokens;
  }
  // ...
}
```

**逐字段解释**：

- `messages: MessageParam[]`——这是对话历史数组，就是发给 API 的那个 `messages`。每一项是 `{ role, content }`。整个上下文管理的目标就是控制这个数组的总 token 数。
- `maxTokens: number`——上下文窗口上限，默认 200000（Claude 3 的限制）。构造时传入，方便不同模型用不同值。
- `lastUsage`——最近一次 API 调用返回的 token 使用量。`input_tokens` 是这次请求输入了多少 token，`output_tokens` 是模型输出了多少。这是**最准的 token 计数来源**，后面详讲。
- `WARN_THRESHOLD = 0.80`——预警阈值。
- `FORCE_THRESHOLD = 0.95`——强制阈值。

**为什么 `messages` 是 `MessageParam[]`**：这是 Anthropic SDK 的类型。`MessageParam` 就是 `{ role: "user" | "assistant", content: string | ContentBlock[] }`。我们直接用 SDK 的类型，不用自己定义。

**为什么 `maxTokens` 可传入**：不同模型限制不同。Claude 3 是 200K，GPT-4 是 8K，Gemini 是 1M。写死 200K 就不通用。构造时传入，实例用哪个模型就传哪个限制。

### 6.3 基础方法：addMessage 和 updateUsage

```typescript
addMessage(message: MessageParam): void {
  this.messages.push(message);
}

updateUsage(usage: { input_tokens: number; output_tokens: number }): void {
  this.lastUsage = usage;
}
```

**`addMessage`**：往历史数组追加一条。主循环每轮会调两三次——加用户消息、加模型回复、加工具结果。

**`updateUsage`**：每次 API 调用返回时，把返回的 `usage` 存下来。这是后面 `getTokenCount` 的数据来源。

**为什么不把 `addMessage` 和 `updateUsage` 合并**：因为它们发生的时机不同。`addMessage` 可能在 API 调用前（加用户输入）或 API 调用后（加模型回复）发生，而 `updateUsage` 只在 API 调用后发生。分开更清晰。

### 6.4 token 计数：getTokenCount

```typescript
getTokenCount(): number {
  if (this.lastUsage) {
    return this.lastUsage.input_tokens + this.lastUsage.output_tokens;
  }
  // 没有 usage 信息时，粗略估算
  return this.estimateTokens();
}

private estimateTokens(): number {
  let chars = 0;
  for (const msg of this.messages) {
    if (typeof msg.content === "string") {
      chars += msg.content.length;
    } else {
      for (const block of msg.content) {
        if (block.type === "text") chars += block.text.length;
        else if (block.type === "tool_use") chars += JSON.stringify(block.input).length;
        else if (block.type === "tool_result" && typeof block.content === "string") {
          chars += block.content.length;
        }
      }
    }
  }
  return Math.ceil(chars / 4);  // 粗略：4 字符 ≈ 1 token
}
```

**两种模式**：

1. **有 `lastUsage` 时**：直接用 API 返回的数字。这是**最准的**——API 自己算的，不可能更准了。
2. **没有 `lastUsage` 时**（比如第一次调用前）：用 `字符数 / 4` 粗略估算。

**为什么用 API usage 而不是本地 tokenizer**——这是 6.5 节要专门讲的问题。

### 6.5 为什么用 API usage 而不是本地 tokenizer

理论上最准的方式是本地用官方 tokenizer 算：

```typescript
import { countTokens } from "@anthropic-ai/tokenizer";
const tokens = countTokens(JSON.stringify(this.messages));
```

但我们不这么做，原因有三：

1. **Claude 没有公开的官方 tokenizer**。Anthropic 没有像 OpenAI 那样发布 `tiktoken` 这样的官方包。社区有近似实现，但不保证和 API 一致。
2. **API 返回的 usage 是真实值**。API 处理请求时已经算好了 `input_tokens`，这是模型实际看到的 token 数，不可能更准。我们直接用就行。
3. **省一次本地计算**。tokenizer 对长文本也要算一会儿，不如直接用 API 白给的数字。

**缺点**：`lastUsage` 只反映**上一次** API 调用时的 token 数。如果我们在两次 API 调用之间加了几条消息（比如加了用户输入还没发给 API），`lastUsage` 就不包含这些新消息。所以 `getTokenCount` 在有 `lastUsage` 时也可能不准——它反映的是上次调用时的状态，不是当前实时状态。

**缓解**：在 `estimateTokens` 里把新加的消息也粗略算上。但本章代码为了简洁没做这个，留作练习。

### 6.6 状态判断：isNearLimit、isOverLimit

```typescript
isNearLimit(): boolean {
  return this.getTokenCount() > this.maxTokens * this.WARN_THRESHOLD;
}

isOverLimit(): boolean {
  return this.getTokenCount() > this.maxTokens * this.FORCE_THRESHOLD;
}
```

**就两行**，但这两个方法是整个策略编排的开关。主循环靠它们决定要不要压缩、要不要截断。

**为什么不直接暴露 token 数让主循环判断**：封装。如果哪天阈值从 80% 改成 85%，只改这里，不用改主循环。

### 6.7 状态显示：getStatus

```typescript
getStatus(): string {
  const tokens = this.getTokenCount();
  const percent = (tokens / this.maxTokens * 100).toFixed(1);
  const bar = this.renderBar(tokens / this.maxTokens);
  return `${bar} ${tokens} / ${this.maxTokens} tokens (${percent}%)`;

private renderBar(ratio: number): string {
  const width = 20;
  const filled = Math.round(ratio * width);

```

**效果**：

```

[████████████████░░░░] 160000 / 200000 tokens (80.0%)
[███████████████████░] 190000 / 200000 tokens (95.0%)
```

**为什么费劲做进度条**：数字不够直观。"160000 / 200000" 要算一下才知道是 80%，进度条一眼就看出来。

### 6.8 截断工具结果：truncateToolResults

前面 4.1 节已经给过完整代码，这里补充几个细节：

```typescript
truncateToolResults(maxResultLength: number = 10000): void {
  for (const msg of this.messages) {
    if (msg.role !== "user") continue;        // tool_result 都在 user 消息里
    if (typeof msg.content === "string") continue;  // 纯文本消息没有 tool_result

    for (const block of msg.content) {
      if (block.type !== "tool_result") continue;
      if (typeof block.content !== "string") continue;  // content 可能是数组
      if (block.content.length <= maxResultLength) continue;

      const half = Math.floor(maxResultLength / 2);
      const head = block.content.slice(0, half);
      const tail = block.content.slice(-half);
      const originalLen = block.content.length;

      block.content =
        head +
        `\n\n...(已截断，原 ${originalLen} 字符，保留头尾各 ${half} 字符)...\n\n` +
        tail;
    }
  }
}
```

**几个边界处理**：

- `msg.role !== "user"` 跳过 assistant 消息——tool_result 总是在 user 角色的消息里（这是 Anthropic API 的约定）。
- `typeof msg.content === "string"` 跳过纯文本消息——纯文本没有 tool_result 块。
- `typeof block.content !== "string"` 跳过 content 是数组的情况——tool_result 的 content 有时是 `ContentBlock[]` 而不是 string，本章不处理这种复杂情况。
- `block.content.length <= maxResultLength` 跳过已经够短的结果——没必要截。

**截断信息要写进替换文本里**（`原 ${originalLen} 字符，保留头尾各 ${half} 字符`）。为什么？让模型知道这里被截了，原内容有多长。否则模型可能以为头尾就是全部，产生误解。

### 6.9 截断历史：truncateHistory

```typescript
truncateHistory(keepRecent: number = 10): void {
  if (this.messages.length <= keepRecent) return;
  const removed = this.messages.length - keepRecent;
  this.messages = this.messages.slice(-keepRecent);
  console.log(`已截断历史，删除 ${removed} 条旧消息，保留最近 ${keepRecent} 条`);
}
```

**就一行核心逻辑**（`slice(-keepRecent)`），但加了两个保护：

- `length <= keepRecent` 时直接返回——没必要截。
- 打日志告诉用户删了多少条——截断是暴力操作，要让用户知道发生了什么。

**一个潜在问题**：`slice(-10)` 可能从工具调用的中间切断——比如保留了 `tool_use` 但删了对应的 `tool_result`，或者反过来。这会导致 API 报错"tool_use_id 不匹配"。**真实代码需要成对保留**，但本章为了简洁忽略这个问题，留作练习。

### 6.10 压缩：compress

前面 4.3 节给过代码，这里重贴并逐行讲：

```typescript
async compress(
  client: Anthropic,
  model: string
): Promise<boolean> {
  // 太少消息不值得压缩
  if (this.messages.length < 10) return false;

  // 划分：旧消息要压缩，最近 4 条保留
  const oldMessages = this.messages.slice(0, -4);
  const recentMessages = this.messages.slice(-4);

  // 把旧消息拼成纯文本
  const conversationText = oldMessages
    .map(m => `${m.role}: ${JSON.stringify(m.content)}`)
    .join("\n");

  // 调用模型总结
  const summaryResponse = await client.messages.create({
    model,
    max_tokens: 1000,
    messages: [{
      role: "user",
      content:
        `请把以下对话历史总结成一段简洁的上下文摘要，` +
        `保留关键信息（用户意图、已做的决定、已读的文件、已发现的问题），` +
        `丢弃冗余细节:\n\n${conversationText}`
    }]
  });

  const summary = summaryResponse.content[0].text;

  // 用总结替换旧消息
  this.messages = [
    {
      role: "user",
      content: `[以下是之前对话的摘要]\n${summary}\n[摘要结束]`
    },
    ...recentMessages
  ];

  return true;
}
```

**逐行讲**：

- `if (this.messages.length < 10) return false`——消息太少时直接返回 false。压缩太少消息没意义，还浪费一次 API 调用。返回 false 让主循环知道压缩没做，可以走兜底策略。
- `slice(0, -4)` 和 `slice(-4)`——把消息分成"要压缩的旧部分"和"要原样保留的最近部分"。为什么保留 4 条而不是 10 条？压缩时上下文已经很满了，保留太多就压缩不了多少。4 条（约 2 轮对话）够模型知道"刚才在干什么"。
- `JSON.stringify(m.content)`——把消息内容序列化成文本。因为 `content` 可能是字符串也可能是数组（带 tool_use、tool_result），统一序列化才能拼进 prompt。
- `max_tokens: 1000`——限制总结长度。总结太长就失去压缩意义了。1000 token 的总结大约能装下"用户想干什么、做了什么、发现了什么"这些要点。
- prompt 里明确要求"保留关键信息、丢弃冗余细节"——引导模型做我们想要的总结，而不是随便复述。
- 替换后 `this.messages` 变成 `[总结消息, ...最近4条]`。总结消息用 `role: "user"`，因为我们要让它看起来像用户提供的背景信息。

**为什么返回 `boolean`**：让主循环知道压缩是否真的发生了。如果返回 false（消息太少），主循环可以走兜底策略（比如直接截断）。

## 七、compress 的原理深入

`compress` 是三种策略里最复杂、也最有意思的一个。专门展开讲。

### 7.1 为什么 compress 比截断好

**截断**的问题是：它不区分信息重要性。一条消息"用户说要 TypeScript"和一条消息"工具返回了 5 万行日志"，截断时一视同仁地删。但前者是关键信息，后者删了无所谓。

**压缩**的核心洞察：**让模型自己判断哪些信息重要**。模型读一遍旧对话，把重要的提炼出来，不重要的丢掉。这比我们写规则判断"哪些重要"准得多——因为"重要性"是语义层面的，规则很难覆盖。

举个例子，旧对话里有：

```
用户: 我在写一个 React 项目
用户: 帮我读 package.json
工具: { "dependencies": { "react": "^18.2.0", "typescript": "^5.0.0" } }
用户: 把 App.tsx 里的类组件改成函数组件
工具: （修改后的代码）
用户: 跑一下测试
工具: （测试输出，5 万 token）
```

**截断**可能直接把前面全删了，模型不知道用户在写 React、不知道用了 TypeScript、不知道改过什么。

**压缩**会总结成：

```
用户在写一个 React 18 + TypeScript 5 项目。
已将 App.tsx 里的类组件改成了函数组件。
刚跑完测试（测试输出已省略）。
```

几百 token，但关键信息都在。模型接着干活不迷糊。

### 7.2 compress 的代价

天下没有免费的午餐。compress 的代价：

1. **一次额外 API 调用**。要花钱、花时间。一次总结调用大约：
   - 输入：旧对话的 token 数（可能几万）。
   - 输出：总结 1000 token。
   - 费用：按 Claude 3 Sonnet 的价格（$3/M input、$15/M output），压缩一次大约 $0.1~0.3。
   - 时间：几秒到十几秒。
2. **总结可能不准**。模型可能：
   - 漏掉关键信息（"用户说要用 TypeScript" 没总结进去）。
   - 总结偏题（把注意力放在不重要的细节上）。
   - 编造内容（幻觉，虽然总结场景少见）。
3. **工具调用上下文丢失**。旧对话里的 `tool_use` / `tool_result` 对被总结成纯文本后，模型不能再"引用"之前的工具结果。如果后续需要引用，就得重新调工具。
4. **格式变化**。总结后的消息是纯文本，和原来的结构化 `MessageParam` 不同。某些依赖消息格式的逻辑可能出问题。

### 7.3 什么时候值得 compress

权衡下来，compress 适合：

- 对话**内容语义密集**——用户做了很多决定、探讨了很多方案，截断会丢掉关键上下文。
- 对话**还有继续的价值**——用户还会基于前面的内容继续聊，不是"前面的事已经了结"。
- **愿意花一次 API 调用的代价**——用户能接受几秒延迟和几分钱费用。

不适合 compress 的情况：

- 对话**主要是工具输出撑大的**——比如就是读了好几个大文件，没什么"决定"或"探讨"。此时工具结果截断更直接。
- 对话**很快要结束了**——用户已经准备收工，没必要花钱压缩。
- **消息太少**（< 10 条）——压缩没意义，`compress` 会直接返回 false。

### 7.4 compress 的 prompt 设计

我们用的 prompt 是：

```
请把以下对话历史总结成一段简洁的上下文摘要，
保留关键信息（用户意图、已做的决定、已读的文件、已发现的问题），
丢弃冗余细节:

{旧对话}
```

**设计要点**：

1. **明确要保留什么**——"用户意图、已做的决定、已读的文件、已发现的问题"。这四类是后续对话最可能用到的。
2. **明确要丢弃什么**——"冗余细节"。给模型一个丢弃的方向。
3. **要求"简洁"**——限制总结长度，否则可能总结得跟原文一样长。
4. **用 `max_tokens: 1000` 硬限制**——即使 prompt 没生效，硬限制也兜底。

**真实 Claude Code 的 compactConversation prompt 更精细**——它会要求模型用特定格式输出、保留工具调用的结构等。我们这里简化了。

## 八、token 计数方式深入

### 8.1 两种方式

**方式一：API usage 返回**

每次调 Claude API，响应里都带一个 `usage` 字段：

```json
{
  "id": "msg_xxx",
  "content": [...],
  "usage": {
    "input_tokens": 12345,
    "output_tokens": 678
  }
}
```

`input_tokens` 就是这次请求的 `messages` 数组总共多少 token，`output_tokens` 是模型这次生成了多少 token。这是**模型实际看到的 token 数**，最准。

**方式二：本地 tokenizer**

本地用分词器算：

```typescript
import { countTokens } from "some-tokenizer";
const tokens = countTokens(JSON.stringify(messages));
```

理论上可以在任何时刻算，不依赖 API 响应。

### 8.2 为什么我们用方式一

三个原因：

1. **Claude 没有官方 tokenizer**。OpenAI 有 `tiktoken`，但 Anthropic 没发布等价物。社区有近似实现，但不保证和 API 一致——可能算出来 12 万 token，API 实际算 13 万，差 1 万就够影响判断。
2. **API usage 是真实值**。API 处理请求时已经算好了，不可能更准。我们直接用，零成本、零误差。
3. **省一次本地计算**。tokenizer 对长文本也要算一会儿（几十毫秒到几百毫秒），不如直接用 API 白给的数字。

### 8.3 方式一的缺点

`lastUsage` 只反映**上一次 API 调用时**的 token 数。问题场景：

```
1. API 调用返回，lastUsage.input_tokens = 100000
2. 用户输入新消息，addMessage 加进 messages
3. 工具执行，addMessage 加进 tool_result
4. 此时调用 getTokenCount()
   → 返回 100000 + output_tokens
   → 但实际 messages 已经涨了，真实 token 数可能是 120000
```

`getTokenCount` 漏算了步骤 2 和 3 加的内容。这在主循环里不是大问题（马上就要再调 API，会拿到新 usage），但判断 `isNearLimit` 时可能偏乐观。

**缓解方案**：在 `getTokenCount` 里把"上次 API 调用后新加的消息"也粗略估算上。伪代码：

```typescript
getTokenCount(): number {
  if (!this.lastUsage) return this.estimateTokens();

  // 上次调用时的 token 数
  let tokens = this.lastUsage.input_tokens + this.lastUsage.output_tokens;

  // 加上上次调用后新加的消息的粗略估算
  // （需要记录上次调用时 messages 的长度）
  for (const msg of this.messages.slice(this.lastUsageMessageCount)) {
    tokens += this.estimateMessageTokens(msg);
  }
  return tokens;
}
```

本章代码为了简洁没做这个，留作练习。

### 8.4 粗略估算的公式

`estimateTokens` 用的是 `字符数 / 4`。这个 4 哪来的？

- 英文：平均 1 token ≈ 4 字符。这是 OpenAI 在 GPT-3 时代给出的经验值，被广泛引用。
- 中文：1 token ≈ 1.5~2 字符，也就是 1 字符 ≈ 0.5~0.7 token。用 `/ 4` 会**低估**中文的 token 数。
- 代码：接近英文，但符号密集时偏多。

**对中英混合内容**，`/ 4` 是一个偏乐观的估算（算出来的 token 数偏少）。这意味着我们的 `isNearLimit` 可能比实际晚触发——实际 85% 了，我们以为才 70%。这是一个已知偏差，用 API usage 来兜底（API 调用后会拿到真实值，`lastUsage` 会被更新）。

**更准的混合估算**：

```typescript
function estimateTokens(text: string): number {
  let tokens = 0;
  for (const char of text) {
    // 中文字符（基本多文种平面）算 0.6 token
    if (/[\u4e00-\u9fff]/.test(char)) tokens += 0.6;
    // 其他按 0.25 token（4 字符/token）
    else tokens += 0.25;
  }
  return Math.ceil(tokens);
}
```

但本章为了简洁用 `/ 4`。对英文为主的代码内容够用。

## 九、状态监控设计

### 9.1 为什么要显示状态

用户不知道上下文用了多少，就像开车没油表——开着开着突然抛锚。状态监控让用户：

1. **心里有数**——看到 60% 还安心，看到 85% 就知道该收尾了。
2. **理解 CLI 的行为**——看到"压缩中..."就知道为什么慢了一下。
3. **调试问题**——如果模型突然忘了前面说的话，看一眼状态发现 95% 触发了截断，就明白原因了。

### 9.2 显示什么

每轮结束显示一行：

```
[████████░░░░░░░░░░░░] 80000 / 200000 tokens (40.0%)
```

包含：

- **进度条**——20 格，直观。
- **当前 token 数**——精确数字。
- **上限**——200000，提醒用户上限是多少。
- **百分比**——一眼看出用了多少。

### 9.3 颜色（可选）

更进一步可以加颜色：

- 0~80%：绿色（正常）。
- 80~95%：黄色（预警）。
- 95~100%：红色（危险）。

用 ANSI 转义码实现：

```typescript
private getStatus(): string {
  const tokens = this.getTokenCount();
  const ratio = tokens / this.maxTokens;
  const percent = (ratio * 100).toFixed(1);
  const bar = this.renderBar(ratio);

  let color = "\x1b[32m";  // 绿
  if (ratio > this.FORCE_THRESHOLD) color = "\x1b[31m";  // 红
  else if (ratio > this.WARN_THRESHOLD) color = "\x1b[33m";  // 黄
  const reset = "\x1b[0m";

  return `${color}${bar} ${tokens} / ${this.maxTokens} tokens (${percent}%)${reset}`;
}
```

本章代码没加颜色（保持简洁），但生产代码建议加。

### 9.4 在主循环里调用

```typescript
// main.ts 主循环
while (true) {
  const userInput = await prompt("你: ");
  ctx.addMessage({ role: "user", content: userInput });

  const response = await client.messages.create({
    model,
    messages: ctx.getMessages(),
    tools,
    max_tokens: 4096,
  });

  ctx.addMessage({ role: "assistant", content: response.content });
  ctx.updateUsage(response.usage);

  // 处理工具调用...

  // 截断和压缩...
  ctx.truncateToolResults();
  if (ctx.isNearLimit()) {
    const ok = await ctx.compress(client, model);
    if (!ok) ctx.truncateHistory();
  }
  if (ctx.isOverLimit()) ctx.truncateHistory();

  // 每轮结束显示状态
  console.log(ctx.getStatus());
}
```

**状态显示放在每轮最后**，让用户看到"这轮结束后上下文用了多少"。如果触发了压缩或截断，用户会看到 token 数掉下来——直观反馈。

## 十、常见陷阱

### 10.1 陷阱一：截断丢失关键信息

**现象**：模型突然"忘了"用户一开始说的需求，开始答非所问。

**原因**：`truncateHistory` 把早期的消息删了，其中包含用户的需求说明。

**例子**：

```
第 1 轮: 用户: 帮我把这个项目从 JavaScript 迁移到 TypeScript
第 2~50 轮: 各种工具调用、代码修改
第 51 轮: 触发截断，第 1 轮被删
第 52 轮: 模型不知道要迁移到 TS 了，可能开始写 JS
```

**避免**：

- 用 `compress` 而不是 `truncateHistory`——compress 会把"迁移到 TS"这个意图总结进去。
- 或者把关键需求**固定**在系统提示里，不放进会被截断的 `messages`。
- 或者截断时**保留第一条用户消息**——很多对话的第一条是总需求。

### 10.2 陷阱二：压缩总结不准

**现象**：压缩后模型行为变怪，好像总结里漏了什么。

**原因**：模型总结时漏掉了关键信息，或者总结偏题。

**例子**：旧对话里用户说"用 React 18 的 Suspense"，总结里只写"用 React"，丢了"18"和"Suspense"。模型后续可能用 React 17 的写法。

**避免**：

- **prompt 里明确列出要保留的信息类型**（我们做了：用户意图、已做的决定、已读的文件、已发现的问题）。
- **压缩后让用户看一眼总结**——打印出来，用户发现漏了可以手动补。
- **不要压缩太少消息**——消息越少，总结越容易漏（信息密度相对高）。我们设了 `< 10` 不压缩。
- **关键信息放系统提示**——最稳，不会被压缩。

### 10.3 陷阱三：token 估算偏差

**现象**：`isNearLimit` 没触发，但 API 报错"prompt is too long"。

**原因**：`estimateTokens` 用 `字符数 / 4`，对中文、JSON 等内容低估了 token 数。实际已经超限，估算还说没到 80%。

**例子**：一段 10 万字符的中文对话，`estimateTokens` 算 25000 token（10 万 / 4），实际可能是 50000 token（中文 1 字 ≈ 0.5 token）。差了一倍。

**避免**：

- **优先用 API usage**——真实值，不会偏。我们做了。
- **估算偏保守**——用 `/ 3` 而不是 `/ 4`，宁可早触发也别晚触发。
- **混合内容用更细的估算**——区分中英文，分别用不同比例。

### 10.4 陷阱四：工具结果未截断

**现象**：一次 `read_file` 读了大文件，下一轮 API 直接报超限。

**原因**：忘记调 `truncateToolResults`，或者 `maxResultLength` 设太大。

**例子**：

```typescript
// 忘了这行：
// ctx.truncateToolResults();

// 或者设太大：
ctx.truncateToolResults(200000);  // 等于没截
```

**避免**：

- **每次工具执行后必调 `truncateToolResults`**——养成习惯，写进主循环固定位置。
- **`maxResultLength` 别设太大**——10000 字符（约 2500 token）是个合理值。一个工具结果 2500 token，20 次工具调用也才 5 万 token。
- **工具内部就限制输出**——比如 `read_file` 读文件时，超过 1 万字符就只读头尾。这样工具结果天生就不大，`truncateToolResults` 是兜底。

### 10.5 陷阱五：tool_use 和 tool_result 被截断拆散

**现象**：截断后 API 报错"tool_use_id xxx not found"或"tool_result without tool_use"。

**原因**：`truncateHistory(10)` 用 `slice(-10)`，可能正好把 `tool_use` 留下、对应的 `tool_result` 删了（或反过来）。API 要求 `tool_use` 和 `tool_result` 必须成对出现。

**避免**：

- **截断时成对保留**——找到所有 `tool_use` 的 id，确保对应的 `tool_result` 也在保留范围内。
- **或者截断到最近的"非工具调用边界"**——找一个没有未配对 tool_use 的位置截断。

本章代码没处理这个，留作练习。这是一个**真实会发生的 bug**，生产代码必须处理。

## 十一、与真实 Claude Code 对比

### 11.1 对比表

| 方面 | 本章 | 真实 Claude Code |
|------|------|------------------|
| token 计数 | API usage 返回 | 用 tokenizer 精确计数 |
| 截断策略 | 头尾保留 | 智能截断（保留关键信息） |
| 压缩 | 用模型总结 | `compactConversation` 专用 prompt |
| 触发时机 | 80% 预警，95% 强制 | 多级阈值 |
| 状态显示 | token 数 + 百分比 | 同 |
| 工具结果处理 | 每次截断 | 工具内部就限制 + 外部截断 |
| tool_use 配对 | 不处理 | 严格成对保留 |

### 11.2 tokenizer

真实 Claude Code 用 Anthropic 内部的 tokenizer 精确计数。这意味着：

- 它可以在**任何时刻**知道精确 token 数，不依赖 API 响应。
- 判断 `isNearLimit` 不会偏。
- 可以在加一条消息前先算一下"加了会不会超限"，超了就先压缩。

我们用 API usage，只能在**API 调用后**知道精确值。两次 API 调用之间是盲区，靠粗略估算。这是本章的主要简化。

### 11.3 compactConversation

真实 Claude Code 有一个专门的 `compactConversation` 函数，用精心设计的 prompt 压缩对话。和我们的 `compress` 比：

- **prompt 更精细**——明确要求保留工具调用结构、代码块、文件路径等。
- **输出格式化**——总结不是一段纯文本，而是结构化的"上下文摘要"。
- **多级压缩**——先轻压缩（只去冗余），不够再重压缩（总结语义）。
- **保留最近更多消息**——不是固定 4 条，而是根据 token 余量动态决定保留多少。

我们的 `compress` 是简化版，但核心思路一样：**让模型自己判断什么重要**。

### 11.4 多级阈值

真实 Claude Code 的阈值更复杂：

```
0% ──── 50% ──── 80% ──── 92% ──── 95% ──── 100%
         │        │        │        │
         │        │        │        └─ 强制截断
         │        │        └─ 重压缩
         │        └─ 轻压缩
         └─ 开始监控
```

- 50%：开始留意，状态栏变色。
- 80%：轻压缩（只去冗余工具结果）。
- 92%：重压缩（总结语义）。
- 95%：强制截断（兜底）。

我们简化成两级（80%、95%），够用但不如它精细。

### 11.5 工具内部限制

真实 Claude Code 的工具**天生**就限制输出：

- `read_file` 默认只读前 2000 行，超过要显式 `offset` / `limit`。
- `run_command` 有输出长度限制，超过截断。
- `grep` 限制匹配行数。

这样工具结果天生就不大，`truncateToolResults` 是兜底而不是主力。我们的工具没做内部限制，完全靠 `truncateToolResults` 兜，比较被动。

## 十五、本章小结

这一章的核心就一句话：**工具结果是上下文膨胀的主要矛盾，要在超限前主动管理**。

具体做了什么：

1. **`ContextManager` 类**——封装 messages 数组、token 计数、状态判断、三种策略。
2. **工具结果截断**——每次工具执行后压住大输出，预防性。
3. **对话压缩**——80% 时用模型总结旧对话，保留关键信息。
4. **历史截断**——95% 时兜底，直接砍旧消息。
5. **状态监控**——每轮显示 token 使用率，用户心里有数。

关键设计决策：

- **用 API usage 而不是本地 tokenizer**——准、省、Claude 没官方 tokenizer。
- **多级阈值而不是单级**——80% 预警、95% 强制，给温和策略留空间。
- **压缩优先于截断**——压缩保留信息，截断丢弃信息，能压缩就先压缩。
- **工具结果截断放最前**——它针对主要矛盾，且零额外开销。
