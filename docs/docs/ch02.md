## 1. 本章目标

理解两件事：

1. **tool_use 协议** — 模型如何"请求"调用工具，工具结果如何回传给模型
2. **内层 agentic loop** — 工具调用可能连续多轮，模型看完一个工具结果后可能再调下一个工具

第一章的循环是"用户说话 → 模型回话 → 等用户"，只有一层循环。这一章我们引入**内层循环**：模型回话后，如果它想调工具，我们就执行工具、把结果塞回 messages、再调一次模型——如此反复，直到模型说"我做完了"。

这个内层循环就是 **Agent 的本质**。所有 Agent 系统（Claude Code、Cursor、Devin）的核心都是这个循环。区别只在于工具数量、工具实现、权限控制、错误处理这些工程细节。**核心循环完全一致。**

## 2. 前置知识：聊天机器人 vs Agent

### 2.1 什么是工具调用

**工具调用（Tool Use / Function Calling）** 是一种让大语言模型"使用外部工具"的机制。

普通对话中，模型只能输出文本。它不能读文件、不能查数据库、不能执行代码、不能调 API。工具调用就是给模型开了一扇窗：模型可以说"我想调用 read\_file 工具，参数是 path='hello.txt'"，然后**由你的代码**去真正执行这个工具，把结果回传给模型，模型再基于结果继续对话。

关键点：**模型本身不执行任何工具**。模型只是"请求"调用工具。真正执行工具的是你的代码。模型是一个"决策者"，它决定调哪个工具、传什么参数；你的代码是"执行者"，负责真正干活。

这个分工非常重要：
- 模型不能直接访问你的文件系统（安全）
- 模型不能直接执行任意命令（安全）
- 你的代码可以决定执行哪些工具、拒绝哪些工具（权限控制）
- 你的代码可以记录每次工具调用（审计日志）

### 2.2 为什么需要工具

没有工具的模型有几个致命限制：

**1. 知识截止。** 模型的训练数据有截止日期。你问"今天北京天气如何"，它不知道。给它一个 `get_weather` 工具，它就能查实时天气。

**2. 不能访问用户数据。** 你问"读一下我桌面的 notes.txt"，模型读不到。给它一个 `read_file` 工具，它就能读你的文件。

**3. 不能执行计算。** 你问"123456789 × 987654321 等于多少"，模型可能算错（大数乘法是 LLM 的弱项）。给它一个 `calculator` 工具，它就能精确计算。

**4. 不能产生副作用。** 你问"帮我创建一个 hello.txt"，模型只能告诉你"你可以用 echo 命令..."。给它一个 `write_file` 工具，它就能直接创建文件。

**5. 容易幻觉。** 你问"项目里有哪些 TypeScript 文件"，模型会瞎猜。给它一个 `list_files` 工具，它就能真正列出文件。

工具的本质是**扩展模型的能力边界**。模型负责理解意图、规划步骤、选择工具；工具负责真正与外部世界交互。

### 2.3 聊天机器人 vs Agent 的本质区别

| 方面 | 聊天机器人 | Agent |
|------|-----------|-------|
| 能力 | 只能生成文本 | 能调用工具，与外部世界交互 |
| 循环结构 | 单层：用户→模型→用户 | 双层：外层等用户，内层跑工具循环 |
| 状态 | 只有对话历史 | 对话历史 + 工具调用历史 + 外部世界状态 |
| 主动性 | 被动回答 | 主动规划、主动调用工具、主动验证结果 |
| 失败处理 | 答错就答错了 | 可以看到工具报错，调整策略重试 |
| 典型例子 | ChatGPT 网页版（无插件） | Claude Code、Cursor、Devin |

**最本质的区别是循环结构。** 聊天机器人是"一问一答"，Agent 是"一问多步多答"。用户问一个问题，Agent 可能要调 5 个工具、读 3 个文件、写 2 个文件，最后才给出答案。这个"多步"就是内层循环。

### 2.4 一个直观的对比例子

用户问："把 src 目录下所有 .ts 文件的行数统计出来，写到 lines.txt"

**聊天机器人**（无工具）：
```
用户: 把 src 目录下所有 .ts 文件的行数统计出来，写到 lines.txt
模型: 你可以用以下命令：
      find src -name "*.ts" -exec wc -l {} + > lines.txt
      这会统计所有 .ts 文件的行数并写入 lines.txt。
```
模型只能告诉你怎么做，不能替你做。

**Agent**（有工具）：
```
用户: 把 src 目录下所有 .ts 文件的行数统计出来，写到 lines.txt
模型: [调 list_files("src")] → 看到 [a.ts, b.ts, c.ts]
模型: [调 read_file("src/a.ts")] → 100 行
模型: [调 read_file("src/b.ts")] → 200 行
模型: [调 read_file("src/c.ts")] → 300 行
模型: [调 write_file("lines.txt", "a.ts: 100\nb.ts: 200\nc.ts: 300")]
模型: 已完成。统计结果已写入 lines.txt。
```
Agent 自己读文件、自己统计、自己写文件。用户只说了一句话，Agent 干了 5 步。

这就是 Agent 的力量。而这 5 步的执行，靠的就是本章要讲的**内层 agentic loop**。

## 3. tool_use 协议深入

### 3.1 协议三步骤总览

tool\_use 协议是一个**三步骤的循环**：

```
① 定义工具：在调 API 时传入 tools 参数，告诉模型有哪些工具可用
② 模型请求：response 的 content 里出现 tool_use block，模型说"我想调这个工具"
③ 回传结果：你执行工具，构造 tool_result 消息塞回 messages，继续调 API
```

这三步会**循环执行**。模型可能调一个工具、看结果、再调一个工具、看结果、再调一个工具...直到它认为任务完成，返回 `stop_reason: "end_turn"`。

下面逐步详解。

### 3.2 第一步：定义工具

定义工具就是告诉模型"你有哪些工具可用"。这是通过 API 请求的 `tools` 参数完成的：

```typescript
const tools = [
  {
    name: "read_file",
    description: "读取指定路径的文件内容。返回文件的文本内容。",
    input_schema: {
      type: "object",
      properties: {
        path: {
          type: "string",
          description: "要读取的文件路径（相对路径或绝对路径）"
        }
      },
      required: ["path"]
    }
  },
  {
    name: "write_file",
    description: "将内容写入指定路径的文件。如果文件已存在则覆盖，不存在则创建。",
    input_schema: {
      type: "object",
      properties: {
        path: { type: "string", description: "要写入的文件路径" },
        content: { type: "string", description: "要写入的文件内容" }
      },
      required: ["path", "content"]
    }
  }
];

// 调 API 时传入
const response = await client.messages.create({
  model,
  messages,
  tools,  // ← 这里
  max_tokens: 4096
});
```

每个工具有三个字段：
- `name`：工具名，模型用它来引用工具。必须是字符串，建议用 snake\_case。
- `description`：自然语言描述，告诉模型这个工具做什么、什么时候该用。**极其重要**，后面专门讲。
- `input_schema`：JSON Schema，定义工具的参数结构。模型按这个 schema 生成参数。

**这一步是"声明"。** 你只是告诉模型"有这些工具可用"，模型还没决定用不用。

### 3.3 第二步：模型请求

模型收到请求后，它会决定：
- 不需要工具，直接回答 → `stop_reason: "end_turn"`，content 里只有 text block
- 需要调工具 → `stop_reason: "tool_use"`，content 里有 tool\_use block

一个 tool\_use block 长这样：

```typescript
{
  type: "tool_use",
  id: "toolu_01ABC123",        // 工具调用的唯一 ID，回传结果时要用
  name: "write_file",          // 要调用的工具名
  input: {                     // 模型生成的参数，符合 input_schema
    path: "hello.txt",
    content: "Hello World"
  }
}
```

注意几个点：
- `id` 是模型生成的，每次工具调用有唯一 ID。你回传结果时必须用这个 ID 关联。
- `input` 是模型按你给的 `input_schema` 生成的。如果 schema 要求 `path` 是 string，模型就会生成 string。
- 一次 response 可能包含**多个** tool\_use block（并行调用多个工具），后面专门讲。
- 一次 response 也可能同时包含 text block 和 tool\_use block。text 是模型的"自言自语"（"我来创建这个文件"），tool\_use 是实际的工具请求。

**这一步是"决策"。** 模型决定调哪个工具、传什么参数。

### 3.4 第三步：回传结果

你执行完工具后，要把结果回传给模型。这是通过构造一条 `role: "user"` 的消息，content 里放 `tool_result` block：

```typescript
messages.push({
  role: "user",
  content: [
    {
      type: "tool_result",
      tool_use_id: "toolu_01ABC123",  // ← 关联到第二步的 id
      content: "已成功写入文件: hello.txt (11 字符)"
    }
  ]
});
```

然后**继续调 API**，模型会看到工具结果，决定下一步：
- 还需要调别的工具 → 又返回 `stop_reason: "tool_use"`
- 任务完成 → 返回 `stop_reason: "end_turn"`，给出最终文本回复

**这一步是"反馈"。** 你把执行结果告诉模型，模型基于结果继续决策。

三步循环：声明 → 决策 → 反馈 → 决策 → 反馈 → ... → 结束。

### 3.5 JSON Schema 是什么

`input_schema` 用的是 **JSON Schema**，一种描述 JSON 数据结构的标准格式。

最简单的 JSON Schema：

```json
{
  "type": "object",
  "properties": {
    "path": { "type": "string" }
  },
  "required": ["path"]
}
```

这表示：一个对象，有一个 `path` 属性，类型是 string，且必填。

JSON Schema 能描述很复杂的结构：

```json
{
  "type": "object",
  "properties": {
    "files": {
      "type": "array",
      "items": { "type": "string" },
      "description": "要处理的文件路径列表"
    },
    "options": {
      "type": "object",
      "properties": {
        "recursive": { "type": "boolean", "default": false },
        "encoding": { "type": "string", "enum": ["utf-8", "gbk"] }
      }
    }
  },
  "required": ["files"]
}
```

这表示：`files` 是字符串数组，`options.recursive` 是布尔值默认 false，`options.encoding` 是枚举只能是 "utf-8" 或 "gbk"。

**为什么用 JSON Schema？** 因为模型训练时学过 JSON Schema。你给它一个 schema，它能按 schema 生成合法的参数。这是模型和工具之间的"契约"。

常见 type 有：`object`、`string`、`number`、`integer`、`boolean`、`array`、`null`。

常见约束：`required`（必填字段）、`enum`（枚举值）、`default`（默认值）、`description`（描述）、`minimum`/`maximum`（数值范围）、`minLength`/`maxLength`（字符串长度）。

**本章只用到最简单的 schema**：object + string properties + required。后面章节会用到更复杂的。

### 3.6 description 为什么极其重要

`description` 是模型理解工具的**唯一途径**。

模型看不到你的工具实现代码。它不知道 `read_file` 内部是 `fs.readFileSync` 还是 `fetch`。它只知道你告诉它的 `description`。

**description 写得好，模型就正确使用工具。description 写得差，模型就乱调。**

举个差例子：

```typescript
{
  name: "read_file",
  description: "read file",  // ← 太简略
  input_schema: { ... }
}
```

模型看到这个，可能：
- 不知道该传相对路径还是绝对路径
- 不知道返回的是文本还是二进制
- 不知道文件不存在时会怎样
- 在该用 read\_file 的地方用了 write\_file

好例子：

```typescript
{
  name: "read_file",
  description: "读取指定路径的文件内容。返回文件的文本内容（UTF-8 编码）。如果文件不存在返回错误信息。",
  input_schema: {
    type: "object",
    properties: {
      path: {
        type: "string",
        description: "要读取的文件路径，支持相对路径和绝对路径"
      }
    },
    required: ["path"]
  }
}
```

模型看到这个，就知道：
- 这个工具返回 UTF-8 文本（不能用来读图片）
- 文件不存在会返回错误信息（不是抛异常）
- path 支持相对和绝对路径

**description 的写作原则**：
1. 说清楚工具做什么
2. 说清楚输入参数的含义和格式
3. 说清楚返回值的格式
4. 说清楚边界情况（文件不存在、权限不足等）
5. 说清楚什么时候该用这个工具、什么时候不该用

真实 Claude Code 的工具 description 都写得很长很详细，后面会看到例子。

## 4. 内层 agentic loop 详解

### 4.1 为什么需要内层循环

考虑这个请求："读 a.txt，如果里面写的是 'delete'，就删掉 b.txt，否则读 c.txt"

这个任务需要：
1. 读 a.txt
2. **看 a.txt 的内容**，决定下一步
3. 根据内容，要么删 b.txt，要么读 c.txt

第 2 步是关键。模型必须**看到工具结果**才能决定下一步。这不是一次 API 调用能完成的——模型第一次调用时还没看到 a.txt 的内容，它不可能预先决定是删 b.txt 还是读 c.txt。

所以需要**循环**：
- 调 API → 模型说"读 a.txt" → 执行 → 结果塞回 messages
- 调 API → 模型看到 a.txt 内容是 "delete" → 模型说"删 b.txt" → 执行 → 结果塞回 messages
- 调 API → 模型说"任务完成" → 结束

这个"调 API → 执行工具 → 塞结果 → 再调 API"的循环，就是**内层 agentic loop**。

**没有内层循环，模型就只能"盲调"工具**——一次性调一堆工具，看不到中间结果。这对简单任务可以，对需要根据中间结果决策的任务不行。

### 4.2 两层循环的结构

第一章的循环（单层）：

```
while (true) {
  用户输入
  调 LLM
  输出
  等用户
}
```

第二章的循环（双层）：

```
while (true) {                    // 外层：等用户
  用户输入

  while (true) {                  // 内层：工具循环
    调 LLM
    if (想调工具) {
      执行工具
      结果塞回 messages
      continue                    // 继续内层循环
    } else {
      输出
      break                       // 跳出内层，回外层等用户
    }
  }
}
```

**外层循环**负责多轮对话：用户说一句、Agent 处理一句、等用户下一句。
**内层循环**负责单轮内的工具调用：用户说一句，Agent 可能要调好几次工具才回答。

两层循环嵌套，就是 Agent 的完整骨架。

### 4.3 stop_reason 分支逻辑

内层循环的核心是 `stop_reason` 分支：

```typescript
if (response.stop_reason === "tool_use") {
  // 模型想调工具
  // 执行工具，塞结果，继续循环
} else {
  // stop_reason === "end_turn"（或其他）
  // 模型说完了，输出，跳出循环
}
```

`stop_reason` 有几个值：
- `"end_turn"`：模型说完了，正常结束
- `"tool_use"`：模型想调工具，需要你执行工具并回传结果
- `"max_tokens"`：达到 max\_tokens 上限，被截断
- `"stop_sequence"`：遇到 stop sequence，提前停止

**本章只关心两个**：`tool_use`（继续循环）和 `end_turn`（跳出循环）。其他值当 `end_turn` 处理（输出并跳出）。

**为什么用 if-else 而不是 switch？** 因为只有两种情况需要区分：要继续循环 vs 要跳出循环。if-else 最简洁。

### 4.4 连续工具调用示例

用户："创建一个 test.txt，内容是 'hello'，然后读出来确认一下"

这个任务需要两次工具调用，**串行**执行（第二次依赖第一次的结果）：

```
第 1 次调 API:
  messages = [
    { role: "user", content: "创建 test.txt 内容 hello，然后读出来确认" }
  ]
  → response:
      stop_reason = "tool_use"
      content = [
        { type: "text", text: "我先创建文件" },
        { type: "tool_use", id: "toolu_1", name: "write_file",
          input: { path: "test.txt", content: "hello" } }
      ]

执行工具: fs.writeFileSync("test.txt", "hello")
messages.push({ role: "assistant", content: response.content })
messages.push({
  role: "user",
  content: [{ type: "tool_result", tool_use_id: "toolu_1",
              content: "已成功写入文件: test.txt (5 字符)" }]
})

第 2 次调 API:
  → response:
      stop_reason = "tool_use"
      content = [
        { type: "text", text: "现在读出来确认" },
        { type: "tool_use", id: "toolu_2", name: "read_file",
          input: { path: "test.txt" } }
      ]

执行工具: fs.readFileSync("test.txt")
messages.push({ role: "assistant", content: response.content })
messages.push({
  role: "user",
  content: [{ type: "tool_result", tool_use_id: "toolu_2",
              content: "hello" }]
})

第 3 次调 API:
  → response:
      stop_reason = "end_turn"
      content = [{ type: "text", text: "已确认，文件内容是 hello" }]

输出: "已确认，文件内容是 hello"
跳出内层循环
```

注意：
- 每次调 API 都传**完整的 messages**，包括之前所有工具调用和结果
- 每次都要 push assistant 消息（response.content）和 tool\_result 消息
- 模型在第二次调用时看到了第一次的工具结果，所以知道文件已创建
- 第三次模型看到 read\_file 的结果是 "hello"，确认无误，end\_turn

这就是连续工具调用。模型像一个"边做边看"的人：做一步、看结果、决定下一步。

### 4.5 内层循环的终止条件

内层循环什么时候结束？**当 `stop_reason` 不是 `"tool_use"` 时**。

正常情况：模型认为任务完成，返回 `end_turn`，循环结束。

异常情况：
- **max\_tokens**：模型输出太长被截断。本章当 end\_turn 处理（不完美，但简单）。
- **API 报错**：网络问题、超限等。被外层 try-catch 捕获。
- **死循环**：模型一直调工具不结束。本章没有防护，真实 Claude Code 有最大迭代次数限制。

**重要：本章没有限制内层循环次数。** 如果模型陷入死循环（一直调工具），程序会卡死。真实 Claude Code 会限制最大工具调用次数（比如 50 次），超过就强制结束。这是个可以改进的点，练习题里会提到。

## 6. tools.ts 逐行讲解

### 6.1 import 三个模块

```typescript
import * as fs from "fs";
import * as path from "path";
import type Anthropic from "@anthropic-ai/sdk";
```

- `fs`：Node.js 文件系统模块，readFile/writeFile/mkdir 等
- `path`：Node.js 路径模块，resolve/dirname 等，处理跨平台路径
- `Anthropic`（type-only）：只引入类型，不引入运行时值。用于复用 SDK 的 Tool、ToolUseBlock 等类型定义

**为什么用 `import * as`？** 把整个模块当命名空间导入，用 `fs.readFileSync` 而不是 `readFileSync`。代码更清晰，一眼知道是 fs 的方法。

**为什么 `import type`？** 因为只需要类型，不需要运行时值。这样编译后这行 import 会被删除，减小产物体积。

### 6.2 类型导出

```typescript
export type Tool = Anthropic.Tool;
export type ToolUseBlock = Anthropic.ToolUseBlock;
export type ToolResultBlockParam = Anthropic.ToolResultBlockParam;
```

从 SDK 复用三个类型，起别名导出：
- `Tool`：工具定义的类型（name/description/input\_schema）
- `ToolUseBlock`：response 里 tool\_use block 的类型
- `ToolResultBlockParam`：构造 tool\_result 消息时用的类型

**为什么不自己定义类型？** 因为 SDK 的类型最准确，跟 API 规范完全一致。自己定义容易漏字段或写错类型。复用 SDK 类型是最稳妥的做法。

### 6.3 read_file 工具定义

```typescript
export const tools: Tool[] = [
  {
    name: "read_file",
    description:
      "读取指定路径的文件内容。返回文件的文本内容。",
    input_schema: {
      type: "object" as const,
      properties: {
        path: {
          type: "string",
          description: "要读取的文件路径（相对路径或绝对路径）",
        },
      },
      required: ["path"],
    },
  },
  // ... write_file
];
```

逐字段看：
- `name: "read_file"`：工具名，模型用它引用工具。snake\_case 是惯例。
- `description`：自然语言描述。这里说"读取指定路径的文件内容，返回文本内容"。
- `input_schema.type: "object"`：参数必须是个对象（不是 string、number）。
- `input_schema.properties.path`：对象有个 `path` 属性，类型 string。
- `input_schema.required: ["path"]`：path 是必填。模型不传 path 会报错。
- `as const`：TypeScript 类型收窄。把 `"object"` 收窄成字面量类型 `"object"` 而不是 `string`，避免类型报错。

**为什么 path 的 description 也要写？** 告诉模型 path 支持相对和绝对路径。不写的话模型可能只传绝对路径，或者传一个奇怪的格式。

### 6.4 write_file 工具定义

```typescript
{
  name: "write_file",
  description:
    "将内容写入指定路径的文件。如果文件已存在则覆盖，不存在则创建。",
  input_schema: {
    type: "object" as const,
    properties: {
      path: {
        type: "string",
        description: "要写入的文件路径",
      },
      content: {
        type: "string",
        description: "要写入的文件内容",
      },
    },
    required: ["path", "content"],
  },
},
```

和 read\_file 类似，但有两个参数：
- `path`：文件路径
- `content`：要写入的内容

description 里特别说明"已存在则覆盖，不存在则创建"。这很重要——模型知道这个行为，就不会担心覆盖问题，也不会先检查文件是否存在。

**为什么不加一个 append 模式？** 保持简单。本章只有两个工具，参数越少越好。append 模式可以做成单独的工具 `append_file`，后面章节再说。

### 6.5 executeTool 函数签名

```typescript
export function executeTool(name: string, input: any): string {
  try {
    switch (name) {
      case "read_file": { ... }
      case "write_file": { ... }
      default: return `错误: 未知工具 "${name}"`;
    }
  } catch (err: any) {
    return `错误: ${err.message}`;
  }
}
```

- `name: string`：工具名，决定走哪个 case
- `input: any`：工具参数。用 `any` 是因为不同工具参数结构不同。生产代码可以用泛型或联合类型。
- 返回值 `string`：工具结果。**总是返回字符串**，不抛异常。错误也用字符串返回（"错误: ..."）。

**为什么用 switch-case 而不是 if-else？** 工具多了 if-else 会很长很难看。switch-case 更清晰，加新工具只需加一个 case。

**为什么用 try-catch 包住？** 工具执行可能抛异常（文件不存在、权限不足、磁盘满）。不 catch 会让整个程序崩。catch 后把异常转成错误字符串返回，模型看到错误能调整策略。

**为什么返回字符串而不是抛异常？** 因为工具结果要回传给模型。模型能理解"错误: 文件不存在"这样的文本，但不能理解一个 JavaScript 异常对象。把错误转成文本是最简单的处理方式。

### 6.6 read_file 执行分支

```typescript
case "read_file": {
  const filePath = path.resolve(input.path);
  if (!fs.existsSync(filePath)) {
    return `错误: 文件不存在: ${input.path}`;
  }
  const content = fs.readFileSync(filePath, "utf-8");
  return content;
}
```

三步：
1. `path.resolve(input.path)`：把相对路径转成绝对路径。比如 `"test.txt"` 转成 `"/current/dir/test.txt"`。
2. `fs.existsSync`：检查文件是否存在。不存在直接返回错误字符串。
3. `fs.readFileSync(filePath, "utf-8")`：同步读文件，编码 utf-8。返回文件内容。

**为什么先检查存在性再读？** 因为 `readFileSync` 不存在会抛异常。虽然外面有 try-catch，但主动检查能返回更友好的错误信息（"文件不存在: xxx"而不是"ENOENT: no such file or directory"）。

**为什么用同步 readFileSync 而不是异步 readFile？** 因为 executeTool 不是 async 函数。工具执行通常很快（读个小文件），同步够用。如果要读大文件或做网络请求，应该改成 async。本章保持简单。

### 6.7 write_file 执行分支

```typescript
case "write_file": {
  const filePath = path.resolve(input.path);
  const dir = path.dirname(filePath);
  if (!fs.existsSync(dir)) {
    fs.mkdirSync(dir, { recursive: true });
  }
  fs.writeFileSync(filePath, input.content, "utf-8");
  return `已成功写入文件: ${input.path} (${input.content.length} 字符)`;
}
```

四步：
1. `path.resolve`：转绝对路径。
2. `path.dirname`：取目录部分。比如 `"/a/b/c.txt"` → `"/a/b"`。
3. `fs.existsSync(dir)` + `mkdirSync`：如果目录不存在，递归创建。这样模型可以写 `src/utils/helper.ts`，即使 `src/utils` 目录不存在也能自动创建。
4. `fs.writeFileSync`：同步写文件，编码 utf-8。

返回值包含文件路径和字符数：`"已成功写入文件: test.txt (11 字符)"`。这个信息会回传给模型，模型知道写成功了、写了多少字符。

**为什么自动创建目录？** 因为模型经常写嵌套路径（`src/components/Button.tsx`），如果目录不存在就失败，体验很差。自动创建目录让模型更自由。

**为什么返回字符数？** 让模型确认写入的内容长度对不对。如果模型想写 100 字符但只写了 50，它能从返回值发现问题。

### 6.8 default 分支与错误兜底

```typescript
default:
  return `错误: 未知工具 "${name}"`;
```

如果模型调了一个没定义的工具（比如 `delete_file`），default 分支返回错误。模型看到"未知工具"会知道这个工具不可用，换一个。

```typescript
} catch (err: any) {
  return `错误: ${err.message}`;
}
```

外层 try-catch 兜底。任何异常（fs 抛的、path 抛的、JSON 解析抛的）都被转成错误字符串返回。

**这两层错误处理的意义**：工具执行**永远返回字符串**，永远不抛异常。这保证了内层循环不会被异常打断。模型总是能收到工具结果（成功的或错误的），基于结果继续决策。

## 7. main.ts 逐行讲解

### 7.1 import 与 Ch1 的差异

```typescript
import Anthropic from "@anthropic-ai/sdk";
import * as readline from "readline";
import * as dotenv from "dotenv";
import { tools, executeTool, type ToolResultBlockParam } from "./tools.js";
```

前三行和 Ch1 一样。第四行从 `tools.ts` 导入：
- `tools`：工具定义数组，传给 API
- `executeTool`：工具执行函数
- `ToolResultBlockParam`：类型，用于构造 tool\_result

**为什么 import 路径是 `./tools.js` 而不是 `./tools.ts`？** 因为用 `tsx` 运行 TypeScript，它编译后是 .js。import 路径要写编译后的文件名。这是 Node.js ESM 的规则。

### 7.2 内层 while 循环

```typescript
while (true) {
  const userInput = await prompt("\n> ");
  // ...
  messages.push({ role: "user", content: userInput });

  try {
    while (true) {  // ← 内层 agentic loop
      // ...
    }
  } catch (err) { ... }
}
```

外层 while：等用户输入、push user 消息、进入内层循环。
内层 while：调 API、处理 tool\_use 或 end\_turn、决定继续还是跳出。

**内层循环是本章的核心。** 所有 Agent 系统都有这个内层循环。

### 7.3 tools 参数传入

```typescript
const response = await client.messages.create({
  model,
  max_tokens: maxTokens,
  messages,
  tools,  // ← 新增
});
```

和 Ch1 唯一的差异：多了 `tools` 参数。这告诉模型"你有这些工具可用"。

**不传 tools 会怎样？** 模型不会返回 tool\_use block，stop\_reason 永远是 end\_turn。就是 Ch1 的聊天机器人。

**传了 tools 模型一定会用吗？** 不一定。模型根据问题决定用不用。问"你好"模型不会调工具，问"读 a.txt"模型会调 read\_file。

### 7.4 push assistant 消息

```typescript
messages.push({ role: "assistant", content: response.content });
```

**这行极其重要，千万别漏。**

response.content 是模型返回的内容，可能包含 text block 和 tool\_use block。必须把它作为 assistant 消息塞回 messages，这样下次调 API 时模型能看到自己之前说了什么。

**漏掉这行会怎样？** 下次调 API 时，messages 里上一条是 user 消息，紧接着又是 user 消息（tool\_result）。API 会报错"messages must alternate between user and assistant"。就算不报错，模型也看不到自己之前的工具请求，会混乱。

### 7.5 stop_reason === "tool_use" 分支

```typescript
if (response.stop_reason === "tool_use") {
  // 模型请求调用工具
  const toolResults: ToolResultBlockParam[] = [];

  for (const block of response.content) {
    if (block.type === "tool_use") {
      // ...
    }
  }

  messages.push({ role: "user", content: toolResults });
  // 不 break，继续内层循环
} else {
  // end_turn
  // ...
  break;
}
```

stop\_reason 是 tool\_use 时：
1. 准备一个空数组 `toolResults`
2. 遍历 response.content，找所有 tool\_use block
3. 对每个 tool\_use block，执行工具，构造 tool\_result，push 到 toolResults
4. 把所有 tool\_result 作为一个 user 消息 push 到 messages
5. **不 break**，继续内层循环（再调一次 API）

stop\_reason 不是 tool\_use 时（通常是 end\_turn）：
1. 提取文本输出给用户
2. **break**，跳出内层循环，回外层等用户

### 7.6 遍历 content 找 tool_use block

```typescript
for (const block of response.content) {
  if (block.type === "tool_use") {
    console.log(`\n  [工具调用] ${block.name}(${JSON.stringify(block.input)})`);
    // ...
  }
}
```

response.content 是个数组，可能同时包含 text block 和 tool\_use block。遍历时只处理 tool\_use block，跳过 text block（text block 已经在 push assistant 消息时存了）。

`console.log` 打印工具调用信息，让用户看到 Agent 在干什么。比如：
```
  [工具调用] write_file({"path":"hello.txt","content":"Hello World"})
  [工具结果] 已成功写入文件: hello.txt (11 字符)
```

这个日志很重要——让用户看到 Agent 的"思考过程"，不是黑盒。

### 7.7 executeTool 执行

```typescript
const result = executeTool(block.name, block.input);
console.log(`  [工具结果] ${result.slice(0, 200)}${result.length > 200 ? "..." : ""}`);
```

`executeTool(block.name, block.input)` 执行工具，返回字符串结果。

`result.slice(0, 200)` 只打印前 200 字符。为什么？因为 read\_file 可能返回一个 10000 行的大文件，全打印会刷屏。截断显示，但**回传给模型的是完整结果**（不是截断的）。

**注意：console.log 是给人看的，messages.push 是给模型看的。** 两者内容可能不同——给人看的可以截断，给模型看的必须完整。

### 7.8 构造 tool_result

```typescript
toolResults.push({
  type: "tool_result",
  tool_use_id: block.id,
  content: result,
});
```

三个字段：
- `type: "tool_result"`：标识这是工具结果 block
- `tool_use_id: block.id`：关联到哪个工具调用。`block.id` 是模型生成的 tool\_use ID。
- `content: result`：工具执行结果字符串

**tool\_use\_id 必须对上。** 如果工具调用 ID 是 `"toolu_01ABC"`，回传结果时 tool\_use\_id 必须也是 `"toolu_01ABC"`。对不上 API 会报错。

### 7.9 push tool_result 到 messages

```typescript
messages.push({ role: "user", content: toolResults });
```

**关键：role 是 "user"，不是 "assistant"。**

所有 tool\_result 作为一个 user 消息的 content。为什么是 user？下一节专门讲。

push 完后**不 break**，内层循环继续，再调一次 API。模型会看到工具结果，决定下一步。

### 7.10 end_turn 分支

```typescript
} else {
  // stop_reason === "end_turn"，模型说完了
  const text = extractText(response.content);
  if (text) console.log(text);
  break; // 回到外层等待用户输入
}
```

模型说完了：
1. 提取 text block 的文本
2. 打印给用户
3. break 跳出内层循环，回外层等用户下一轮输入

**extractText 做什么？**

```typescript
function extractText(content: Anthropic.ContentBlock[]): string {
  return content
    .filter((b) => b.type === "text")
    .map((b) => (b as Anthropic.TextBlock).text)
    .join("");
}
```

过滤出 text block，提取 text 字段，拼接成字符串。end\_turn 时 content 通常只有一个 text block，但写通用点没坏处。

## 9. tool_result 为什么是 role:"user"

### 9.1 反直觉的事实

这是 tool\_use 协议里最反直觉的一点：**工具结果作为 `role: "user"` 消息回传，不是 `role: "assistant"`**。

```typescript
messages.push({ role: "user", content: toolResults });  // ← user，不是 assistant
```

很多人第一次看到会困惑：工具是模型请求调的，结果不应该算模型说的吗？为什么是 user？

### 9.2 从对话语义理解

想想人类对话的类比：

```
你（user）: 帮我查一下北京天气
我（assistant）: 我查一下天气接口 [调 get_weather("北京")]
[工具执行，返回 "晴，25°C"]
我（assistant）: 北京现在晴，25°C
```

工具结果 "晴，25°C" 是谁"说"的？不是我（assistant），是天气接口说的。在对话里，天气接口是"外部世界"，和"你"（user）一样，都是给 assistant 提供信息的来源。

所以 tool\_result 的角色是 user——它代表"外部世界告诉模型的信息"。模型收到 tool\_result，就像收到用户的回复一样，基于这个信息继续说话。

### 9.3 从 API 规范理解

Anthropic API 要求 messages **交替**：user → assistant → user → assistant → ...

一轮工具调用的 messages 结构是：

```
{ role: "user",      content: "创建 hello.txt" }         // 用户输入
{ role: "assistant", content: [tool_use block] }          // 模型请求工具
{ role: "user",      content: [tool_result block] }       // 工具结果
{ role: "assistant", content: [text block] }              // 模型最终回复
```

如果 tool\_result 是 assistant 角色：

```
{ role: "user",      content: "创建 hello.txt" }
{ role: "assistant", content: [tool_use block] }
{ role: "assistant", content: [tool_result block] }  // ← 连续两个 assistant！
```

这违反了交替规则，API 会报错。

**tool\_result 必须是 user，是为了满足交替约束。**

### 9.4 一个常见误解

有人以为"tool\_result 是 user 意味着用户执行了工具"。不是的。

tool\_result 的 role 是 user，但**内容是 tool\_result block**，不是普通文本。API 能区分这是工具结果而不是用户输入。role 只是为了满足交替约束，语义上 tool\_result 代表"外部世界的反馈"。

你的代码执行工具，构造 tool\_result，以 user 角色塞回 messages。用户没有参与这一步。

## 10. 多工具调用

### 10.1 一次 response 含多个 tool_use block

模型可以在一次 response 里请求**多个工具调用**。response.content 可以有多个 tool\_use block：

```typescript
response.content = [
  { type: "text", text: "我来读这两个文件" },
  { type: "tool_use", id: "toolu_1", name: "read_file",
    input: { path: "a.txt" } },
  { type: "tool_use", id: "toolu_2", name: "read_file",
    input: { path: "b.txt" } }
]
```

模型一次请求读两个文件。这通常发生在任务独立、可以并行的情况下——读 a.txt 和读 b.txt 没有依赖关系，模型一次请求两个。

### 10.2 并行还是串行

**模型请求是并行的**（一次返回多个 tool\_use），但**你的执行可以串行也可以并行**。

本章代码是串行执行（for 循环顺序执行）：

```typescript
for (const block of response.content) {
  if (block.type === "tool_use") {
    const result = executeTool(block.name, block.input);
    toolResults.push({ ... });
  }
}
```

串行够用，因为 read\_file/write\_file 都很快。如果工具有网络请求（比如 fetch\_url），并行执行会快很多。改成并行：

```typescript
const toolUseBlocks = response.content.filter(b => b.type === "tool_use");
const toolResults = await Promise.all(
  toolUseBlocks.map(async block => {
    const result = await executeToolAsync(block.name, block.input);
    return { type: "tool_result", tool_use_id: block.id, content: result };
  })
);
```

**但本章保持串行，因为简单。** 并行要改 executeTool 成 async，引入 Promise.all，对初学者不友好。

### 10.3 代码如何处理多个 block

```typescript
const toolResults: ToolResultBlockParam[] = [];

for (const block of response.content) {
  if (block.type === "tool_use") {
    const result = executeTool(block.name, block.input);
    toolResults.push({
      type: "tool_result",
      tool_use_id: block.id,
      content: result,
    });
  }
}

messages.push({ role: "user", content: toolResults });
```

关键：**所有 tool\_result 放在同一个 user 消息的 content 数组里**。

不是：
```typescript
// 错误！每个 tool_result 单独 push 一条 user 消息
messages.push({ role: "user", content: [toolResult1] });
messages.push({ role: "user", content: [toolResult2] });  // 连续两个 user，违反交替
```

而是：
```typescript
// 正确！所有 tool_result 放一个 user 消息
messages.push({ role: "user", content: [toolResult1, toolResult2] });
```

每个 tool\_result 的 `tool_use_id` 不同，模型能区分哪个结果对应哪个工具调用。

### 10.4 多工具调用的时序示例

用户："读 a.txt 和 b.txt，告诉我哪个更长"

```
第 1 次调 API:
  → response:
      stop_reason = "tool_use"
      content = [
        { text: "我读一下这两个文件" },
        { tool_use, id: "toolu_1", name: "read_file", input: { path: "a.txt" } },
        { tool_use, id: "toolu_2", name: "read_file", input: { path: "b.txt" } }
      ]

执行工具（串行）:
  executeTool("read_file", { path: "a.txt" }) → "aaa" (3 字符)
  executeTool("read_file", { path: "b.txt" }) → "bbbbbbbb" (8 字符)

messages.push({ role: "assistant", content: response.content })
messages.push({
  role: "user",
  content: [
    { type: "tool_result", tool_use_id: "toolu_1", content: "aaa" },
    { type: "tool_result", tool_use_id: "toolu_2", content: "bbbbbbbb" }
  ]
})

第 2 次调 API:
  → response:
      stop_reason = "end_turn"
      content = [{ text: "b.txt 更长（8 字符 vs 3 字符）" }]

输出: "b.txt 更长（8 字符 vs 3 字符）"
```

模型一次请求两个 read\_file，代码串行执行两个，结果一起回传，模型对比后给出答案。两轮 API 调用完成。

## 11. 工具 description 的艺术

### 11.1 description 是模型理解工具的唯一途径

再强调一次：**模型看不到你的工具实现代码**。

模型不知道：
- `read_file` 内部用的是 `fs.readFileSync` 还是 `fetch`
- 文件不存在时是抛异常还是返回错误字符串
- 路径是相对还是绝对
- 返回的是文本还是二进制

模型只知道你 `description` 里写的字。description 是工具的"说明书"，模型照着说明书用。

### 11.2 好的 description 长什么样

```typescript
{
  name: "read_file",
  description: "读取指定路径的文件内容。返回文件的文本内容（UTF-8 编码）。如果文件不存在返回错误信息字符串。",
  input_schema: {
    type: "object",
    properties: {
      path: {
        type: "string",
        description: "要读取的文件路径，支持相对路径和绝对路径"
      }
    },
    required: ["path"]
  }
}
```

好在哪里：
- 说了做什么（读取文件内容）
- 说了返回格式（UTF-8 文本）
- 说了边界情况（文件不存在返回错误字符串，不抛异常）
- 说了参数格式（支持相对和绝对路径）

### 11.3 差的 description 会怎样

```typescript
{
  name: "read_file",
  description: "read file",  // ← 太简略
  input_schema: { ... }
}
```

模型可能：
- 传一个 URL 当 path（以为能读网络文件）
- 传一个二进制路径（以为能读图片）
- 文件不存在时不知道会返回什么，可能误判
- 在该用 read\_file 的地方用了 write\_file（description 没区分清楚）

**差 description 导致模型乱调工具，是 Agent 最常见的 bug 来源。**

### 11.4 参数也要写 description

```typescript
properties: {
  path: {
    type: "string",
    description: "要读取的文件路径（相对路径或绝对路径）"
  }
}
```

参数的 description 告诉模型这个参数是什么格式、什么含义。不写的话模型只能猜。

**反例**：

```typescript
properties: {
  path: { type: "string" }  // ← 没 description
}
```

模型不知道 path 要什么格式。可能传 `"hello.txt"`，可能传 `"/absolute/path"`，可能传 `"file://hello.txt"`。写了 description 就明确了。

### 11.5 真实 Claude Code 的 description 长什么样

真实 Claude Code 的 Read 工具 description（简化版）：

```typescript
{
  name: "Read",
  description: `Reads a file from the local filesystem. You can use this tool to:
- Read text files (UTF-8 encoded)
- Read the first N lines of a large file
- Read files with specific line ranges

The file_path must be an absolute path. Relative paths are not supported.

When to use this tool:
- You need to see the contents of a file
- You need to check if a file exists
- You need to read a specific portion of a large file

When NOT to use this tool:
- You need to search for patterns in files (use Grep instead)
- You need to list files in a directory (use Glob instead)
- You need to read a binary file (images, PDFs)`,
  input_schema: {
    type: "object",
    properties: {
      file_path: {
        type: "string",
        description: "The absolute path to the file to read. Must be a valid path."
      },
      offset: {
        type: "number",
        description: "The line number to start reading from. 1-indexed."
      },
      limit: {
        type: "number",
        description: "The number of lines to read. Defaults to 2000."
      }
    },
    required: ["file_path"]
  }
}
```

注意真实 Claude Code 的 description：
- **很长**（几十行）
- 说了**什么时候用**（When to use）
- 说了**什么时候不用**（When NOT to use，引导模型用别的工具）
- 说了**参数格式**（absolute path，1-indexed）
- 说了**默认值**（limit defaults to 2000）

这就是工具 description 的"艺术"。写得好，模型就像一个训练有素的助手，精准使用每个工具；写得差，模型就像一个没看过说明书的人，乱按按钮。

## 12. 常见陷阱

### 12.1 工具名拼写错误

```typescript
// tools.ts
{ name: "read_file", ... }

// 模型请求
{ name: "readFile", ... }  // ← 驼峰，不是 snake_case
```

如果模型返回的工具名和定义的不一致，executeTool 的 default 分支会返回"未知工具"。

**防范**：
- 工具名用 snake\_case（模型训练数据里常见）
- description 里也用同样的名字
- default 分支返回友好错误，模型看到会调整

实际上模型很少拼错，因为 API 会把 tools 传给模型，模型按 tools 里的 name 用。但你的 executeTool 要能处理未知工具名。

### 12.2 JSON Schema 格式错误

```typescript
// 错误：type 写成 "string" 而不是 "object"
input_schema: {
  type: "string",
  properties: { ... }
}

// 错误：properties 写成 params
input_schema: {
  type: "object",
  params: { ... }  // ← 应该是 properties
}

// 错误：required 写成 "path" 而不是 ["path"]
input_schema: {
  type: "object",
  properties: { path: { type: "string" } },
  required: "path"  // ← 应该是数组
}
```

Schema 格式错误，API 可能报错，或者模型生成的参数不符合预期。

**防范**：用 SDK 的类型（`Tool` 类型），TypeScript 会检查格式。复制粘贴现成的 schema 改。

### 12.3 tool_use_id 关联错误

```typescript
// 错误：tool_use_id 写成固定的字符串
toolResults.push({
  type: "tool_result",
  tool_use_id: "toolu_fixed",  // ← 应该用 block.id
  content: result
});
```

如果 tool\_use\_id 对不上实际的 tool\_use block ID，API 会报错"tool\_use\_id does not match any tool\_use"。

**防范**：永远用 `block.id`，不要手写 ID。

### 12.4 忘记 push assistant 消息

```typescript
// 错误：只 push tool_result，不 push assistant
const response = await client.messages.create({ ... });
// 忘了: messages.push({ role: "assistant", content: response.content });
messages.push({ role: "user", content: toolResults });
```

下次调 API 时，messages 里连续两个 user 消息，API 报错"messages must alternate"。

**防范**：push assistant 消息是固定模式，永远紧跟在 response 后面：

```typescript
const response = await client.messages.create({ ... });
messages.push({ role: "assistant", content: response.content });  // ← 永远这行
if (response.stop_reason === "tool_use") {
  // ... 构造 toolResults
  messages.push({ role: "user", content: toolResults });
}
```

### 12.5 tool_result 用错 role

```typescript
// 错误：role 写成 "assistant"
messages.push({ role: "assistant", content: toolResults });
```

连续两个 assistant 消息，API 报错。或者模型把工具结果当成自己的话，逻辑混乱。

**防范**：tool\_result 永远是 `role: "user"`。背下来。

### 12.6 工具抛异常没捕获

```typescript
// 错误：executeTool 没 try-catch
export function executeTool(name: string, input: any): string {
  switch (name) {
    case "read_file":
      return fs.readFileSync(input.path, "utf-8");  // ← 文件不存在会抛异常
  }
}
```

工具抛异常，内层循环被打断，外层 try-catch 捕获，整个用户请求失败。

**防范**：executeTool 内部 try-catch，把异常转成错误字符串返回。工具**永远返回字符串**，永远不抛异常。

### 12.7 内层循环死循环

模型可能陷入死循环：一直调工具，永不 end\_turn。原因可能是：
- 工具一直返回错误，模型一直重试
- 任务本身无法完成（比如读一个不存在的文件，模型一直尝试）
- 模型 bug（罕见）

本章没有防护。真实 Claude Code 会限制最大工具调用次数。

**防范**：加一个计数器，超过 N 次强制 break：

```typescript
let toolCallCount = 0;
const maxToolCalls = 20;

while (true) {
  const response = await client.messages.create({ ... });
  messages.push({ role: "assistant", content: response.content });

  if (response.stop_reason === "tool_use") {
    toolCallCount++;
    if (toolCallCount > maxToolCalls) {
      console.log("达到最大工具调用次数，强制结束");
      break;
    }
    // ... 执行工具
  } else {
    // ... end_turn
    break;
  }
}
```

这是个重要的生产级防护，练习题里会提到。

|---|------|-------------|
| 权限 | 无，直接执行 | 写操作需用户确认 |

本章 write\_file 直接执行，不问用户。Claude Code 的写操作（Write、Edit、Bash）会先问用户"允许吗？"，用户同意才执行。

这是安全考虑。Agent 能写文件、能执行命令，如果模型被 prompt injection 攻击（用户读的文件里嵌入恶意指令），Agent 可能干坏事。权限确认是最后一道防线。

本章为了简单省略了权限确认。生产级 Agent 必须有。

### 13.3 参数校验

| | 本章 | Claude Code |
|---|------|-------------|
| 校验 | 基本校验（文件存在性） | 严格校验 + 错误提示 |

本章 executeTool 只检查文件存在性。Claude Code 会严格校验参数：路径合法吗、编码支持吗、大小没超限吗。校验失败返回结构化错误，告诉模型怎么改。

### 13.4 工具实现结构

| | 本章 | Claude Code |
|---|------|-------------|
| 结构 | 函数 + switch-case | 类（class），有 validate/checkPermissions/execute |

本章用一个函数 + switch-case 实现所有工具。Claude Code 每个工具是个类，有统一接口：

```typescript
class Tool {
  validate(input): ValidationResult      // 参数校验
  checkPermissions(input): PermissionResult  // 权限检查
  execute(input): Promise<string>        // 执行
}
```

类的好处：每个工具独立，加工具不用改 switch-case，错误处理统一。

本章用 switch-case 是为了简单——74 行 vs 几百行，初学者更容易看懂。

### 13.5 错误处理

| | 本章 | Claude Code |
|---|------|-------------|
| 错误 | try-catch 返回错误文本 | 结构化错误 + 重试逻辑 |

本章工具错误就是字符串："错误: 文件不存在"。Claude Code 的错误是结构化的：错误类型、错误消息、建议修复动作。某些错误（网络超时）会自动重试。

### 13.6 核心循环完全一致

**这是最重要的一点。** 尽管工具数量、权限、校验、错误处理都不同，**核心循环完全一致**：

```typescript
while (true) {
  const response = await client.messages.create({ model, messages, tools });
  messages.push({ role: "assistant", content: response.content });

  if (response.stop_reason === "tool_use") {
    // 执行工具，构造 tool_result
    messages.push({ role: "user", content: toolResults });
    // 继续循环
  } else {
    // end_turn，输出，break
    break;
  }
}
```

Claude Code 的核心循环就是这个结构。区别只在于：
- tools 数组更长（10+ 个工具）
- executeTool 更复杂（类、权限、校验）
- 有最大迭代次数限制
- 有流式输出（streaming）
- 有日志、监控、成本统计

**但骨架一模一样。** 看懂本章的 150 行，你就看懂了 Claude Code 的核心。

### 14.4 思考题

1. **为什么模型不能直接执行工具，必须通过你的代码？**
   提示：安全、权限、审计。

2. **如果工具 description 写"读取文件"，模型会不会用错？**
   提示：缺少路径格式、返回格式、边界情况说明。

3. **内层循环为什么不能写成递归？**
   提示：可以写成递归，但 while 循环更直观、不容易栈溢出。

4. **如果模型一次返回 10 个 tool\_use，你的代码能处理吗？**
   提示：for 循环遍历所有 block，能处理。

5. **tool\_result 的 content 可以不是字符串吗？**
   提示：API 支持 content 是数组（多段文本），但字符串最简单。

6. **为什么 messages 要传完整的？只传最近的几条不行吗？**
   提示：模型需要看到完整历史才能理解上下文。截断会丢失上下文。

7. **如果用户说"读 a.txt"，但 a.txt 不存在，Agent 会怎么表现？**
   提示：read\_file 返回错误字符串，模型看到错误会告诉用户文件不存在。

8. **Claude Code 的权限确认是怎么实现的？**
   提示：executeTool 之前加一步 checkPermissions，返回 false 就不执行，返回错误给模型。

## 15. 下一章预告

现在模型能读写文件了，但还有限制：
- 不能**修改**文件（只能整体覆盖）→ 需要 Edit 工具
- 不能**执行命令**（不能跑 npm、git、python）→ 需要 Bash 工具

- **Bash**：执行 shell 命令（npm install、git status、python script.py）
- **Glob**：按文件名模式搜索（`**/*.ts`）
- **Grep**：按内容搜索（正则表达式）

这四个工具加上现有的 Read/Write，就是 Claude Code 的核心工具集。有了这些，模型就能：
- 找到所有 TypeScript 文件（Glob）
- 搜索某个函数在哪定义（Grep）
- 修改函数实现（Edit）
- 跑测试验证（Bash）

从"能读写"到"能开发"，这就是第三章的主题。

1. **tool\_use 协议三步骤**：定义工具 → 模型请求 → 回传结果，循环执行

**关键代码模式（背下来）：**

```typescript
while (true) {
  const response = await client.messages.create({ model, messages, tools });
  messages.push({ role: "assistant", content: response.content });

  if (response.stop_reason === "tool_use") {
    const toolResults = [];
    for (const block of response.content) {
      if (block.type === "tool_use") {
        const result = executeTool(block.name, block.input);
        toolResults.push({
          type: "tool_result",
          tool_use_id: block.id,
          content: result,
        });
      }
    }
    messages.push({ role: "user", content: toolResults });
    // 继续循环
  } else {
    console.log(extractText(response.content));
    break;
  }
}
```

这 20 行就是 Agent 的灵魂。所有 Agent 系统的核心都是这 20 行的变体。
