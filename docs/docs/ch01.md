## 1. 本章目标

读完这一章，你应该能**清楚地回答**以下三个问题：

1. **Anthropic SDK 怎么调？** —— `client.messages.create()` 这一个调用背后发生了什么。
2. **多轮对话的本质是什么？** —— 一个 `messages` 数组，每次把 user 和 assistant 消息追加进去，再整体发给 API。
3. **Agent Loop 的外层长什么样？** —— `while (true)` 等待用户输入、调 API、输出结果，再回到起点。

**更重要的事**：这一章建立的"心智模型"是后续所有章节的地基。第二章加工具、第三章加流式、第四章加 system prompt、第五章加上下文压缩——所有这些复杂功能，本质上都只是在**操作同一个 `messages` 数组**和**扩展同一个 `while` 循环**。如果这一章没看懂，后面会越看越糊涂；如果看懂了，后面每一步都只是"在已知骨架上加东西"。

本章**不**涉及：工具调用（Ch2）、流式输出（Ch3）、system prompt（Ch4）、上下文压缩（Ch5）、权限确认（Ch6）。这是**故意**的。教学的最小可复现单元（Minimal Reproducible Unit）原则：每次只引入一个新概念。本章的新概念就是"messages 数组 + while 循环"，仅此而已。

## 2. 前置知识

在写代码之前，先讲清楚三个会被反复用到、但很多教程默认你已经懂了的概念。

### 2.1 什么是 SDK

**SDK** = Software Development Kit，软件开发工具包。

你完全可以不用 SDK，直接用 `fetch` 调 Anthropic 的 HTTP API：

```typescript
// 不用 SDK，直接 fetch（伪代码，省略错误处理）
const resp = await fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  headers: {
    "x-api-key": process.env.API_KEY,
    "anthropic-version": "2023-06-01",
    "content-type": "application/json",
  },
  body: JSON.stringify({
    model: "claude-sonnet-4-20250514",
    max_tokens: 1024,
    messages: [{ role: "user", content: "你好" }],
  }),
});
const data = await resp.json();
```

这样写**完全能跑**。那为什么还要 SDK？因为 SDK 帮你做了三件烦事：

1. **拼请求**：自动加正确的 header（`x-api-key`、`anthropic-version`、`content-type`），自动序列化 body。
2. **解析响应**：把 JSON 反序列化成 TypeScript 类型安全的对象，IDE 有自动补全。
3. **错误处理**：HTTP 429 限流自动重试、超时自动断开、错误码翻译成可读的 Error 对象。

**一句话**：SDK 就是"帮你少写 30 行样板代码的封装层"。本章用的 `@anthropic-ai/sdk` 是 Anthropic 官方维护的 npm 包，版本在 `package.json` 里锁定为 `^0.39.0`。

> **教学向提醒**：理解 SDK 在做什么很重要，但**不要**为了"理解底层"就拒绝用 SDK。SDK 不是黑魔法，它只是 HTTP 客户端的语法糖。等你写完这一章，可以去看 SDK 的源码（`node_modules/@anthropic-ai/sdk/src/`），你会发现它本质上就是上面那段 `fetch` 加了一堆 `try/catch` 和类型定义。

### 2.2 什么是 messages 数组

`messages` 是一个**数组**，每个元素是一条**消息**，每条消息有两个字段：

```typescript
{
  role: "user" | "assistant",   // 谁说的
  content: string | ContentBlock[]  // 说了什么
}
```

- `role: "user"` —— 用户说的话
- `role: "assistant"` —— 模型回的话

一个两轮对话的 `messages` 数组长这样：

```typescript
const messages = [
  { role: "user",      content: "你好" },           // 第 1 轮：用户
  { role: "assistant", content: "你好！有什么可以帮你的？" },  // 第 1 轮：模型
  { role: "user",      content: "1+1 等于几？" },     // 第 2 轮：用户
  { role: "assistant", content: "1+1 等于 2。" },     // 第 2 轮：模型
];
```

**关键点**：这个数组是**有序的**、**完整的**、**追加只增不删的**（在本章里）。它就是对话的"完整历史记录"。

> 第二章你会看到 `content` 不一定是字符串，也可能是 `ContentBlock[]`（包含文本块、工具调用块、工具结果块）。本章为了简化，user 的 content 是字符串，assistant 的 content 是 SDK 返回的 `response.content`（一个数组，但里面只有文本块）。

### 2.3 什么是"无状态"

**无状态**（stateless）是理解 LLM API 最重要的一个词。

对比两种服务：

| | 有状态服务 | 无状态服务 |
|---|---|---|
| 例子 | 数据库连接、WebSocket | HTTP、LLM API |
| 服务端记不记得你上一次干了啥 | 记得 | **不记得** |
| 每次请求要带什么 | 只带"这次想干什么" | 带"全部历史 + 这次想干什么" |

**LLM API 是无状态的**。这意味着：

- 你第一次发 `"你好"`，模型回 `"你好！"`。
- 你第二次发 `"刚才我说了什么？"`，**模型不知道你刚才说了什么**。它会瞎猜。
- 你必须在第二次请求里**把第一次的对话也带上**，模型才能"记得"。

```
❌ 错误的心智模型：
   第 1 次请求 → 模型记住了"你好"
   第 2 次请求 "刚才我说了什么" → 模型从记忆里取出"你好" → 回答"你说了你好"

✅ 正确的心智模型：
   第 1 次请求 [user: "你好"] → 模型回 "你好！" → 服务端立刻忘掉这次请求
   第 2 次请求 [user: "你好", assistant: "你好！", user: "刚才我说了什么"]
   → 模型看到完整历史 → 回答"你说了你好"
```

**"多轮对话"是个假象**。服务端从来没有"记住"任何对话。所谓多轮对话，**100% 靠客户端每次把完整历史发上去**。这是本章最核心的一句话，请反复读三遍。

> **为什么 LLM API 设计成无状态？** 因为无状态服务可以无限水平扩展——每个请求独立处理，不需要在服务器之间同步会话状态。Anthropic 每秒处理几十万请求，靠的就是这个。如果是有状态的，服务器要存几千万个进行中的对话，内存撑不住，也加不了机器。

## 3. 多轮对话的本质

### 3.1 一个反直觉的事实

很多人第一次写 LLM 应用时会这样想：

> "我先调一次 API 建立会话，拿到一个 `session_id`，之后用这个 id 继续对话。"

**完全不是这样**。Anthropic 的 API **没有** `session_id`，**没有** `create_session()`，**没有** `continue_session()`。每次都是全新的 `client.messages.create()` 调用，唯一的"会话"就是你自己维护的 `messages` 数组。

```typescript
// ❌ 错误想象：API 有会话
const session = await client.createSession();
await session.send("你好");
await session.send("刚才我说了什么");  // 模型"记得"，因为 session 在

// ✅ 实际情况：API 无会话，全靠 messages 数组
const messages = [];
messages.push({ role: "user", content: "你好" });
await client.messages.create({ model, messages });  // 第 1 次
messages.push({ role: "user", content: "刚才我说了什么" });
await client.messages.create({ model, messages });  // 第 2 次，messages 里已经有第 1 次的历史
```

### 3.2 messages 数组是唯一状态

看本章代码，整个程序里**唯一跨循环迭代保持的变量**就是 `messages`：

```typescript
const messages: Anthropic.MessageParam[] = [];  // ← 整个程序的"记忆"

while (true) {
  const userInput = await prompt("\n> ");
  messages.push({ role: "user", content: userInput });      // ← 往记忆里加
  const response = await client.messages.create({ messages }); // ← 用记忆
  messages.push({ role: "assistant", content: response.content }); // ← 往记忆里加
}
```

没有数据库，没有文件，没有 Redis，没有任何持久化。**整个对话的全部状态，就在内存里这一个数组里。** 关掉终端，对话就没了。

这是教学上的故意简化，但也是一个**深刻的事实**：Claude Code 真实的产品逻辑，本质上也是这样。它有更长的 system prompt、有工具调用、有上下文压缩，但"对话状态"的核心载体，**仍然是一个 messages 数组**，只不过那个数组会被压缩、会被序列化到磁盘、会在 token 超限时被截断。但骨架和本章一模一样。

### 3.3 为什么必须带完整历史

因为模型是**自回归**（autoregressive）的：它根据前面的 token 预测下一个 token。你给它看的前面 token 越多，它"知道"的上下文就越多。

```
请求 1：messages = [user: "我叫小明"]
模型输出：                    "你好，小明！"

请求 2：messages = [user: "我叫小明", assistant: "你好，小明！", user: "我叫什么？"]
模型看到前面有"我叫小明"，输出： "你叫小明。"

请求 2'（错误）：messages = [user: "我叫什么？"]   ← 没带历史
模型只看到"我叫什么？"，输出：    "我不知道你叫什么。"
```

**带完整历史的代价**：每次请求的 token 数会越来越大。第 1 轮 100 token，第 2 轮 200，第 10 轮可能 5000。费用线性增长，延迟也线性增长。这就是为什么后面要有"上下文压缩"（Ch5）——但那是优化，不是骨架。

### 3.4 Agent Loop 的两层结构

Claude Code 的循环其实有**两层**：

```
外层循环（用户交互）:
  while True:
    user_input = 等待用户输入
    messages.append(user_input)
    
    内层循环（工具调用）:        ← Ch2 才加，本章没有
      response = 调用 LLM
      if 模型想调工具:
        执行工具，结果加入 messages
        继续循环                ← 关键：不回外层，继续调 LLM
      else:
        输出文本
        break  ← 回到外层等用户
```

**本章只有外层循环**。模型说一句话，就直接 `break` 回外层等下一个用户输入。没有"模型想调工具"这个分支。

**内层循环是 Ch2 的核心**，那是从"聊天机器人"变成"Agent"的关键。但请注意：内层循环不是另写一个 `while`，而是**同一个 `while` 里加一个 `if` 分支**。骨架还是本章这个骨架。这就是为什么本章必须先看懂。

## 4. 完整代码

下面是 `lessons/ch01-minimal/main.ts` 的完整 61 行代码。先通读一遍，下一节逐行讲解。

```typescript
import Anthropic from "@anthropic-ai/sdk";
import * as readline from "readline";
import * as dotenv from "dotenv";

dotenv.config();

const client = new Anthropic({
  apiKey: process.env.API_KEY,
  baseURL: process.env.BASE_URL || undefined,
});

const model = process.env.MODEL || "claude-sonnet-4-20250514";
const maxTokens = parseInt(process.env.MAX_TOKENS || "1024");

const messages: Anthropic.MessageParam[] = [];

const rl = readline.createInterface({
  input: process.stdin,
  output: process.stdout,
});

function prompt(query: string): Promise<string> {
  return new Promise((resolve) => rl.question(query, resolve));
}

async function main() {
  console.log("=== Mini Claude Code - Ch1 (minimal) ===");
  console.log(`模型: ${model}`);
  console.log('输入 "exit" 退出\n');

  while (true) {
    const userInput = await prompt("\n> ");
    if (userInput.trim() === "exit") break;
    if (!userInput.trim()) continue;

    messages.push({ role: "user", content: userInput });

    try {
      const response = await client.messages.create({
        model,
        max_tokens: maxTokens,
        messages,
      });

      const text = (response.content as Anthropic.TextBlock[])
        .filter((b) => b.type === "text")
        .map((b) => b.text)
        .join("");

      messages.push({ role: "assistant", content: response.content });
      console.log(text);
    } catch (err: any) {
      console.error(`[错误] ${err.message}`);
    }
  }

  console.log("再见！");
  rl.close();
}

main();
```

## 5. 代码逐行讲解

### 5.1 import 三行

```typescript
import Anthropic from "@anthropic-ai/sdk";   // ①
import * as readline from "readline";          // ②
import * as dotenv from "dotenv";              // ③
```

**① `Anthropic`**：从 `@anthropic-ai/sdk` 包默认导出的类。`new Anthropic({...})` 会创建一个客户端实例，里面封装了 HTTP 调用、重试、类型定义。这个包在 `package.json` 的 `dependencies` 里，`npm install` 时会装到 `node_modules/`。

**② `readline`**：Node.js **内置**模块，不需要 `npm install`。它提供命令行交互能力——从 `stdin` 读一行用户输入，写到 `stdout`。`* as` 是命名空间导入，用 `readline.createInterface()` 调用。

**③ `dotenv`**：第三方包，把 `.env` 文件里的 `KEY=VALUE` 加载到 `process.env` 里。后面会详细讲。

> **为什么 `Anthropic` 是默认导入，`readline` 和 `dotenv` 是命名空间导入？** 这是包作者的决定的导出方式，不是我们能选的。`@anthropic-ai/sdk` 用 `export default class Anthropic`，所以 `import Anthropic from`。`readline` 用 CommonJS 的 `module.exports`，所以 `import * as readline`。实际写代码时照着 IDE 自动补全来就行。

### 5.2 dotenv.config()

```typescript
dotenv.config();
```

这一行执行后，`process.env` 里就有了 `.env` 文件中所有的变量。例如 `.env` 里有 `API_KEY=sk-ant-xxx`，之后就能用 `process.env.API_KEY` 拿到 `"sk-ant-xxx"`。

**注意位置**：必须在 `new Anthropic({ apiKey: process.env.API_KEY })` **之前**调用，否则 `process.env.API_KEY` 还是 `undefined`。

**这一行没有 `await`**：`dotenv.config()` 是**同步**的，返回一个对象 `{ parsed: {...}, error: null }`，但本章代码忽略返回值。它读 `.env` 文件、按行解析、写入 `process.env`，全部同步完成。

### 5.3 Anthropic 客户端初始化

```typescript
const client = new Anthropic({
  apiKey: process.env.API_KEY,
  baseURL: process.env.BASE_URL || undefined,
});
```

**`new Anthropic({...})`** 创建一个客户端实例。这个实例本身不发起任何 HTTP 请求，只是把配置存起来。真正的请求发生在后面 `client.messages.create()` 调用时。

**`apiKey`**：Anthropic 用来认证的密钥。如果没填或填错，后面调用会报 401 错误。SDK 会把这个 key 自动放到 HTTP header 的 `x-api-key` 字段里。

**`baseURL`**：API 的基础地址。默认是 `https://api.anthropic.com`。如果填了 `https://api.deepseek.com/anthropic`，SDK 就会去 DeepSeek 的服务器（DeepSeek 提供了 Anthropic 兼容的 API 接口）。这是本章支持"切换后端"的原理——**同一份代码，改一个环境变量就能换模型供应商**。

**`process.env.BASE_URL || undefined`** 这个写法很关键：
- 如果 `.env` 里 `BASE_URL=`（空字符串），`"" || undefined` 等于 `undefined`，SDK 用默认值。
- 如果 `.env` 里 `BASE_URL=https://api.deepseek.com/anthropic`，取这个值。

为什么不能直接 `baseURL: process.env.BASE_URL`？因为 SDK 收到空字符串 `""` 会真的把 baseURL 设成空字符串，导致请求发到 `""` + `/v1/messages` = `/v1/messages` 这种错误地址。`|| undefined` 是把"空字符串"翻译成"没设置"。

### 5.4 model 与 maxTokens 常量

```typescript
const model = process.env.MODEL || "claude-sonnet-4-20250514";
const maxTokens = parseInt(process.env.MAX_TOKENS || "1024");
```

**`model`**：模型名。默认 `claude-sonnet-4-20250514`。可以通过 `.env` 的 `MODEL=` 切换。模型名是字符串字面量，写错会报 404。

**`maxTokens`**：模型最多生成多少 token。**这是必填参数**，不填 SDK 直接报错。`parseInt` 把字符串 `"1024"` 转成数字 `1024`。

> **token 是什么？** 粗略理解：1 个英文单词 ≈ 1-2 token，1 个中文字 ≈ 1-2 token。`max_tokens: 1024` 意味着模型最多输出大约 500-1000 字。超过这个数，模型会被强制截断，`stop_reason` 会变成 `"max_tokens"`（后面讲）。

### 5.5 messages 数组声明

```typescript
const messages: Anthropic.MessageParam[] = [];
```

**这一行是整个程序的核心**。

- `Anthropic.MessageParam[]` 是 TypeScript 类型，表示"一个元素类型为 `MessageParam` 的数组"。`MessageParam` 是 SDK 定义的类型，等价于 `{ role: "user" | "assistant"; content: string | ContentBlock[] }`。
- 初始为空数组 `[]`，因为对话还没开始。
- 这个 `messages` 变量是**模块级**的（不在 `main()` 里），所以它在整个进程生命周期内都存在。每次 `while` 循环迭代都往里 push，**永远不会被重置**。

**类型注解有什么用？** 让 IDE 知道 `messages.push(...)` 时应该检查什么。如果你写 `messages.push({ role: "system", content: "..." })`，IDE 会报错，因为 `MessageParam` 的 `role` 不允许 `"system"`（system prompt 在 Anthropic API 里是单独的字段，不在 messages 数组里）。

### 5.6 readline 与 prompt 函数

```typescript
const rl = readline.createInterface({
  input: process.stdin,
  output: process.stdout,
});

function prompt(query: string): Promise<string> {
  return new Promise((resolve) => rl.question(query, resolve));
}
```

**`readline.createInterface`** 创建一个交互接口，绑定到标准输入输出。之后 `rl.question("> ", callback)` 会在终端打印 `"> "`，等用户敲回车，把输入行传给 `callback`。

**`prompt` 函数**：把 `rl.question` 的回调风格包装成 `async/await` 风格。`rl.question` 是 Node.js 老式回调 API：

```typescript
// 原始回调风格
rl.question("> ", (answer) => {
  console.log("你输入了", answer);
});

// 包装成 Promise 风格
const answer = await prompt("> ");
console.log("你输入了", answer);
```

**为什么要包装？** 因为我们在 `while` 循环里要 `await` 用户输入。直接用回调会让循环逻辑变成回调地狱。包装成 Promise 后就能用同步风格的 `await` 写。

**`new Promise((resolve) => ...)`**：创建一个 Promise，把 `resolve` 函数作为回调传给 `rl.question`。用户敲回车 → `rl.question` 调用 `resolve(输入行)` → Promise 完成 → `await` 返回输入行。

### 5.7 main 函数与欢迎语

```typescript
async function main() {
  console.log("=== Mini Claude Code - Ch1 (minimal) ===");
  console.log(`模型: ${model}`);
  console.log('输入 "exit" 退出\n');
```

**为什么包在 `main()` 里？** 顶层 `await` 在 CommonJS 里不支持，要把异步代码包进一个 `async function` 里。文件最后 `main();` 启动它。

**欢迎语**：打印程序名、当前模型、退出指令。教学向，让用户知道程序在跑、用的什么模型、怎么退出。

### 5.8 while 循环：外层骨架

```typescript
  while (true) {
    const userInput = await prompt("\n> ");
    if (userInput.trim() === "exit") break;
    if (!userInput.trim()) continue;
```

**`while (true)`**：无限循环。这是 Agent Loop 的外层。每次迭代 = 一轮用户交互。

**`await prompt("\n> ")`**：在终端打印 `\n> `（换行 + 提示符），等用户输入一行，敲回车后 `userInput` 拿到这行字符串。`await` 让程序在这里**阻塞**，直到用户敲回车。

**`if (userInput.trim() === "exit") break;`**：输入 `exit` 退出循环。`.trim()` 去掉首尾空格，所以 `"  exit  "` 也能退出。

**`if (!userInput.trim()) continue;`**：空输入（直接敲回车）跳过本轮，不发给 API。避免给模型发空消息。

### 5.9 messages.push(user)

```typescript
    messages.push({ role: "user", content: userInput });
```

**这一行是多轮对话的关键**。把用户输入追加到 `messages` 数组。注意：

- `role: "user"` —— 标记这是用户说的
- `content: userInput` —— 用户输入的字符串
- **push 而非赋值** —— 数组只增不删，历史完整保留

push 之后，`messages` 长这样：

```typescript
[
  // ...之前的所有历史
  { role: "user", content: "本次用户输入" }
]
```

### 5.10 client.messages.create()

```typescript
    try {
      const response = await client.messages.create({
        model,
        max_tokens: maxTokens,
        messages,
      });
```

**这是真正调 API 的地方**。`client.messages.create()` 发起一个 HTTP POST 请求到 `{baseURL}/v1/messages`，body 是：

```json
{
  "model": "claude-sonnet-4-20250514",
  "max_tokens": 1024,
  "messages": [
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "..." },
    { "role": "user", "content": "本次输入" }
  ]
}
```

**`await`**：HTTP 请求是异步的，模型生成也要时间（通常 0.5-5 秒）。`await` 让程序等响应回来再继续。

**`messages` 是引用传递**：SDK 内部会 `JSON.stringify(messages)`，序列化时拿到的是当前完整数组。**不要**在请求未完成时修改 `messages`，否则会出竞态。本章是单线程顺序执行，不会有这个问题。

**响应结构**：`response` 是一个对象，大致长这样：

```typescript
{
  id: "msg_abc123",
  type: "message",
  role: "assistant",
  content: [
    { type: "text", text: "模型生成的文字" }
  ],
  model: "claude-sonnet-4-20250514",
  stop_reason: "end_turn",       // ← 第 8 节详讲
  usage: { input_tokens: 50, output_tokens: 20 }
}
```

注意 `content` 是**数组**，不是字符串。因为模型可能输出多种类型的块（文本块、工具调用块）。本章只有文本块，但结构上仍然是数组。

### 5.11 提取文本

```typescript
      const text = (response.content as Anthropic.TextBlock[])
        .filter((b) => b.type === "text")
        .map((b) => b.text)
        .join("");
```

因为 `response.content` 是数组，且可能包含非文本块（Ch2 会有工具调用块），所以要**过滤 + 提取 + 拼接**：

1. `.filter((b) => b.type === "text")` —— 只留文本块
2. `.map((b) => b.text)` —— 取出 `.text` 字段
3. `.join("")` —— 拼成单个字符串

**`as Anthropic.TextBlock[]`**：TypeScript 类型断言。SDK 的类型定义里 `content` 是联合类型 `Array<TextBlock | ToolUseBlock | ...>`，断言成 `TextBlock[]` 后 `.filter` 里访问 `b.text` 不会报错。这是教学简化，生产代码应该用类型守卫 `if (b.type === "text")` 而非断言。

### 5.12 messages.push(assistant)

```typescript
      messages.push({ role: "assistant", content: response.content });
```

**注意**：push 的是 `response.content`（原始数组），**不是** `text`（拼接后的字符串）。

为什么？因为 `content` 是 SDK 定义的标准格式，下次请求时 SDK 能正确序列化。如果 push `text` 字符串，下次请求虽然也能跑（API 接受字符串形式），但**Ch2 加工具调用后**，assistant 消息里可能既有文本块又有工具调用块，必须用数组形式才能完整保留。本章养成好习惯，push 原始 `content`。

push 之后，`messages` 长这样：

```typescript
[
  // ...之前的历史
  { role: "user", content: "本次用户输入" },
  { role: "assistant", content: [{ type: "text", text: "模型回复" }] }
]
```

下一轮循环时，这个完整历史会被发给 API。

### 5.13 try/catch 错误处理

```typescript
    } catch (err: any) {
      console.error(`[错误] ${err.message}`);
    }
```

**`try/catch`**：捕获 `await client.messages.create()` 抛出的异常。常见异常：

| 错误 | 原因 | 处理 |
|------|------|------|
| 401 Unauthorized | API Key 错或过期 | 检查 `.env` |
| 429 Rate Limit | 调用太频繁 | 等几秒重试 |
| 400 Bad Request | messages 格式错 | 检查 push 的内容 |
| 网络错误 | 断网/代理问题 | 检查网络 |

**`err: any`**：教学简化，实际 SDK 抛的是 `APIError` 子类，有 `status`、`error`、`headers` 等字段。生产代码应该 `if (err instanceof Anthropic.APIError)` 分支处理。

**`console.error` 而非 `throw`**：打印错误后**继续循环**，让用户能再试一次。如果 `throw`，进程会崩，对话全丢。这是 CLI 程序的常见模式：错误不致命就别崩。

**注意 try 的范围**：只包了 `create()` 和后续处理，**没包** `prompt()`。因为 `prompt` 出错（用户 Ctrl+C）应该让程序退出，不是"再试一次"。

### 5.14 main() 启动

```typescript
  console.log("再见！");
  rl.close();
}

main();
```

**`console.log("再见！")`**：循环 `break` 后打印告别语。

**`rl.close()`**：关闭 readline 接口，释放 `stdin` 占用。如果不调，进程不会退出（因为 `stdin` 还开着）。Node.js 会在所有事件循环任务空了后退出，`rl.close()` 让 `stdin` 不再保持事件循环。

**`main()`**：在文件最外层调用，启动整个程序。因为 `main` 是 `async function`，调用它返回一个 Promise，但这里没 `await`——顶层没法 `await`（除非用 ESM top-level await，但教学向保持简单）。

## 6. 为什么用 readline 而非 inquirer

Node.js 生态里有更"高级"的命令行交互库：

- **inquirer** / **prompts** / **enquirer**：支持选择列表、多选、密码输入、自动补全等花式交互。
- **@inquirer/prompts**：inquirer 的新版，模块化设计。

它们都很好用，但本章**故意**用最底层的 `readline`。原因：

### 6.1 教学向：理解底层

`readline` 是 Node.js **内置**模块，零依赖。它的 API 暴露了"命令行交互的本质"：

```
1. 监听 stdin 的 'line' 事件
2. 用户敲回车 → 触发事件 → 拿到一行输入
```

用 `readline` 你能看清"等待用户输入"这件事到底在做什么。用 inquirer 你只能看到 `const answer = await input({ message: ">" })`，背后发生了什么全是黑盒。

### 6.2 零依赖原则

每多一个依赖就多一个：

- 安装时间（`npm install` 慢一点）
- 安全风险（供应链攻击面）
- 维护负担（库废弃了你就得换）

本章目标是"最小可对话 CLI"，引入 inquirer 违背"最小"原则。`readline` 是 Node.js 自带的，不增加任何依赖。

### 6.3 Claude Code 真实选择

真实的 Claude Code 用的是更底层的 `ink`（React for CLI）+ 自定义输入处理。但**外层骨架仍然是 while 循环 + 等待输入**，和本章一样。学会 `readline` 版本后，看 ink 版本会容易得多——只是 UI 层换了，循环骨架没变。

### 6.4 什么时候该换 inquirer

当你要做这些事时，readline 就不够用了：

- 多选列表（让用户选几个文件）
- 是/否确认（带默认值）
- 密码输入（输入时不显示）
- 自动补全

Claude Code 在工具权限确认时就需要 yes/no，那时候再升级交互层。本章不需要，所以用最简的。

## 7. 环境变量配置原理

### 7.1 dotenv 做了什么

`.env` 文件长这样：

```bash
API_KEY=sk-ant-xxx
BASE_URL=
MODEL=claude-sonnet-4-20250514
MAX_TOKENS=1024
```

`dotenv.config()` 做的事非常简单，伪代码：

```typescript
function config() {
  const content = fs.readFileSync(".env", "utf-8");  // 读文件
  for (const line of content.split("\n")) {           // 逐行
    if (line.startsWith("#")) continue;               // 跳过注释
    if (!line.includes("=")) continue;                // 跳过空行
    const [key, ...rest] = line.split("=");
    const value = rest.join("=").trim();              // 值可能含 =
    process.env[key.trim()] = value;                  // 写入 process.env
  }
}
```

就这么多。读文件、按行解析、写入 `process.env`。**没有**网络请求、**没有**加密、**没有**校验。

**为什么用 `.env` 而不是直接 `export API_KEY=xxx`？**

- 跨平台：Windows 没有 `export`，用 `.env` 文件所有系统一致。
- 持久化：终端关了再开，环境变量没了，但 `.env` 文件还在。
- 团队协作：`.env.example` 提交到 git，每个人复制一份填自己的 key。
- 安全：`.env` 加进 `.gitignore`，不会误提交密钥。

### 7.2 baseURL 切换原理

SDK 内部发起请求的代码大致是：

```typescript
async function create(params) {
  const url = this.baseURL + "/v1/messages";  // 拼接 URL
  return fetch(url, {
    method: "POST",
    headers: { "x-api-key": this.apiKey, ... },
    body: JSON.stringify(params),
  });
}
```

`this.baseURL` 就是 `new Anthropic({ baseURL })` 时传的值。所以：

- `baseURL = undefined` → SDK 用默认 `https://api.anthropic.com` → 请求发到 `https://api.anthropic.com/v1/messages`
- `baseURL = "https://api.deepseek.com/anthropic"` → 请求发到 `https://api.deepseek.com/anthropic/v1/messages`

DeepSeek 提供了一个 **Anthropic 兼容**的 API 端点，路径和参数格式跟 Anthropic 一模一样，只是域名不同。所以同一份代码，改一个环境变量就能切换供应商。这是"供应商中立的 API 设计"的一个简单例子。

> **教学提醒**：不是所有模型供应商都提供 Anthropic 兼容端点。OpenAI、Google、阿里通义、智谱 GLM 都有自己的 API 格式，要换就得改代码。本章能切 DeepSeek 是因为 DeepSeek 主动做了兼容层。

### 7.3 为什么用环境变量而非硬编码

```typescript
// ❌ 硬编码
const client = new Anthropic({ apiKey: "sk-ant-xxx" });

// ✅ 环境变量
const client = new Anthropic({ apiKey: process.env.API_KEY });
```

硬编码的问题：

1. **安全**：API Key 提交到 git 就泄露了。GitHub 有爬虫专门扫公开仓库里的 `sk-ant-` 开头字符串，扫到立刻被盗用。
2. **灵活**：开发用测试 key，生产用正式 key，硬编码要改代码才能切。
3. **协作**：每个人的 key 不同，硬编码没法多人协作。

环境变量是 12-Factor App 的最佳实践之一，**所有**生产级应用都这么做。

## 8. stop_reason 的含义

每次 API 响应里有个 `stop_reason` 字段，告诉客户端"模型为什么停了"。本章代码没显式读它，但理解它对 Ch2 至关重要。

`stop_reason` 有四个可能的值：

| 值 | 含义 | 本章会发生吗 |
|----|------|--------------|
| `"end_turn"` | 模型自然说完话了 | ✅ 几乎总是这个 |
| `"max_tokens"` | 被 `max_tokens` 截断 | 可能，如果输出太长 |
| `"stop_sequence"` | 遇到了自定义停止序列 | 不会，本章没设 |
| `"tool_use"` | 模型想调工具，停下来等你执行 | **不会，本章没工具** |

**本章**：`stop_reason` 几乎总是 `"end_turn"`。模型说完话就停，客户端把响应加进 `messages`，回外层等下一个用户输入。

**Ch2 之后**：`stop_reason` 可能是 `"tool_use"`。这时模型**没说完话**，它输出的是"我想调 read_file 工具，参数是 {path: 'foo.txt'}"。客户端要：

1. 把模型的工具调用请求加进 `messages`
2. 执行工具，拿到结果
3. 把结果加进 `messages`
4. **再次调 `client.messages.create()`**，让模型继续

这就是内层 agentic loop 的来源——`stop_reason === "tool_use"` 时**不回外层**，继续调 LLM。

**本章为什么没读 stop_reason？** 因为没有工具，模型只可能 `end_turn` 或 `max_tokens`，两种情况都是"输出文本，回外层等用户"。读不读都一样。Ch2 必须读，因为要分支。

> **教学铺垫**：现在记住一句话——**`stop_reason` 决定循环往哪走**。`end_turn` 回外层，`tool_use` 留内层。这是 Agent Loop 的核心控制流。

## 9. 完整运行流程时序图

下面是一次完整运行的时间线，从启动到两轮对话到退出：

```
时间 →

[启动]
  │
  ├─ dotenv.config()                    读 .env，写入 process.env
  ├─ new Anthropic({apiKey, baseURL})   创建客户端（不发请求）
  ├─ messages = []                      初始化空数组
  ├─ readline.createInterface(...)      绑定 stdin/stdout
  ├─ main() 进入
  ├─ console.log(欢迎语)
  │
  ├─ while (true) ──────────────────────────────────────┐
  │                                                     │
  │  [第 1 轮]                                          │
  │   ├─ await prompt("\n> ")          阻塞等用户输入   │
  │   │   └─ 用户输入 "你好" + 回车                     │
  │   ├─ userInput = "你好"                              │
  │   ├─ messages.push({role:"user", content:"你好"})   │
  │   │   messages = [ {user:"你好"} ]                  │
  │   ├─ client.messages.create({model, messages})      │
  │   │   └─ HTTP POST → Anthropic                     │
  │   │       { model, max_tokens,                     │
  │   │         messages: [{user:"你好"}] }            │
  │   │   ← 响应: { content: [{text:"你好！"}],        │
  │   │              stop_reason: "end_turn" }          │
  │   ├─ text = "你好！"                                 │
  │   ├─ messages.push({role:"assistant", content:[...]})│
  │   │   messages = [ {user:"你好"},                  │
  │   │                 {assistant:"你好！"} ]          │
  │   └─ console.log("你好！")         终端显示          │
  │                                                     │
  │  [第 2 轮]                                          │
  │   ├─ await prompt("\n> ")                           │
  │   │   └─ 用户输入 "刚才我说了什么" + 回车            │
  │   ├─ messages.push({role:"user", content:"刚才..."})│
  │   │   messages = [ {user:"你好"},                  │
  │   │                 {assistant:"你好！"},           │
  │   │                 {user:"刚才我说了什么"} ]       │
  │   ├─ client.messages.create({model, messages})      │
  │   │   └─ HTTP POST → Anthropic                     │
  │   │       messages 里带完整 3 条历史                │
  │   │   ← 响应: "你说了你好"                          │
  │   ├─ messages.push({role:"assistant", ...})         │
  │   └─ console.log("你说了你好")                      │
  │                                                     │
  │  [退出]                                             │
  │   ├─ await prompt("\n> ")                           │
  │   │   └─ 用户输入 "exit" + 回车                     │
  │   ├─ break                                          │
  │   └─ 跳出 while ────────────────────────────────────┘
  │
  ├─ console.log("再见！")
  ├─ rl.close()
  └─ 进程退出
```

**关键观察**：

1. **每次请求都带完整 messages**：第 2 轮的 HTTP 请求 body 里有 3 条消息（1 个 user + 1 个 assistant + 1 个 user），不是只带第 2 轮的输入。
2. **messages 只增不减**：从 `[]` 长到 4 条（2 轮 × 2 条），从不删除。
3. **客户端是单线程顺序执行**：`await` 让每一步都等上一步完成，没有并发。这是教学简化，生产代码可能并发处理多个用户，但骨架一样。

## 10. 常见陷阱

按踩坑频率从高到低排：

### 10.1 API Key 忘填或填错

**症状**：`[错误] 401 Unauthorized` 或 `[错误] Authentication failed`。

**排查**：

```bash
# 1. 检查 .env 文件存在
ls .env

# 2. 检查 .env 内容（注意别把 key 提交到 git）
cat .env
# 应该有：API_KEY=sk-ant-xxx（不是空的）

# 3. 检查 .env 在 .gitignore 里
grep ".env" .gitignore
```

**常见原因**：

- 没复制 `.env.example` 到 `.env`，直接编辑了 example 文件（dotenv 默认读 `.env`，不读 `.env.example`）。
- `API_KEY=` 后面有空格，dotenv 把空格也算进值里。
- 用了 DeepSeek 的 key 但 `BASE_URL` 没切，或反过来。

### 10.2 messages 格式错误

**症状**：`[错误] 400 Bad Request` + `messages: expected at least 1 message`。

**原因**：

- `messages` 是空数组就调 `create()`。本章代码 `push` 在 `create` 之前，不会出这个错，但改代码时容易把顺序弄反。
- `role` 拼错，如 `"User"`（大写 U）。API 严格要求小写。
- `content` 是 `null` 或 `undefined`。空字符串 `""` 可以，但 `null` 不行。
- 连续两条 `role: "user"` 没隔 `assistant`。API 要求 user/assistant 交替（第一条必须是 user）。

### 10.3 async/await 理解不到位

**症状 1**：`Promise { <pending> }` 打印出来，而不是实际值。

```typescript
// ❌ 忘了 await
const userInput = prompt("\n> ");  // 这是 Promise，不是字符串
console.log(userInput);            // 打印 Promise { <pending> }

// ✅
const userInput = await prompt("\n> ");
```

**症状 2**：`SyntaxError: await is only valid in async functions`。

```typescript
// ❌ 在非 async 函数里用 await
function foo() {
  const x = await prompt("> ");  // 报错
}

// ✅
async function foo() {
  const x = await prompt("> ");
}
```

**症状 3**：`Uncaught Promise rejection`，进程崩了。

```typescript
// ❌ async 函数里 throw 没 catch
async function main() {
  throw new Error("oops");  // 这个错误没人接，进程崩
}
main();

// ✅ 要么 try/catch，要么 main().catch(...)
main().catch(console.error);
```

本章代码用 `try/catch` 包了 `create()`，所以 API 错误不会崩进程。但 `main()` 本身的错误（如 `dotenv.config()` 失败）没接，会崩。教学简化，生产代码应该加 `main().catch(...)`。

### 10.4 max_tokens 太小

**症状**：模型话说到一半被截断，`stop_reason: "max_tokens"`。

**原因**：本章默认 `MAX_TOKENS=1024`，约 500-1000 字。让模型写长文章会被截断。

**解决**：改 `.env` 里 `MAX_TOKENS=4096` 或更大。但注意：越大越贵越慢。

### 10.5 网络代理问题

**症状**：`[错误] fetch failed` 或超时。

**原因**：Anthropic API 在国外，国内访问可能需要代理。SDK 默认不走代理。

**解决**：设环境变量 `HTTPS_PROXY=http://127.0.0.1:7890`（或你代理的端口），SDK 底层的 fetch 会读这个变量。或者用 DeepSeek 等国内兼容端点。

### 10.6 中文输入乱码

**症状**：终端里中文显示成 `??` 或方块。

**原因**：Windows 默认终端编码不是 UTF-8。

**解决**：

```bash
# PowerShell
chcp 65001  # 切到 UTF-8

# 或在 .env 里加（如果用 cmd）
CHCP=65001
```

或直接用 Windows Terminal（默认 UTF-8）。

### 10.7 Ctrl+C 退出时残留

**症状**：Ctrl+C 退出后，终端提示符显示异常。

**原因**：`readline` 没正常关闭。

**解决**：本章代码 `rl.close()` 只在 `break` 后调，Ctrl+C 是强杀，没机会调。生产代码应该监听 `SIGINT`：

```typescript
process.on("SIGINT", () => {
  rl.close();
  process.exit(0);
});
```

教学向省略了，但要知道。

## 11. 与真实 Claude Code 对比

真实 Claude Code 是 Anthropic 官方的 CLI Agent，本章是它的最简骨架。下表是详细对比：

| 方面 | 本章（ch01） | 真实 Claude Code | 差距 |
|------|--------------|------------------|------|
| **代码行数** | 61 行 | 数万行 | 100× |
| **工具调用** | 无 | 10+ 个工具（Read/Write/Bash/Grep/Glob/Edit/...） | Ch2 起 |
| **流式输出** | 无，等全部生成完再打印 | 流式逐字输出，边生成边显示 | Ch3 |
| **System Prompt** | 无 | 数千字精心设计，含工具说明、权限规则、风格指南 | Ch4 |
| **上下文管理** | 无限增长，直到 token 爆 | token 计数 + 自动压缩 + 滑动窗口 | Ch5 |
| **权限确认** | 无 | 工具执行前问用户 yes/no | Ch6 |
| **多行输入** | 不支持，回车即提交 | 支持，三引号或反斜杠续行 | - |
| **历史持久化** | 无，关掉就丢 | 可选保存到磁盘 | - |
| **错误重试** | 无，错误就跳过 | 指数退避重试 | - |
| **并发** | 单请求 | 多工具可并发 | - |
| **UI** | 纯文本 | ink + 语法高亮 + 进度条 | - |
| **配置** | `.env` 4 个变量 | 多个配置文件 + 命令行参数 | - |
| **模型选择** | 单一模型 | 可按任务选不同模型 | - |

**但核心骨架完全一致**：

```
本章：     messages 数组 + while 循环 + client.messages.create()
Claude Code：messages 数组 + while 循环 + client.messages.create() + 一堆增强
```

Claude Code 的 `query()` 函数本质就是这个 `while` 循环的增强版。增强的是：

1. **循环内分支多了**：`stop_reason === "tool_use"` 时进内层循环，执行工具，继续调 LLM。
2. **messages 操作多了**：压缩、截断、序列化、反序列化。
3. **请求参数多了**：`system`、`tools`、`stream: true`、`metadata` 等。
4. **错误处理复杂了**：重试、降级、用户提示。

**但骨架没变**。这就是为什么这一章值得花时间彻底看懂——后面所有章节都是在**这个骨架上加东西**，不会推翻重来。

> **心智模型**：把本章的 61 行代码想象成一个"光秃秃的衣架"。后面 Ch2 加工具是挂一件外套，Ch3 加流式是挂一条裤子，Ch4 加 system prompt 是挂一顶帽子。衣架本身不动，挂的东西越来越多。最后挂满了就是 Claude Code。

## 12. 下一章预告

现在模型只能"说话"，不能"做事"。你问它"当前目录有哪些文件？"，它会**编造**一个答案，因为它**看不到**你的文件系统。

下一章（Ch2）加入两个工具：`read_file` 和 `write_file`，让模型能真正读写文件——从聊天机器人变成 Agent。

**关键概念**：

1. **tool_use 协议**：模型怎么"说"它想调工具？答案是在 `content` 数组里输出一个 `{ type: "tool_use", name: "read_file", input: { path: "foo.txt" } }` 块。
2. **tool_result 块**：你执行完工具，要把结果以 `{ type: "tool_result", tool_use_id: "...", content: "文件内容" }` 形式加回 `messages`。
3. **内层 agentic loop**：`stop_reason === "tool_use"` 时不回外层，执行完工具继续调 LLM，直到 `stop_reason === "end_turn"`。
4. **tools 参数**：`client.messages.create()` 加一个 `tools` 参数，告诉模型有哪些工具可用、参数 schema 是什么。

下一章代码会在本章基础上加约 50 行，达到 100 行左右。骨架完全不变，只是 `while` 循环里多一个 `if` 分支。

### 练习 2：打印 token 用量（10 分钟）

**任务**：每次 API 响应后，打印本次消耗的 token 数。

**提示**：`response.usage` 是 `{ input_tokens, output_tokens }`。在 `console.log(text)` 后加：

```typescript
console.log(`  [tokens: in=${response.usage.input_tokens}, out=${response.usage.output_tokens}]`);
```

**目标**：直观看到"带完整历史"的代价——第 N 轮的 `input_tokens` 会比第 1 轮大很多。

**思考**：跑 10 轮对话后，`input_tokens` 增长了多少倍？这就是 Ch5 上下文压缩要解决的问题。

### 练习 3：切换到 DeepSeek（10 分钟）

**任务**：注册一个 DeepSeek 账号（https://platform.deepseek.com），拿到 API Key，改 `.env`：

```bash
API_KEY=sk-xxx          # DeepSeek 的 key
BASE_URL=https://api.deepseek.com/anthropic
MODEL=deepseek-chat
```

跑同一份代码，验证能正常对话。

**目标**：理解 baseURL 切换原理——同一份代码，不同供应商。

**思考**：对比 Claude 和 DeepSeek 的回答风格、速度、价格。为什么 Claude Code 选择默认用 Claude？

### 练习 4：加 system prompt（15 分钟）

**任务**：在 `client.messages.create()` 调用里加一个 `system` 参数：

```typescript
const response = await client.messages.create({
  model,
  max_tokens: maxTokens,
  system: "你是一个毒舌但有用的编程助手。每次回答前先吐槽一句，再给答案。",
  messages,
});
```

**目标**：理解 system prompt 不在 `messages` 数组里，是单独的字段。它对每次请求都生效，但不算"对话历史"。

**思考**：system prompt 会不会随着轮数增加被"忘掉"？为什么？（答：不会，因为每次请求都带同一个 system 字段，它是请求参数，不是历史的一部分。）

### 练习 5：实现 "exit" 时保存对话（20 分钟）

**任务**：用户输入 `exit` 时，把 `messages` 数组序列化成 JSON 写到 `conversation.json`：

```typescript
import * as fs from "fs";

// 在 break 之前
if (userInput.trim() === "exit") {
  fs.writeFileSync("conversation.json", JSON.stringify(messages, null, 2));
  console.log("对话已保存到 conversation.json");
  break;
}
```

**延伸**：启动时检查 `conversation.json` 是否存在，存在就加载到 `messages`，实现"继续上次对话"。

```typescript
if (fs.existsSync("conversation.json")) {
  const saved = JSON.parse(fs.readFileSync("conversation.json", "utf-8"));
  messages.push(...saved);
  console.log(`已加载 ${saved.length} 条历史消息`);
}
```

**目标**：亲手验证"messages 数组就是对话的全部状态"——把它存到文件、再从文件读回来，对话能无缝继续。没有任何"会话 ID"或"服务端状态"参与。

**思考**：如果两个不同的 `conversation.json` 文件，加载不同的一个，对话内容就不同。这是不是证明了"对话状态 100% 在客户端"？
