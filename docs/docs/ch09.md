## 9.1 前置知识

### 9.1.1 什么是 CLI

**CLI**（Command-Line Interface，命令行界面）是一种通过终端文本输入输出与程序交互的方式。相对于 GUI（图形界面），CLI 有几个特点：

- **无窗口**：直接在终端里跑，不弹窗、不画按钮。
- **参数驱动**：启动时通过 `--flag value` 传参，运行中通过 stdin / readline 接收用户输入。
- **可脚本化**：可以放进 shell 脚本、CI 流水线、管道里组合使用。
- **对开发者友好**：日志、错误、堆栈都直接打到终端，调试方便。

为什么 Claude Code、Aider、Cursor Agent 这类编码 Agent 都做成 CLI？

1. **代码本身就在终端里**：开发者本来就在 shell 里跑 `git`、`npm`、`python`，Agent 顺理成章地嵌进这个工作流。
2. **工具调用天然适配**：Agent 要执行 `bash`、`read`、`write` 这些工具，这些工具的输入输出本来就是文本流，CLI 是最自然的承载。
3. **可组合**：CLI 可以被 IDE 插件、Web 后端、CI 脚本调用，一份核心可以多前端复用。
4. **流式输出直观**：模型逐 token 生成，终端逐字打印，用户能实时看到 Agent 在"想什么"。

### 9.1.2 参数解析是什么

启动一个 CLI 时，用户会这样写：

```bash
npx tsx src/main.ts --model deepseek-chat --auto-approve --help
```

`process.argv` 在 Node.js 里是一个字符串数组，大概长这样：

```javascript
[
  "node",                                      // argv[0]: 解释器路径
  "/path/to/src/main.ts",                      // argv[1]: 脚本路径
  "--model", "deepseek-chat",                  // argv[2..3]: 一个带值的参数
  "--auto-approve",                            // argv[4]: 一个布尔型参数
  "--help"                                     // argv[5]: 一个布尔型参数
]
```

**参数解析**就是把这个字符串数组**结构化**成一个对象：

```typescript
{
  model: "deepseek-chat",
  autoApprove: true,
  help: true
}
```

解析器要处理几类参数：

| 类型 | 例子 | 解析结果 |
|------|------|----------|
| 布尔 flag | `--auto-approve` | `autoApprove: true` |
| 带值参数 | `--model X` | `model: "X"` |
| 简写 flag | `-h` | `help: true` |
| 位置参数 | `foo.ts` | `files: ["foo.ts"]` |
| 未知参数 | `--unknown` | 报错 or 忽略 |

### 9.1.3 配置管理是什么

一个 Agent 需要很多"运行参数"：API Key、模型名、最大 token 数、是否自动批准、Base URL……这些参数有三个来源：

1. **命令行参数**：用户本次启动时显式指定，**优先级最高**。
2. **环境变量**：写在 `.env` 文件或 shell 里，**会话级默认值**。
3. **代码默认值**：写在源码里，**兜底**。

**配置管理**就是按优先级把这三个来源合并成一个 `Config` 对象，供后续所有模块使用。为什么需要优先级？

- 命令行参数优先级最高：用户**本次**显式指定的，应该覆盖一切。
- 环境变量次之：用户**会话级**的偏好，不该被代码默认值覆盖。
- 代码默认值最低：**兜底**，确保没配置也能跑。

举个例子：用户在 `.env` 里写了 `MODEL=claude-sonnet-4-20250514`，但本次启动加了 `--model deepseek-chat`，最终应该用 `deepseek-chat`。反过来，如果没加 `--model`，就用 `.env` 里的值。如果 `.env` 也没写，就用代码里的默认值。

### 9.1.4 为什么需要"整合"这一章

前 8 章每一章都是**独立可运行**的 demo，各自有自己的 `main.ts`、自己的工具定义、自己的 prompt。这种方式便于学习，但有几个问题：

1. **代码重复**：每章都重新写了一遍 `Anthropic` 客户端初始化、消息循环、工具 dispatch。
2. **无法组合**：Ch7 的权限系统没法直接用 Ch4 的流式输出，因为它们在不同的文件里、接口不对齐。
3. **不可交付**：用户没法 `npm install -g` 后直接 `my-agent` 启动，因为没有一个统一的入口。

整合的目的就是**消除重复、对齐接口、提供统一入口**，让这 8 块能力能**协同工作**。整合后，用户只需要一个命令就能启动一个**同时具备**流式、权限、子智能体、上下文管理的 Agent。

## 9.2 整合的思路

### 9.2.1 把 Ch1-Ch8 合并到 `src/`

整合的核心动作是：**把每一章的核心代码抽成一个模块，放进 `src/` 目录**。不是简单复制粘贴，而是要做三件事：

1. **抽接口**：把每章的"核心函数"或"核心类"导出，去掉每章自己的 `main()` 演示代码。
2. **改 import 路径**：从 `from "./tools"` 改成 `from "./tools"` 这种相对路径，对齐新目录结构。
3. **对齐类型**：比如 Ch4 的流式输出和 Ch6 的上下文管理都要用 `Message[]`，要确保它们引用的是**同一个** `types.ts` 里的定义，而不是各自再定义一遍。

### 9.2.2 模块化组织原则

我们把代码分成 9 个模块（文件），每个模块**只负责一件事**：

| 文件 | 职责 | 来源章节 |
|------|------|----------|
| `main.ts` | 入口：解析参数 → 加载配置 → 启动循环 | Ch9 新增 |
| `cli.ts` | 命令行参数解析 | Ch9 新增 |
| `config.ts` | 配置加载（env + args 合并） | Ch9 新增 |
| `types.ts` | 共享类型定义（Message、Tool、Config 等） | Ch1-Ch8 抽取 |
| `agent-loop.ts` | 核心循环（整合流式+prompt+上下文+权限+子智能体） | Ch1-Ch8 整合 |
| `tools/` | 完整工具集（bash、read、write、edit、glob、grep） | Ch3 |
| `prompts/` | System Prompt 生成 | Ch5 |
| `context.ts` | 上下文管理（token 计数 + 截断 + 压缩） | Ch6 |
| `permission.ts` | 权限系统（危险命令检测 + 用户确认） | Ch7 |
| `subagent.ts` | 子智能体（独立循环 + 上下文隔离） | Ch8 |

**单一职责原则**：每个文件只做一件事，改一个能力只动一个文件。比如要加一个新工具，只动 `tools/`；要改 prompt，只动 `prompts/`；要加一个 CLI 参数，只动 `cli.ts` 和 `config.ts`。

### 9.2.3 模块间依赖关系

整合时最容易踩的坑是**循环依赖**：A 依赖 B，B 又依赖 A，Node.js 会报错或得到 `undefined`。我们按下面的层次组织依赖：

```
              main.ts
                │
        ┌───────┴───────┐
        ▼               ▼
     cli.ts          config.ts
        │               │
        └───────┬───────┘
                ▼
          agent-loop.ts  ◄──── 整合层
                │
   ┌─────┬──────┼──────┬─────┐
   ▼     ▼      ▼      ▼     ▼
 tools/ prompts/ context permission subagent
   │     │      │      │         │
   └─────┴──────┴──────┴─────────┴──► types.ts  ◄──── 叶子层
```

- **叶子层**：`types.ts` 只定义类型，不依赖任何模块。所有人都可以依赖它。
- **能力层**：`tools/`、`prompts/`、`context.ts`、`permission.ts`、`subagent.ts` 各自实现一个能力，只依赖 `types.ts`。
- **整合层**：`agent-loop.ts` 把能力层组合起来，依赖所有能力层模块。
- **入口层**：`main.ts`、`cli.ts`、`config.ts` 负责启动配置，依赖 `agent-loop.ts`。

**关键约束**：依赖只能**向下**流动，不能向上、不能横向。比如 `tools/` 不能依赖 `agent-loop.ts`，`context.ts` 不能依赖 `permission.ts`。这样保证没有循环依赖。

## 9.3 CLI 参数解析设计

### 9.3.1 支持哪些参数

我们设计以下参数：

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `--model` | string | `claude-sonnet-4-20250514` | 模型名 |
| `--base-url` | string | `https://api.anthropic.com` | API Base URL（兼容 DeepSeek 等） |
| `--api-key` | string | 从 env 读 | API Key |
| `--max-tokens` | number | 4096 | 单次回复最大 token |
| `--context-limit` | number | 100000 | 上下文窗口 token 上限 |
| `--auto-approve` | boolean | false | 自动批准所有工具调用（跳过确认） |
| `--system-prompt` | string | 内置默认 | 自定义 System Prompt 路径 |
| `--help` / `-h` | boolean | false | 显示帮助 |
| `--version` / `-v` | boolean | false | 显示版本 |

### 9.3.2 为什么手写而非用 commander

Node.js 生态有成熟的参数解析库：`commander`、`yargs`、`meow`、`clipanion`。为什么我们手写？

1. **教学目的**：这一章是讲"从零实现"，用第三方库就跳过了参数解析的本质。手写一遍，你才能理解 `commander` 在做什么。
2. **依赖最小化**：每多一个依赖，就多一份 `node_modules` 体积、多一个安全审计面、多一个版本升级负担。对于一个 2000 行的教学项目，引入 commander 是杀鸡用牛刀。
3. **完全可控**：手写解析器，错误信息、帮助格式、参数校验都完全可控，不会被库的默认行为绑架。
4. **参数少**：我们只有 9 个参数，手写一个 switch-case 就够了。commander 的优势在于几十个参数 + 子命令 + 自动补全，我们用不上。

**真实 Claude Code 的选择**：它用的是 `commander`，因为它有几十个子命令、复杂的参数校验、shell 补全需求。我们的场景不需要。

### 9.3.3 `parseArgs` 函数实现

```typescript
// src/cli.ts
export interface CLIArgs {
  model?: string;
  baseURL?: string;
  apiKey?: string;
  maxTokens?: number;
  contextLimit?: number;
  autoApprove: boolean;     // 默认 false，所以不是 optional
  systemPrompt?: string;
  help: boolean;
  version: boolean;
}

export function parseArgs(argv: string[]): CLIArgs {
  // argv[0] 是 node，argv[1] 是脚本路径，从 argv[2] 开始才是用户参数
  const args = argv.slice(2);

  const result: CLIArgs = {
    autoApprove: false,
    help: false,
    version: false,
  };

  for (let i = 0; i < args.length; i++) {
    const arg = args[i];

    switch (arg) {
      // 布尔 flag
      case "--auto-approve":
        result.autoApprove = true;
        break;
      case "--help":
      case "-h":
        result.help = true;
        break;
      case "--version":
      case "-v":
        result.version = true;
        break;

      // 带值参数：值在下一个 argv 元素
      case "--model":
        result.model = args[++i];
        break;
      case "--base-url":
        result.baseURL = args[++i];
        break;
      case "--api-key":
        result.apiKey = args[++i];
        break;
      case "--max-tokens":
        result.maxTokens = parseInt(args[++i], 10);
        break;
      case "--context-limit":
        result.contextLimit = parseInt(args[++i], 10);
        break;
      case "--system-prompt":
        result.systemPrompt = args[++i];
        break;

      default:
        // 未知参数：报错退出，避免用户拼错参数名却静默忽略
        console.error(`错误: 未知参数 ${arg}`);
        console.error("使用 --help 查看可用参数");
        process.exit(1);
    }
  }

  return result;
}
```

**几个初学者容易忽略的细节**：

1. **`argv.slice(2)`**：`process.argv` 前两个元素是 `node` 路径和脚本路径，必须跳过。
2. **`args[++i]`**：带值参数的值在**下一个**元素，用 `++i` 先自增再取值，同时让外层 for 跳过这个值。
3. **未知参数报错**：而不是静默忽略。用户拼错 `--modle` 时应该立刻报错，否则他会以为参数生效了。
4. **`parseInt` 的第二个参数**：永远传 `10`，避免 `0x` 开头的字符串被当成十六进制。

## 9.4 配置加载设计

### 9.4.1 三级优先级

```
命令行参数 (--model X)  >  环境变量 (MODEL=X in .env)  >  代码默认值
```

实现方式很简单：**从低到高覆盖**。先用默认值，再用环境变量覆盖，最后用命令行参数覆盖。

```typescript
// src/config.ts
import { CLIArgs } from "./cli";

export interface Config {
  apiKey: string;
  model: string;
  baseURL: string;
  maxTokens: number;
  contextLimit: number;
  autoApprove: boolean;
  systemPrompt?: string;
}

export function loadConfig(args: CLIArgs): Config {
  // 1. 默认值（最低优先级）
  const config: Config = {
    apiKey: "",
    model: "claude-sonnet-4-20250514",
    baseURL: "https://api.anthropic.com",
    maxTokens: 4096,
    contextLimit: 100000,
    autoApprove: false,
  };

  // 2. 环境变量覆盖（中优先级）
  // 用 dotenv 加载 .env 文件，把里面的 KEY=VALUE 注入 process.env
  // 这里假设 dotenv 已经在 main.ts 里调用过 dotenv.config()
  if (process.env.ANTHROPIC_API_KEY) config.apiKey = process.env.ANTHROPIC_API_KEY;
  if (process.env.MODEL)             config.model = process.env.MODEL;
  if (process.env.BASE_URL)          config.baseURL = process.env.BASE_URL;
  if (process.env.MAX_TOKENS)        config.maxTokens = parseInt(process.env.MAX_TOKENS, 10);
  if (process.env.CONTEXT_LIMIT)     config.contextLimit = parseInt(process.env.CONTEXT_LIMIT, 10);
  if (process.env.AUTO_APPROVE === "true") config.autoApprove = true;

  // 3. 命令行参数覆盖（最高优先级）
  if (args.apiKey)       config.apiKey = args.apiKey;
  if (args.model)        config.model = args.model;
  if (args.baseURL)      config.baseURL = args.baseURL;
  if (args.maxTokens)    config.maxTokens = args.maxTokens;
  if (args.contextLimit) config.contextLimit = args.contextLimit;
  if (args.autoApprove)  config.autoApprove = true;
  if (args.systemPrompt) config.systemPrompt = args.systemPrompt;

  // 4. 校验必填项
  if (!config.apiKey) {
    console.error("错误: 未配置 API_KEY");
    console.error("请通过 --api-key 参数或 ANTHROPIC_API_KEY 环境变量提供");
    process.exit(1);
  }

  return config;
}
```

**为什么这个顺序是对的**：后赋值的覆盖先赋值的。默认值最先写，环境变量第二，命令行参数最后。所以命令行参数一旦出现，就一定覆盖前两个。

### 9.4.2 缺失 API Key 的处理

API Key 是**必填项**，没有它整个 Agent 无法调用模型。处理方式是：

1. 检查 `config.apiKey` 是否为空字符串。
2. 如果为空，**打印清晰的错误信息**（告诉用户两种配置方式），然后 `process.exit(1)` 退出。

**为什么不抛异常而是直接 exit**？因为这是**启动阶段**的校验，异常没人 catch，会打印一个丑陋的堆栈。直接 `exit(1)` 更干净，错误信息也更友好。

**真实 Claude Code 的处理**：它会在首次启动时**交互式引导**用户登录（OAuth 流程），把 Key 存进 `~/.claude/credentials.json`。我们这里简化成手动配置。

### 9.4.3 `.env` 文件加载

我们用 `dotenv` 这个库加载 `.env` 文件。它是 Node.js 生态最常用的环境变量管理工具，做的事情很简单：

1. 读取项目根目录的 `.env` 文件。
2. 按 `KEY=VALUE` 解析每一行。
3. 把键值对注入 `process.env`。

```typescript
// src/main.ts 顶部
import * as dotenv from "dotenv";
dotenv.config();
```

**为什么不自己写**：`dotenv` 的实现只有几十行，但处理边界情况（引号、注释、多行值、转义）很烦。这是一个**值得用库**的地方，因为它的行为完全标准化，没有定制需求。

**`.env.example` 模板**：

```bash
# 复制此文件为 .env，填入你的 API Key
ANTHROPIC_API_KEY=sk-ant-xxxxx
# 可选：覆盖默认模型
# MODEL=deepseek-chat
# BASE_URL=https://api.deepseek.com/anthropic
```

提交到 git 的是 `.env.example`（不含真实 Key），`.env` 加进 `.gitignore`（含真实 Key，不能泄露）。

### 9.5.2 每个文件的职责

**`main.ts`（入口，~30 行）**

只做三件事：加载 `.env`、解析参数、启动循环。是整个程序的**唯一入口点**，`package.json` 的 `bin` 字段指向它。

**`cli.ts`（参数解析，~80 行）**

纯函数模块，输入 `argv` 数组，输出 `CLIArgs` 对象。不读 `process.env`，不做 IO，方便单元测试。

**`config.ts`（配置加载，~60 行）**

**`types.ts`（共享类型，~50 行）**

定义 `Message`、`Tool`、`ToolResult`、`Config`、`PermissionResult` 等所有模块共用的类型。**只有类型，没有实现**，编译后不产生任何 JS 代码（只有 `.d.ts`）。

**`agent-loop.ts`（核心循环，~200 行）**

整合层。把 `tools/`、`prompts/`、`context.ts`、`permission.ts`、`subagent.ts` 组装成一个 `runAgentLoop` 函数。这是**整个项目最核心**的文件，下一节会逐行讲解。

**`context.ts`（上下文管理，~150 行）**

来自 Ch6。负责 token 计数、消息截断、历史压缩。导出 `ContextManager` 类。

**`permission.ts`（权限系统，~100 行）**

来自 Ch7。负责危险命令检测、用户确认 prompt。导出 `PermissionManager` 类。

**`subagent.ts`（子智能体，~120 行）**

来自 Ch8。负责启动独立的子 Agent 循环，隔离上下文。导出 `runSubagent` 函数。

**`tools/*.ts`（工具集，每个 ~50 行，共 ~300 行）**

来自 Ch3。每个文件实现一个工具（bash、read、write、edit、glob、grep），导出符合 `Tool` 接口的对象。`tools/index.ts` 把所有工具注册成一个数组。

**`prompts/system-prompt.ts`（System Prompt，~80 行）**

来自 Ch5。生成发给模型的 system prompt，包含工具使用规则、安全约束、输出格式要求。

## 9.6 `agent-loop.ts` 详解

这是整个项目最核心的文件。它把 Ch1-Ch8 的所有能力**整合到一个函数**里。我们逐段讲解。

### 9.6.1 函数签名

```typescript

import { ContextManager } from "./context";
import { PermissionManager } from "./permission";
import { runSubagent } from "./subagent";

export async function runAgentLoop(config: Config): Promise<void> {
  // ...
}
```

输入是一个 `Config` 对象（已经合并完所有参数），输出是 `void`（永远不返回，直到用户 Ctrl+C）。

### 9.6.2 初始化阶段

```typescript
  // 1. 创建 API 客户端
  const client = new Anthropic({
    apiKey: config.apiKey,
    baseURL: config.baseURL,
  });

  // 2. 创建上下文管理器（Ch6）
  const ctx = new ContextManager(config.contextLimit);

  // 3. 创建权限管理器（Ch7）
  const perm = new PermissionManager(config.autoApprove);

  // 4. 构建 System Prompt（Ch5）
  const systemPrompt = buildSystemPrompt({ tools });

  // 5. 初始化 readline，用于读取用户输入
  const rl = readline.createInterface({
    input: process.stdin,
    output: process.stdout,
  });
```

这一步把所有"有状态的对象"创建出来：API 客户端、上下文管理器、权限管理器、readline。这些对象在整个会话期间**只创建一次**，后续循环里反复使用。

### 9.6.3 外层循环：等用户输入

```typescript
  // 外层循环：等用户输入
  while (true) {
    const userInput = await new Promise<string>((resolve) => {
      rl.question("\n> ", resolve);
    });

    // 用户输入 /exit 或 Ctrl+D 退出
    if (userInput.trim() === "/exit" || userInput === null) {
      console.log("再见！");
      rl.close();
      return;
    }

    // 把用户消息加入上下文
    ctx.addMessage({ role: "user", content: userInput });

    // 进入内层循环：跑工具
    await runInnerLoop(client, config, systemPrompt, ctx, perm);

    // 上下文超限时压缩（Ch6）
    if (ctx.tokenCount() > config.contextLimit) {
      await ctx.compress();
    }
  }
```

外层循环只做三件事：**读输入 → 跑内层 → 压缩上下文**。它不直接调模型，也不直接调工具，这些都在内层循环里。

**为什么分两层**：外层是"对话轮次"，每一轮用户说一句话，Agent 可能要调好几个工具才能回答；内层是"工具调用链"，模型可能连续调 N 个工具，每次都把结果回传给模型再问"还要调吗"。这个两层结构在 Ch1 就讲过，这里只是把它落到代码。

### 9.6.4 内层循环：跑工具

```typescript
async function runInnerLoop(
  client: Anthropic,
  config: Config,
  systemPrompt: string,
  ctx: ContextManager,
  perm: PermissionManager,
): Promise<void> {
  while (true) {
    // 1. 调模型（流式，Ch4）
    const stream = client.messages.stream({
      model: config.model,
      max_tokens: config.maxTokens,
      system: systemPrompt,
      messages: ctx.getMessages(),
    });

    // 2. 逐 token 打印 + 收集 tool_use
    let toolUses: ToolUse[] = [];
    for await (const event of stream) {
      if (event.type === "content_block_delta") {
        if (event.delta.type === "text_delta") {
          process.stdout.write(event.delta.text);  // 流式打印
        } else if (event.delta.type === "input_json_delta") {
          // 收集工具调用的参数碎片
          collectToolInput(event.delta, toolUses);
        }
      }
    }

    // 3. 把 assistant 回复加入上下文
    const assistantMessage = await stream.finalMessage();
    ctx.addMessage(assistantMessage);

    // 4. 如果没有工具调用，内层结束（回到外层等用户）
    if (toolUses.length === 0) {
      console.log();  // 换行
      return;
    }

    // 5. 执行所有工具调用
    const toolResults: ToolResult[] = [];
    for (const toolUse of toolUses) {
      // 5a. 权限确认（Ch7）
      const allowed = await perm.check(toolUse.name, toolUse.input);
      if (!allowed) {
        toolResults.push({
          tool_use_id: toolUse.id,
          content: "用户拒绝了这次工具调用",
          is_error: true,
        });
        continue;
      }

      // 5b. 子智能体特殊处理（Ch8）
      if (toolUse.name === "Task") {
        const result = await runSubagent(toolUse.input, config);
        toolResults.push({
          tool_use_id: toolUse.id,
          content: result,
        });
        continue;
      }

      // 5c. 普通工具执行（Ch3）
      const tool = tools.find((t) => t.name === toolUse.name);
      if (!tool) {
        toolResults.push({
          tool_use_id: toolUse.id,
          content: `未知工具: ${toolUse.name}`,
          is_error: true,
        });
        continue;
      }

      const result = await tool.execute(toolUse.input);
      toolResults.push({
        tool_use_id: toolUse.id,
        content: result,
      });
    }

    // 6. 把工具结果加入上下文，继续循环让模型决定下一步
    ctx.addMessage({ role: "user", content: toolResults });
  }
}
```

内层循环做了 6 件事，对应 Ch1-Ch8 的 6 个能力：

| 步骤 | 做什么 | 来源章节 |
|------|--------|----------|
| 1 | 调模型（流式） | Ch4 |
| 2 | 逐 token 打印 + 收集 tool_use | Ch4 + Ch2 |
| 3 | assistant 回复入上下文 | Ch6 |
| 4 | 没工具调用就退出 | Ch1 |
| 5 | 权限确认 + 子智能体 + 普通工具 | Ch7 + Ch8 + Ch3 |
| 6 | 工具结果入上下文 | Ch2 |

**关键点**：步骤 6 之后**不 return**，而是回到 while 顶部继续调模型。模型会看到工具结果，然后决定：**继续调工具**（回到步骤 5）or **回复用户**（步骤 4 退出）。这就是 Agent 的"思考-行动"循环。

### 9.6.5 整合的难点

整合时最让人头疼的不是写新代码，而是**对齐前 8 章的接口**。几个具体问题：

1. **Message 类型统一**：Ch1 用 `{role, content: string}`，Ch2 引入 `content: Array<TextBlock | ToolUseBlock>`，Ch4 流式又引入 `delta` 类型。整合时必须统一成一种 `Message` 类型，所有章节的代码都要改。
2. **工具接口统一**：Ch3 的工具是 `{name, description, execute}`，Ch8 的子智能体也是"工具"但接口不同。整合时让 `Task` 也实现 `Tool` 接口，在内层循环里特殊处理。
3. **流式 + 工具调用**：Ch4 的流式只处理文本，Ch2 的工具调用是非流式。整合时要**在流式事件里同时收集文本和 tool_use 碎片**，这是最 tricky 的部分。
4. **上下文 + 流式**：流式响应是异步迭代器，要等它结束才能拿到完整 message 加入上下文。用 `await stream.finalMessage()` 拿最终结果。

## 9.7 `main.ts` 入口流程

`main.ts` 是整个程序的入口，只做三件事：

```typescript
// src/main.ts
import * as dotenv from "dotenv";
import { parseArgs, printHelp } from "./cli";
import { loadConfig } from "./config";
import { runAgentLoop } from "./agent-loop";

async function main() {
  // 1. 加载 .env 文件
  dotenv.config();

  // 2. 解析命令行参数
  const args = parseArgs(process.argv);

  // 3. 处理 --help / --version
  if (args.help) {
    printHelp();
    process.exit(0);
  }
  if (args.version) {
    console.log("miniclaudecode v0.1.0");
    process.exit(0);
  }

  // 4. 加载配置（合并默认值 + env + args）
  const config = loadConfig(args);

  // 5. 启动 Agent 循环
  console.log(`miniclaudecode 已启动 (模型: ${config.model})`);
  console.log(`输入 /exit 退出，Ctrl+C 中断\n`);

  await runAgentLoop(config);
}

main().catch((err) => {
  console.error("致命错误:", err);
  process.exit(1);
});
```

**为什么用 `async function main()`**：`runAgentLoop` 是异步的，顶层 await 在老版本 Node.js 不支持，所以包一层 `main()` 函数然后 `.catch()`。

**为什么 `main().catch()` 而不是 try-catch**：启动阶段的同步错误（如配置校验）已经 `process.exit` 了，能走到这里的都是运行时异步错误。统一 catch 打印后退出，避免 unhandled rejection。

## 9.8 完整运行流程

让我们**完整走一遍**从用户敲命令到工具执行的全过程，帮助初学者建立"整体感"。

### 9.8.1 启动阶段

```bash
$ cd lessons/ch09-final
$ npx tsx src/main.ts --auto-approve
```

1. **Node.js 启动**：`tsx` 把 `src/main.ts` 编译成 JS 并执行。
2. **`main()` 运行**：
   - `dotenv.config()` 读取 `.env`，把 `ANTHROPIC_API_KEY=sk-...` 注入 `process.env`。
   - `parseArgs(["node", "main.ts", "--auto-approve"])` 返回 `{ autoApprove: true, help: false, ... }`。
   - `loadConfig(args)` 合并默认值 + env + args，返回完整 `Config`。
   - `runAgentLoop(config)` 启动循环。
3. **`runAgentLoop` 初始化**：创建 `Anthropic` 客户端、`ContextManager`、`PermissionManager`、构建 system prompt、创建 readline。
4. **打印欢迎信息**，进入外层 while 循环，`rl.question("\n> ")` 等待用户输入。

### 9.8.2 用户输入阶段

```bash
> 帮我看看当前目录有哪些文件
```

5. **`rl.question` resolve**，返回字符串 `"帮我看看当前目录有哪些文件"`。
6. **`ctx.addMessage`**：把 `{ role: "user", content: "帮我看看..." }` 加入消息历史。
7. **进入 `runInnerLoop`**。

### 9.8.3 模型推理阶段

8. **`client.messages.stream`**：把 system prompt + 消息历史发给模型，开始流式接收。
9. **模型流式返回**：
   - 先返回一段文本："好的，我来用 glob 工具看看当前目录..."
   - 然后返回一个 `tool_use` block：`{ name: "glob", input: { pattern: "*" } }`
10. **逐 token 打印**：文本部分实时打到终端。
11. **收集 tool_use**：`toolUses` 数组里现在有一个元素。
12. **`ctx.addMessage`**：把 assistant 的完整回复（文本 + tool_use）加入上下文。

### 9.8.4 工具执行阶段

13. **遍历 `toolUses`**，对每个工具调用：
    - `perm.check("glob", { pattern: "*" })`：因为 `--auto-approve`，直接返回 `true`。
    - 找到 `tools/glob.ts`，调用 `tool.execute({ pattern: "*" })`。
    - `glob` 工具读取当前目录，返回文件列表 `"package.json\ntsconfig.json\nsrc/\n..."`。
    - 把结果包成 `ToolResult`，push 进 `toolResults`。
14. **`ctx.addMessage`**：把 `{ role: "user", content: toolResults }` 加入上下文（注意 role 是 `user`，这是 Anthropic API 的约定：工具结果以 user 消息形式回传）。
15. **回到内层循环顶部**，再次调模型。

### 9.8.5 第二轮推理

16. **模型看到工具结果**，决定不再调工具，直接回复文本：
    "当前目录有：package.json、tsconfig.json、src/ 目录。需要我做什么？"
17. **流式打印**这段文本。
18. **`toolUses.length === 0`**，内层循环 `return`，回到外层。

### 9.8.6 等待下一次输入

19. **外层循环**检查上下文是否超限，没超限就继续。
20. **`rl.question("\n> ")`** 再次等待用户输入。

整个过程从用户敲回车到看到回复，大约 2-5 秒（取决于模型速度和工具执行速度）。其中模型推理占大部分时间，工具执行（本地 IO）通常很快。

## 9.11 常见陷阱

整合 8 章代码时，初学者几乎必然踩到以下几个坑。提前知道就能避免。

### 9.11.1 模块引用路径错误

**症状**：`Error: Cannot find module './tools'`

**原因**：从单文件 demo 搬到多文件项目时，import 路径没改。比如原来 `import { bash } from "./tools"` 在 `ch03/main.ts` 里是对的，搬到 `src/agent-loop.ts` 里就要改成 `import { tools } from "./tools"`（注意 `tools` 是目录，会自动解析到 `tools/index.ts`）。

**解决**：搬完代码后**全局搜索**原路径，逐一改。TypeScript 的 `tsconfig.json` 里配 `paths` 可以用 `@/tools` 这种别名，但教学项目建议用相对路径，更直观。

### 9.11.2 循环依赖

**症状**：`ReferenceError: Cannot access 'X' before initialization` 或拿到 `undefined`。

**原因**：A import B，B import A。Node.js 的 ES Module 加载是异步的，循环依赖时其中一个会拿到未初始化的值。

**例子**：

```typescript
// agent-loop.ts
import { runSubagent } from "./subagent";

// subagent.ts
import { runAgentLoop } from "./agent-loop";  // 循环！
```

**解决**：

- **方案 1**：把共享的函数抽到第三个文件（如 `loop-core.ts`），让两者都依赖它。
- **方案 2**：用**延迟 import**，在函数内部 import：

```typescript
// subagent.ts
export async function runSubagent(input, config) {
  const { runAgentLoop } = await import("./agent-loop");  // 动态 import
  // ...
}
```

动态 import 在函数执行时才加载，避开了模块加载阶段的循环。

### 9.11.3 配置覆盖顺序写反

**症状**：明明加了 `--model deepseek-chat`，但实际用的还是 `.env` 里的模型。

**原因**：`loadConfig` 里先写 args 再写 env，导致 env 覆盖了 args：

```typescript
// 错误顺序
if (args.model) config.model = args.model;       // 先写 args
if (process.env.MODEL) config.model = process.env.MODEL;  // env 覆盖了 args！
```

**解决**：永远按**默认 → env → args**的顺序写，后写的覆盖先写的。

### 9.11.4 参数解析漏掉 `++i`

**症状**：`--model deepseek-chat` 解析后 `model` 是 `"--auto-approve"`（下一个 flag）。

**原因**：带值参数忘了跳过值：

```typescript
// 错误
case "--model":
  result.model = args[i + 1];  // 没有自增 i，下一轮 for 会把 "deepseek-chat" 当成新参数解析
  break;
```

**解决**：用 `args[++i]` 先自增再取值，这样 for 循环的 `i++` 会跳过值。

### 9.11.5 流式 tool_use 碎片拼接错误

**症状**：工具参数 JSON 不完整，`JSON.parse` 报错。

**原因**：流式响应里，工具的 `input` 是分多个 `input_json_delta` 事件传过来的，每个事件只有一部分 JSON 字符串。必须**拼接完所有碎片**再 parse。

**解决**：

```typescript
// 用一个 map 收集每个 tool_use 的 input 碎片
const inputBuffers = new Map<string, string>();

for await (const event of stream) {
  if (event.type === "content_block_start" && event.content_block.type === "tool_use") {
    inputBuffers.set(event.content_block.id, "");
  }
  if (event.delta?.type === "input_json_delta") {
    const current = inputBuffers.get(event.tool_use_id) || "";
    inputBuffers.set(event.tool_use_id, current + event.delta.partial_json);
  }
}

// 流结束后再 parse
for (const [id, json] of inputBuffers) {
  const input = JSON.parse(json);
  // ...
}
```

### 9.11.6 忘记把工具结果以 `user` role 回传

**症状**：模型报错 `messages must alternate between user and assistant`。

**原因**：工具结果应该以 `{ role: "user", content: [{ type: "tool_result", ... }] }` 形式加入消息，而不是 `role: "assistant"` 或 `role: "tool"`。

**解决**：严格按 Anthropic API 文档，工具结果的 role 是 `user`，content 是 `tool_result` 类型的数组。

### 9.12.1 差距分析

**MCP 协议**（Model Context Protocol）：真实 Claude Code 支持挂载外部工具服务器，用户可以接入自己公司的内部工具（如查数据库、调内部 API）。我们这版工具是硬编码的 7 个，无法扩展。

**IDE 集成**：真实 Claude Code 在 VS Code 里能**直接编辑当前打开的文件**、显示 diff、跳转行号。我们这版只能在终端里跑，工具操作的是磁盘文件，看不到实时 diff。

**AGENTS.md 继承**：真实 Claude Code 会读取项目根目录、子目录、用户主目录的 `AGENTS.md`，把规则**分层继承**进 system prompt。我们这版 system prompt 是硬编码的。

**并行子 Agent**：真实 Claude Code 可以同时启动最多 10 个子智能体并行干活。我们这版子智能体是串行的，一次只能跑一个。

**上下文压缩**：真实 Claude Code 会用**智能摘要**（让模型自己总结历史）+ **分段引用**（保留关键消息原文）。我们这版是简单截断（删掉最早的消息）。

### 9.12.2 为什么说"核心架构完全同构"

虽然有上述差距，但**核心架构是一样的**：

```
真实 Claude Code          本章 2000 行版本
─────────────             ─────────────
Agent Loop                agent-loop.ts (两层循环)
+ 工具系统                 + tools/ (7 个)
+ 上下文管理               + context.ts (截断)
+ 权限系统                 + permission.ts (确认)
+ 子智能体                 + subagent.ts (串行)
+ System Prompt           + prompts/ (硬编码)
+ 流式输出                 + stream (SSE)
```

**同构**的意思是：如果你把这个 2000 行版本的每个模块**扩充**（加更多工具、加 MCP、加并行、加智能压缩），就能**逐步逼近**真实 Claude Code。不需要推翻重来。这就是"从零实现"的价值——你理解的是**架构**，不是 API 调用。

|------|------|----------|
| Ch1 | 50 | 多轮对话 |
| Ch2 | 100 | 工具调用 |

| Ch4 | 500 | 流式输出 |

| Ch7 | 1000 | 权限系统 |

| Ch9 | 2000 | 整合 + CLI + 配置 |

### 9.13.2 七个核心概念回顾

**1. Agent Loop（两层循环）**

外层等用户输入，内层跑工具调用链。这是所有 Agent 产品的骨架。理解了这个循环，就理解了 ChatGPT、Claude、Cursor、Aider 的核心运作方式。

```
while (true) {              // 外层
  userInput = await read()
  while (true) {            // 内层
    response = await callModel()
    if (no tool calls) break
    results = await executeTools()
  }
}
```

**2. tool_use 协议**

模型不直接执行代码，它只**请求**执行某个工具，参数是 JSON。我们的代码负责**实际执行**，把结果**回传**给模型。这个"请求-执行-回传"的循环就是 tool_use 协议。它是 Anthropic、OpenAI、Google 都在采用的标准。

**3. 流式输出**

模型逐 token 生成，我们逐 token 打印。用户体验上，这是"Agent 在思考"的感觉，而不是"等 5 秒后一次性蹦出所有文字"。技术上，是 SSE（Server-Sent Events）+ 异步迭代器。

**4. System Prompt**

通过一段**隐藏的**prompt 给模型设定行为规则："你是编码助手，用工具前要确认，输出要简洁……"。模型在整个会话期间都会遵守这些规则。这是"约束模型行为"的主要手段。

**5. 上下文管理**

模型有 token 上限（如 200K）。对话越长，越接近上限。上下文管理器负责**计数**（当前多少 token）、**截断**（超限就删旧消息）、**压缩**（把旧消息摘要成一段）。这是"让 Agent 长时间运行"的关键。

**6. 权限系统**

Agent 能执行 bash、写文件，这是**危险**的。权限系统在每次工具执行前**拦截**，判断是否危险，危险就**问用户**"允许吗？"。这是"让 Agent 安全运行"的关键。

**7. 子智能体**

复杂任务可以拆给子 Agent 干。子 Agent 有**独立的上下文**（不污染主对话）、**独立的循环**（自己跑工具链）、**受限的工具集**（不能越权）。主 Agent 只拿到子 Agent 的**最终结果**，不看到它的中间过程。这是"让 Agent 处理复杂任务"的关键。

### 9.13.3 你现在理解了什么

读完这 9 章，你应该能够：

- 看懂任何 Agent 产品（Claude Code、Cursor、Aider、Devin）的核心架构。
- 自己从零写一个 Agent，知道每块代码在做什么、为什么这么写。
- 调试 Agent 问题：卡住时知道看哪里（循环？工具？上下文？权限？）。
- 评估 Agent 设计：看到一个新 Agent 产品，能判断它的架构是否合理、哪里是创新、哪里是噱头。

这些就是**所有 AI Agent 产品的通用骨架**。

## 9.14 扩展练习

想进一步加深理解？以下是 6 个扩展练习，按难度排序。每个练习都会让你对架构的理解更深一层。

### 9.14.1 练习 1：加一个 `WebFetch` 工具（简单）

**目标**：让 Agent 能抓取网页内容。

**提示**：

- 在 `tools/` 下新建 `web-fetch.ts`。
- 用 Node.js 内置的 `fetch`（Node 18+）或 `axios`。
- 工具接口：`{ url: string }` → 返回网页文本。
- 注意设置超时（10 秒）和大小上限（1MB），避免抓大文件卡死。
- 在 `tools/index.ts` 里注册新工具。
- 在 `prompts/system-prompt.ts` 里告诉模型有这个工具可用。

**学到什么**：工具系统的**可扩展性**。加一个工具不需要改 `agent-loop.ts`，只在 `tools/` 加文件 + 注册。这就是模块化的好处。

### 9.14.2 练习 2：加 `TodoWrite` 工具（简单）

**目标**：让 Agent 能维护一个待办列表，跟踪复杂任务的进度。

**提示**：

- 工具接口：`{ todos: Array<{ content: string, status: "pending" | "in_progress" | "completed" }> }`。
- 把 todos 存在 `ContextManager` 里（或单独的 `TodoStore` 类）。
- 每次工具调用后，在终端**渲染**待办列表（用颜色区分状态）。
- 在 system prompt 里告诉模型："处理复杂任务时，先用 TodoWrite 列出步骤，逐步完成"。

**学到什么**：Agent 的**自我管理**能力。TodoWrite 让 Agent 能"规划"而不是"瞎试"，这是真实 Claude Code 的核心工具之一。

### 9.14.3 练习 3：加 `AGENTS.md` 配置继承（中等）

**目标**：读取项目根目录的 `AGENTS.md`，把里面的规则注入 system prompt。

**提示**：

- 在 `prompts/system-prompt.ts` 里，启动时读 `./AGENTS.md`（如果存在）。
- 把内容拼到 system prompt 末尾：`"以下是本项目的额外规则：\n" + agentsMdContent`。
- 进阶：支持**多级继承**，从用户主目录 `~/AGENTS.md`、项目根 `./AGENTS.md`、子目录 `./src/AGENTS.md` 逐级读取，按顺序拼接。
- 再进阶：支持**URL 引用**，`AGENTS.md` 里可以写 `@import url://xxx/rules.md` 拉远程规则。

**学到什么**：**配置继承**是真实 Claude Code 的特色功能。它让团队共享规则（项目级 AGENTS.md）和个人偏好（用户级 AGENTS.md）能叠加。

### 9.14.4 练习 4：加 memory 机制（中等）

**目标**：让 Agent 能跨会话记住用户偏好。

**提示**：

- 在 `tools/` 下加 `memory-write.ts` 和 `memory-read.ts`。
- memory 存在 `~/.miniclaudecode/memory.json`。
- 启动时自动读 memory，注入 system prompt："用户偏好：${memory}"。
- Agent 发现用户偏好后，主动调 `memory-write` 记下来。
- 下次启动自动加载，Agent 就"记住"了。

**学到什么**：**持久化记忆**。大多数 Agent 是"无状态"的，每次启动从零开始。memory 机制让 Agent 有了"个性"。

### 9.14.5 练习 5：加并行子 Agent（中等）

**目标**：让 `Task` 工具能同时启动多个子 Agent。

**提示**：

- 修改 `subagent.ts`，支持 `runSubagents(inputs: string[])`，用 `Promise.all` 并行跑。
- 在内层循环里，如果模型一次返回多个 `Task` 工具调用，并行执行。
- 加一个 `--max-parallel-agents` 参数控制并行度（默认 3，上限 10）。
- 注意：并行子 Agent 的输出不能交错打印，要**缓冲**后一起输出，或加前缀区分。

**学到什么**：**并行执行**。真实 Claude Code 支持最多 10 个并行子 Agent，这是它处理大型任务的关键。并行要处理**输出顺序**、**资源竞争**、**错误隔离**。

### 9.14.6 练习 6：加 MCP 协议支持（困难）

**目标**：支持通过 MCP 协议挂载外部工具服务器。

**提示**：

- 读 [MCP 协议规范](https://modelcontextprotocol.io/)。
- MCP 服务器通过 stdio 或 SSE 通信，启动时握手交换工具列表。
- 在 `tools/` 下加 `mcp-client.ts`，负责连接 MCP 服务器、代理工具调用。
- 在 `config.ts` 里加 `mcpServers` 配置，列出要连接的服务器。
- 启动时遍历 `mcpServers`，连上每个服务器，把它的工具**动态注册**进 `tools/`。

**学到什么**：**工具系统的开放性**。MCP 让 Agent 能接入任意外部工具（数据库查询、内部 API、第三方服务），这是真实 Claude Code 生态的基础。这个练习最难，但也最有价值。
