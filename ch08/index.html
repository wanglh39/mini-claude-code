    第八章：子智能体¶

    Agent 里的 Agent。通过 task 工具 spawn 子 Agent 处理子任务，让父 Agent 保持清爽、让子 Agent 各司其职。

    这是"从零实现 Claude Code"系列的第八章。前七章我们搭出了一个能多轮对话、能调工具、能记忆历史、能压缩上下文、能权限确认的 CLI。但有一个问题一直被我们回避：当任务变复杂时，主 Agent 的上下文会被各种工具调用结果塞爆。模型为了回答"项目里哪些地方处理了错误"，可能要 grep 五次、read 十个文件、再 bash 跑一下测试——这些中间结果全部挤进主 messages 数组，token 用量飙升，模型注意力也被稀释。这一章就来解决这个问题——让主 Agent 能 spawn 一个子 Agent 去干脏活累活，干完只把结论带回来。

    目标¶

    读完这一章，你应该能：

    1. 用一句话说清楚子智能体是什么，并解释"Agent 里的 Agent"这个比喻的精确含义。
    2. 区分子智能体调用和普通函数调用、普通工具调用三者之间的本质差别。
    3. 用"老板派实习生"的类比讲清楚父子 Agent 的分工关系，并指出这个类比的局限。
    4. 深入理解三个核心动机：上下文隔离、工具限制、专注性——并能为每一个举一个没有子智能体就会出问题的具体场景。
    5. 解释为什么子智能体的实现本质就是"一个独立的 agent loop"，以及 subMessages 作为局部变量为什么是上下文隔离的关键。
    6. 复述防递归设计的两个层面：工具集排除 task + 迭代次数上限，并解释少了任何一个会怎样。
    7. 逐行读懂 taskTool 定义、executeTask 函数、SUBAGENT_SYSTEM_PROMPT、maxIterations 限制的每一处细节。
    8. 描述父子 Agent 的通信协议：父通过 tool_use.input.prompt 下发任务、子通过返回文本作为 tool_result.content 回传结果、子的中间过程对父完全不可见。
    9. 说清楚串行 spawn 和并行 spawn 的差别，以及为什么本章选择串行、Claude Code 选择支持并行。
    10. 写出一份子智能体的 system prompt，并解释它和主 Agent system prompt 的三点不同。
    11. 避开五个常见陷阱：递归 spawn、无限循环、上下文泄漏、子 Agent 失败处理、子 Agent 滥用。
    12. 知道自己和真实 Claude Code 的差距在哪：subagent_type 分类、并行 10 个、独立工具集配置、独立 token 预算。
    13. 独立完成三个动手练习：加子 Agent 超时、加子 Agent 失败重试、加并行 spawn。

    一、前置知识：什么是子智能体¶

    1.1 一个直觉性的例子¶

    先不讲概念，看一个具体场景。

    你问主 Agent：

    "帮我看看这个项目里所有处理错误的地方，总结一下错误处理的风格是不是一致的。"

    主 Agent 要完成这个任务，大概得做这些事：

    1. grep "catch" 搜一遍代码           → 返回 50 行匹配
2. grep "throw" 再搜一遍             → 返回 30 行匹配
3. read_file 读第一个 catch 所在文件  → 返回 200 行代码
4. read_file 读第二个 catch 所在文件  → 返回 150 行代码
5. read_file 读第三个 catch 所在文件  → 返回 300 行代码
6. ...（可能还要读 5-10 个文件）
7. 最后综合所有信息，写一个总结

    注意前 6 步的中间结果——50 行匹配、200 行代码、150 行代码——这些全部会进入主 Agent 的 messages 数组。一个文件 200 行代码大约 2000 token，读 10 个文件就是 20000 token，再加上 grep 的输出、工具调用的 JSON 包装，主 Agent 的上下文很容易就被塞进去 30000-50000 token。

    这带来两个问题：

    • token 浪费：这些中间结果在第 7 步总结完之后就没用了，但它们仍然占着上下文，后续每一轮对话都要重新发送给模型，按 token 计费。
    • 注意力稀释：模型在生成第 7 步的总结时，要在一个塞满工具结果的上下文里找到关键信息。上下文越长，模型越容易"看漏"关键细节，这在长上下文模型上是个已知问题，叫 "lost in the middle"。

    子智能体就是来解决这个问题的。主 Agent 不自己 grep 和 read，而是 spawn 一个子 Agent 去做：

    主 Agent: "帮我看看项目里错误处理的风格是不是一致"
  → 主 Agent 调用 task 工具
    → spawn 子 Agent（独立的 messages 数组）
      → 子 Agent 自己 grep "catch"        （结果进子 Agent 的 messages）
      → 子 Agent 自己 grep "throw"        （结果进子 Agent 的 messages）
      → 子 Agent 自己 read_file × 10      （结果进子 Agent 的 messages）
      → 子 Agent 综合信息，写一个总结文本
    ← 子 Agent 把总结文本返回给主 Agent
  ← 主 Agent 收到总结（只有总结文本，没有中间的 grep/read 结果）
  → 主 Agent 把总结呈现给用户

    关键：子 Agent 的 grep 结果、read 结果——那些 50 行匹配、200 行代码——全部留在子 Agent 的 subMessages 里，不进入主 Agent 的 messages。主 Agent 只收到一段总结文本，可能就 500 token。从 50000 token 降到 500 token，上下文干净了 100 倍。

    1.2 子智能体和函数调用的区别¶

    有人会问：这不就是函数调用吗？主 Agent 调一个 analyze_errors 函数，函数返回一个总结。有什么区别？

    区别在函数是写死的，子 Agent 是自主的。

    函数调用：
  主 Agent → 调 analyze_errors() → 程序员写死的逻辑执行 → 返回固定格式结果

子 Agent 调用：
  主 Agent → spawn 子 Agent + 传 prompt → 子 Agent 自己决定怎么搜、搜什么
           → 子 Agent 自己决定读哪些文件、读多少
           → 子 Agent 自己决定什么时候搜完了、怎么总结
           → 返回自由格式文本

    具体对比：

    方面 函数调用 子 Agent
    执行逻辑 程序员写死 模型运行时决定
    能调工具 函数内部调什么由程序员决定 子 Agent 自己决定调哪些工具
    能多轮 函数执行一次就返回 子 Agent 可以多轮工具调用
    输出格式 固定返回类型 自由文本
    适应新情况 要改代码 模型自己适应

    一句话：函数是"程序员预设的一个动作"，子 Agent 是"派出去的另一个员工"。函数你告诉它怎么做；子 Agent 你只告诉它做什么，怎么做它自己想。

    1.3 和并行计算的类比¶

    如果你接触过并行计算，子智能体的结构和 fork/join 模式非常像：

    fork/join 并行计算：
  主线程 → fork 出 N 个子线程 → 各自计算 → join 合并结果 → 主线程继续

子 Agent 编排：
  主 Agent → spawn 出 N 个子 Agent → 各自干活 → 收集结果 → 主 Agent继续

    对应关系：

    • fork ≈ spawn 子 Agent（调用 task 工具）
    • 子线程的计算 ≈ 子 Agent 的 agent loop
    • join ≈ 子 Agent 返回文本，作为 tool_result 回到主 Agent
    • 主线程合并 ≈ 主 Agent 把子 Agent 的结果整合进自己的推理

    但有一个关键区别：本章我们只做串行 spawn——主 Agent 一次只 spawn 一个子 Agent，等它干完再继续。并行 spawn（一次 spawn 多个子 Agent 同时干）要处理结果收集、错误处理、token 预算分配等一堆复杂问题，留到 7 节讨论。

    1.4 为什么不直接在主循环里做¶

    又一个问题：为什么不直接在主 Agent 的循环里加一个"探索模式"——让主 Agent 先探索，探索完把探索结果压缩一下，再继续？为什么要 spawn 一个新的 Agent？

    三个原因：

    1. system prompt 不同：主 Agent 的 system prompt 是"你是用户的代码助手"，要对用户负责、要问权限、要解释。子 Agent 的 system prompt 是"你负责完成分配的子任务，专注、不要偏离"——不需要对用户负责，不需要问权限（权限由主 Agent 把关），只需要高效完成。同一个 system prompt 干不了这两件事。

    2. 工具集不同：主 Agent 有 write_file、bash 这些能改东西的工具。子 Agent 如果只是去"探索项目结构"，它只需要 read_file、glob、grep 这些只读工具——给子 Agent write_file 就是给它犯错误的机会。工具集是按子 Agent 的职责定制的，不是按主 Agent 的。

    3. 迭代限制不同：主 Agent 的循环可能跑几十轮、上百轮（用户一直对话）。子 Agent 干一个子任务，20 轮够了。给子 Agent 一个独立的、更紧的迭代上限，能防止子 Agent 跑飞了拖垮整个会话。

    一句话：子 Agent 不是"主 Agent 的一个模式"，它是一个有独立配置的独立 Agent。spawn 的本质是创建一个新的、配置不同的 Agent 实例。

    二、三个核心原因深入¶

    2.1 上下文隔离¶

    这是子智能体最重要的价值。让我们看一个没有上下文隔离会出问题的具体场景。

    假设用户连续问了三个问题：

    Q1: "项目里哪些地方处理了错误？"
Q2: "帮我看看 package.json 里有哪些依赖？"
Q3: "把刚才说的错误处理的地方，都加上日志。"

    没有子 Agent：主 Agent 处理 Q1 时，grep 和 read 的结果全进 messages。处理 Q2 时，read package.json 的结果也进 messages。到 Q3 时，messages 里塞满了 Q1 的 50 行 grep 输出、10 个文件的代码、Q2 的 package.json 内容——主 Agent 要在这个大杂烩里找到"刚才说的错误处理的地方"是什么。

    有子 Agent：主 Agent 处理 Q1 时，spawn 子 Agent 去搜，子 Agent 返回一个总结："错误处理在 5 个文件里，风格是用 try-catch，没有统一日志。"这个总结进 messages。处理 Q2 时，read package.json 的结果进 messages。到 Q3 时，messages 里是：Q1 的总结（500 token）+ Q2 的 package.json（500 token）——干净、紧凑，主 Agent 很容易找到"刚才说的错误处理的地方"。

    上下文隔离的精确表述：

    主 Agent 的 messages:  [user Q1, assistant 调 task, tool_result=总结, user Q2, ...]
子 Agent 的 messages:  [user prompt, assistant 调 grep, tool_result=50行, 
                         assistant 调 read, tool_result=200行, ...]

    子 Agent 的 messages 是 executeTask 函数里的局部变量，函数返回后就被垃圾回收了。那些 50 行、200 行的中间结果物理上不存在了，不可能污染主 Agent。

    反例：如果不隔离会怎样：

    // 错误示范：把子任务的结果直接塞进主 messages
async function badExecuteTask(input, mainMessages) {
  mainMessages.push({ role: "user", content: input.prompt });
  // ... 子 Agent 跑了很多轮，结果都 push 进 mainMessages
  // 主 Agent 的上下文被污染了！
}

    这就是为什么 subMessages 必须是局部变量，不能是主 messages 的引用。隔离的本质是变量作用域。

    2.2 工具限制¶

    子 Agent 的工具集是主 Agent 工具集的子集，具体取哪些工具取决于子 Agent 的职责。

    看几个场景：

    场景 A：探索型子 Agent

    任务: "找出项目里所有处理错误的地方"
工具集: { read_file, glob, grep }        ← 只读，不能改
排除:   { write_file, edit_file, bash, task }

    这个子 Agent 只需要看，不需要改。给它 write_file 没用（它不该改任何东西），给它 bash 危险（它可能误执行命令），给它 task 会递归（见 4 节）。

    场景 B：审查型子 Agent

    任务: "审查这个 PR 的代码质量"
工具集: { read_file, glob, grep }        ← 只读
排除:   { write_file, edit_file, bash, task }

    审查也是只读的。审查 Agent 不应该改代码——它只负责看和评价，改代码是主 Agent 或用户的事。

    场景 C：实现型子 Agent

    任务: "实现这个函数，写到 src/foo.ts"
工具集: { read_file, write_file, edit_file, glob, grep }  ← 能读能写
排除:   { bash, task }                                        ← 不能执行命令

    这个子 Agent 要写代码，所以有 write_file。但不需要 bash——它不该执行命令，执行命令是主 Agent 的事。

    工具限制的价值：

    1. 安全：只读子 Agent 不可能误改文件。即使它的模型抽风了想 write_file，工具集里没这个工具，它调不了。
    2. 聚焦：工具集本身就是一种"职责描述"。给子 Agent {read, glob, grep} 就是在告诉它"你的职责是看，不是改"。
    3. 防递归：排除 task 工具是工具限制的一个重要特例，下一节专门讲。

    本章的实现：本章只有一个通用的子 Agent，工具集是"所有工具减去 task"：

    const subTools = tools.filter(t => t.name !== "task");

    真实 Claude Code 会按 subagent_type 配置不同工具集，10 节细讲。

    2.3 专注性¶

    子 Agent 有自己的 system prompt，和主 Agent 的不同。

    主 Agent 的 system prompt（简化）：

    你是一个代码助手，帮助用户完成软件工程任务。
- 读取单个文件用 read_file，搜索代码用 grep
- 修改文件优先用 edit_file
- 不执行 rm -rf 等破坏性命令
- 工作目录: /home/user/project
- ...

    主 Agent 要对用户负责：要解释自己在干什么、要问权限、要遵守用户的工作目录约束、要遵循用户的代码风格。

    子 Agent 的 system prompt（简化）：

    你是一个子智能体，负责完成父智能体分配的特定任务。
- 专注于完成分配的任务，不要偏离主题
- 使用提供的工具完成任务
- 完成后用简洁的语言总结结果
- 不要执行破坏性操作

    子 Agent 要对父 Agent 负责：要专注、要高效、要返回简洁的总结。它不需要问权限（权限由主 Agent 在 spawn 前把关），不需要解释自己在干什么（它的中间过程对父 Agent 不可见），不需要遵守用户的工作目录约束（它继承主 Agent 的工作目录）。

    专注性带来的行为差异：

    • 主 Agent 被问"项目里有哪些错误处理"，它可能先解释"我来帮你搜一下"，然后 grep，然后解释"我找到了这些"，然后 read，然后解释"我来看看这些文件"——很多"对用户的解释"。
    • 子 Agent 被分配同样的任务，它直接 grep、read、总结，没有解释——因为它的受众是父 Agent，父 Agent 只关心结论，不关心过程。

    一句话：不同的 system prompt 让子 Agent 行为模式不同于主 Agent——更直接、更高效、更聚焦。

    三、实现本质：子智能体就是独立的 agent loop¶

    3.1 回顾主 Agent 的循环¶

    先回忆一下主 Agent 的核心循环（从第一章到现在，这个循环一直在）：

    while (true) {
  const response = await client.messages.create({
    system: systemPrompt,
    messages: messages,        // ← 主 Agent 的 messages
    tools: allTools,           // ← 主 Agent 的工具集
  });

  messages.push({ role: "assistant", content: response.content });

  if (response.stop_reason === "tool_use") {
    // 执行工具，结果 push 进 messages
  } else {
    // 模型不再调工具，本轮结束
    break;
  }
}

    这个循环做了三件事：(1) 调模型，(2) 如果模型要调工具就调工具，(3) 如果模型不调工具了就结束。

    3.2 子 Agent 的循环：几乎一模一样¶

    子 Agent 的循环：

    async function executeTask(input) {
  const subMessages = [{ role: "user", content: input.prompt }];

  while (true) {  // ← 独立的内层循环
    const response = await client.messages.create({
      system: SUBAGENT_SYSTEM_PROMPT,   // ← 独立 system prompt
      messages: subMessages,             // ← 独立 messages
      tools: subTools,                   // ← 独立工具集
    });

    subMessages.push({ role: "assistant", content: response.content });

    if (response.stop_reason === "tool_use") {
      // 执行工具，结果 push 进 subMessages
    } else {
      return extractText(response);  // ← 返回最终文本
    }
  }
}

    结构完全一样：调模型 → 调工具 → 结束。差别只在三个"独立"：

    1. subMessages 是局部变量，和主 messages 互不影响。
    2. SUBAGENT_SYSTEM_PROMPT 是子 Agent 专属的，不是主 Agent 的 systemPrompt。
    3. subTools 排除了 task，和主 Agent 的 allTools 不同。

    这就是子智能体的全部秘密。没有什么魔法，没有什么特殊的 API，就是"用不同的参数跑同一个循环"。如果你把主 Agent 的循环代码复制一份，改三个参数，你就得到了一个子 Agent。

    3.3 为什么"独立 messages"是隔离的关键¶

    看一个对比，理解 subMessages 作为局部变量的意义。

    错误做法：共享 messages

    async function badExecuteTask(input, messages) {  // ← 传入主 messages
  messages.push({ role: "user", content: input.prompt });

  while (true) {
    const response = await client.messages.create({
      system: SUBAGENT_SYSTEM_PROMPT,
      messages: messages,  // ← 用的是主 messages！
      tools: subTools,
    });
    messages.push({ role: "assistant", content: response.content });
    // ...
  }
}

    这能跑，但子 Agent 的所有工具调用结果都进了主 messages。子 Agent grep 了 50 行，这 50 行就出现在主 Agent 的上下文里——隔离彻底失败。

    正确做法：局部 messages

    async function executeTask(input) {
  const subMessages = [{ role: "user", content: input.prompt }];  // ← 局部变量

  while (true) {
    const response = await client.messages.create({
      system: SUBAGENT_SYSTEM_PROMPT,
      messages: subMessages,  // ← 局部变量
      tools: subTools,
    });
    subMessages.push({ role: "assistant", content: response.content });
    // ...
  }
  // 函数返回，subMessages 超出作用域，被垃圾回收
}

    subMessages 是 executeTask 的局部变量，主 Agent 根本拿不到它的引用。子 Agent 往里塞多少东西，主 Agent 都看不见。函数返回后，subMessages 超出作用域，被垃圾回收——那些中间结果物理上消失了。

    一句话：上下文隔离不是靠什么特殊的"隔离 API"，就是靠变量作用域——JavaScript 最基础的机制。

    3.4 子 Agent 的结束条件¶

    子 Agent 的循环什么时候结束？两种情况：

    1. 正常结束：模型的 stop_reason 不是 "tool_use"，意味着模型不再调工具了，准备输出最终文本。这时提取文本，return。

    2. 强制结束：循环跑到了 maxIterations（20 次），强制 return 一个"达到最大迭代次数"的消息。

    while (iteration < maxIterations) {  // ← 强制结束条件
  iteration++;
  const response = await client.messages.create({ ... });

  if (response.stop_reason === "tool_use") {
    // 继续循环
  } else {
    return extractText(response);  // ← 正常结束
  }
}

return `子智能体达到最大迭代次数 (${maxIterations})，强制终止`;  // ← 强制结束

    为什么需要强制结束：模型可能陷入循环——grep 搜不到东西，换个关键词再 grep，还是搜不到，再换……理论上可以无限循环下去。maxIterations 是一个安全网，防止子 Agent 跑飞了。

    20 次是怎么定的？经验值。大多数子任务（搜个东西、读几个文件、总结一下）10 轮以内能搞定。给 20 是留点余量。真实 Claude Code 用的是 token 预算限制，更精细，10 节细讲。

    四、防递归设计¶

    4.1 如果不排除 task 工具¶

    假设我们给子 Agent 的工具集包含了 task：

    const subTools = tools;  // ← 错误！没有排除 task

    会发生什么？子 Agent 在执行任务时，可以再 spawn 一个子子 Agent：

    主 Agent → spawn 子 Agent A
  子 Agent A → spawn 子子 Agent B
    子子 Agent B → spawn 子子子 Agent C
      子子子 Agent C → spawn ...
        → 无限递归，栈溢出，程序崩

    这不是理论上的风险，是实际会发生的事。模型的 system prompt 里说"用提供的工具完成任务"，如果工具集里有 task，模型在遇到复杂子任务时完全可能选择 spawn 一个子子 Agent 来处理——这看起来是合理的工具使用，但会导致无限递归。

    4.2 工具集排除 task¶

    防递归的第一道防线：

    const subTools = tools.filter(t => t.name !== "task");

    子 Agent 的工具集里没有 task，它根本看不到这个工具，自然不会调。这是最简单、最可靠的防递归方式——不是"告诉模型不要调 task"，而是"工具集里就没 task"。

    为什么这比在 system prompt 里说"不要 spawn 子 Agent"更可靠：

    • 在 system prompt 里说"不要 spawn"，模型可能遵守，也可能不遵守——system prompt 是建议，不是强制。
    • 工具集里没有 task，模型物理上调不了——这是强制。

    防递归靠的是结构上的不可能，不是模型的自制力。

    4.3 迭代次数上限：第二道防线¶

    即使排除了 task，子 Agent 仍然可能自己陷入循环（4.3 节提到的 grep 关键词循环）。所以需要第二道防线：

    let iteration = 0;
const maxIterations = 20;

while (iteration < maxIterations) {
  iteration++;
  // ...
}

return `子智能体达到最大迭代次数 (${maxIterations})，强制终止`;

    两道防线缺一不可：

    • 没有工具排除、只有迭代上限：子 Agent spawn 子子 Agent，每个子 Agent 跑 20 轮，2 层就是 400 轮，3 层 8000 轮——指数爆炸，实际效果等于无限。
    • 有工具排除、没有迭代上限：子 Agent 不会递归了，但自己可能 grep 循环，永远不结束。

    完整的防递归 = 工具排除 + 迭代上限。

    4.4 真实 Claude Code 怎么防递归¶

    真实 Claude Code 的做法更精细：

    1. 工具集按 subagent_type 配置，每种类型的工具集都不含 task——和本章一样。
    2. 每个子 Agent 有独立的 token 预算（不只是迭代次数），token 用完就强制结束。
    3. 子 Agent 的 spawn 深度有限制——即使工具集配置错了包含了 task，spawn 深度超过某个值也会被拒绝。

    本章只做了第 1 点和迭代上限，第 3 点没做。在练习里会让你补上。

    5.1 taskTool 定义¶

    export const taskTool: Tool = {
  name: "task",
  description:
    "启动一个子智能体来处理子任务。子智能体有独立的上下文，不会污染主对话。适用于需要多步骤探索的复杂子任务。",

        type: "string",
        description: "给子智能体的详细任务指令",
      },
    },
    required: ["description", "prompt"],
  },

    逐行解读：

    • name: "task"：工具名。主 Agent 的工具列表里会有这个工具，模型看到它就知道可以 spawn 子 Agent。
    • description：工具描述。这是模型决定"要不要调这个工具"的关键依据。描述里明确说了"独立的上下文，不会污染主对话"——这是在引导模型在合适的场景调用这个工具（任务复杂、需要多步探索时）。
    • input_schema：工具的输入参数 schema，告诉模型调这个工具要传什么。
    • description：子任务的简短描述，3-5 个词。这个字段不传给子 Agent，只用于日志输出，让用户知道子 Agent 在干什么。
    • prompt：给子 Agent 的详细任务指令。这个字段直接成为子 Agent 的第一条 user message。
    • required: ["description", "prompt"]：两个字段都必须传。

    为什么分 description 和 prompt 两个字段：

    • description 是给人看的（日志里显示 [子智能体启动] 搜索错误处理代码）。
    • prompt 是给子 Agent 看的（子 Agent 的第一条 message）。

    如果只有一个字段，日志里要么显示一长串 prompt（太长），要么显示截断的 prompt（信息不够）。分两个字段，description 短而精，专门给日志用。

    对比真实 Claude Code 的 Task 工具：

    真实 Claude Code 的 Task 工具有更多参数：subagent_type（指定子 Agent 类型）、task_id（用于恢复之前的子 Agent 会话）等。本章简化了，只有 description 和 prompt。

    5.2 executeTask 函数签名¶

    export async function executeTask(
  client: Anthropic,
  model: string,
  maxTokens: number,
  input: { description: string; prompt: string },
  perm: PermissionManager

    参数解读：

    • client: Anthropic：API 客户端。和主 Agent 用同一个 client——同一个 API key、同一个 base URL。子 Agent 不是另起一个 API 连接，只是用同一个连接发不同的请求。
    • model: string：模型名。和主 Agent 用同一个模型。真实 Claude Code 不同类型的子 Agent 可能用不同模型（比如简单任务用小模型省钱），本章简化了。
    • maxTokens: number：单次响应的最大 token。和主 Agent 用同一个值。
    • input：来自 taskTool 的输入，包含 description 和 prompt。
    • perm: PermissionManager：权限管理器。和主 Agent 共享同一个 perm——子 Agent 调工具时也走权限确认。这很重要：如果子 Agent 要 write_file，用户应该有机会确认。

    5.3 subMessages 初始化¶

    第一行：日志。用户看到 [子智能体启动] 搜索错误处理代码，知道一个子 Agent 启动了。description 用于此。

    第二行：创建 subMessages——子 Agent 的 messages 数组。这是上下文隔离的关键：subMessages 是 executeTask 的局部变量，主 Agent 拿不到它的引用。

    第三行：子 Agent 的第一条 message 是 user 角色，内容是 input.prompt——主 Agent 下发的任务指令。子 Agent 不知道主 Agent 的对话历史，它的"世界"从这条 prompt 开始。

    对比主 Agent 的 messages 初始化：

    结构一样，只是内容的来源不同：主 Agent 的内容来自用户输入，子 Agent 的内容来自主 Agent 的 tool_use.input.prompt。

    5.4 subTools 过滤¶

    const subTools = tools.filter(
  (t) => t.name !== "task"
);

    从所有工具里过滤掉 task，得到子 Agent 的工具集。这是防递归的核心——4 节已详述。

    注意这里过滤的是 tools（从 ./tools/index.js 导入的 6 个基础工具），不是 allTools（主 Agent 的 7 个工具，包含 taskTool）。所以即使不过滤，tools 里本来就没有 task——这行代码是双保险。

    为什么说是双保险？因为 tools 是基础工具列表，taskTool 是单独定义并加到 allTools 里的：

    // tools/index.ts

  readTool, writeTool, editTool, bashTool, globTool, grepTool,
];  // ← 6 个，没有 taskTool

// main.ts
const allTools = [...tools, taskTool];  // ← 7 个，有 taskTool

    subagent.ts 导入的是 tools（6 个），不是 allTools（7 个）。所以 subTools 本来就不含 task。filter 那行是防御性编程——如果以后有人改了 tools/index.ts 把 taskTool 加进去，这行 filter 还能兜住。

    5.5 maxIterations 限制¶

    let iteration = 0;
const maxIterations = 20;

    迭代计数器和上限。20 是经验值，大多数子任务 10 轮内完成，给 20 留余量。

    为什么不用 while(true) 而用 while(iteration < maxIterations)：

    主 Agent 的循环是 while (true)——它靠用户的 "exit" 退出，不靠迭代上限。子 Agent 没有用户交互，如果模型陷入循环，while(true) 会永远跑下去。maxIterations 是子 Agent 的"紧急出口"。

    强制终止时的返回：

    return `子智能体达到最大迭代次数 (${maxIterations})，强制终止`;

    返回一个说明性文本，主 Agent 会看到这个 tool_result，知道子 Agent 没正常完成。主 Agent 可以决定：换个方式重试、告诉用户子任务失败、或者忽略。

    5.6 循环主体¶

  iteration++;

  try {
    const response = await client.messages.create({
      model,
      max_tokens: maxTokens,
      system: SUBAGENT_SYSTEM_PROMPT,
      messages: subMessages,
      tools: subTools,

    逐行解读：

    • while (iteration < maxIterations)：带迭代上限的循环。
    • iteration++：计数。
    • try { ... } catch (err) { return ... }：try-catch 包住整个循环体。如果 API 调用失败（网络错误、rate limit 等），返回错误信息，不让异常冒到主 Agent。
    • client.messages.create({ ... })：调模型。注意这里用的是 create，不是 stream——子 Agent 不流式输出。为什么？因为子 Agent 的输出是给主 Agent 看的，不是给用户看的。用户看到的是主 Agent 的流式输出。子 Agent 的输出要等它完全生成后，作为 tool_result 一次性返回。流式没有意义。
    • system: SUBAGENT_SYSTEM_PROMPT：子 Agent 专属的 system prompt，8 节细讲。
    • messages: subMessages：局部变量，上下文隔离的关键。
    • tools: subTools：排除了 task 的工具集。

    • if (response.stop_reason === "tool_use")：模型要调工具。
    • for (const block of response.content)：遍历响应里的所有 block（可能有多个 tool_use）。
    • console.log(\ [子工具] ${block.name}`)：日志。注意缩进比[子智能体启动]` 多一层——视觉上表示这是子 Agent 内部的工具调用。

    • if (!allowed)：用户拒绝。返回 "[用户拒绝了此操作]" 作为 tool_result——和主 Agent 的处理一样，优雅降级。

    • subMessages.push({ role: "user", content: toolResults })：工具结果加到 subMessages。

    这段和主 Agent 的工具处理几乎完全一样。差别只在：日志多一层缩进、messages 是局部的。这就是"子 Agent 就是独立 agent loop"的具体体现——工具处理逻辑都一样，只是跑在不同的 messages 上。

}

return `子智能体达到最大迭代次数 (${maxIterations})，强制终止`;

    try-catch：API 调用失败时，返回错误信息，不抛异常。为什么 return 而不是 throw？因为如果 throw，异常会冒到主 Agent，主 Agent 的循环可能因此崩掉。return 一个错误字符串，主 Agent 收到后可以决定怎么处理——重试、告诉用户、或者换个方式做。

    最后的 return：循环正常退出（iteration 达到 maxIterations）时执行。返回一个"强制终止"的说明。这个 return 在循环外面，只有 while 条件不满足时才会执行——也就是迭代超限。

    5.10 main.ts 的变化¶

    主 Agent 的 main.ts 只改了两处：

    第一处：工具列表加入 taskTool

    import { taskTool, executeTask } from "./subagent.js";
// ...
const allTools = [...tools, taskTool];  // ← 7 个工具

    主 Agent 的工具列表从 6 个变成 7 个，多了 task。模型现在能看到并调用 task 工具。

    第二处：工具执行时特殊处理 task

    if (block.name === "task") {
  const result = await executeTask(
    client,
    model,
    maxTokens,
    block.input,
    perm
  );
  console.log(`  [子智能体结果] ${result.slice(0, 200)}...`);
  toolResults.push({
    type: "tool_result",
    tool_use_id: block.id,
    content: result,  // ← 子 Agent 的最终文本
  });
  continue;
}

    主 Agent 调 task 工具时，不走普通的 executeTool，而是走 executeTask——spawn 一个子 Agent。子 Agent 返回的文本作为 tool_result.content 加到主 Agent 的 messages。

    注意 continue：跳过后面的普通工具执行逻辑。task 是特殊工具，不走普通路径。

    除了这两处，main.ts 没有任何变化。子智能体的加入对主循环的改动极小——这是设计良好的体现：新功能是"正交"的，不侵入现有逻辑。

    六、父子 Agent 的通信¶

    6.1 通信协议全貌¶

    父子 Agent 的通信可以用一张图说清楚：

    父 Agent 的 messages:                          子 Agent 的 subMessages:
[...,                                          [
  { role: "assistant",                           { role: "user",
    content: [                                     content: "找出所有错误处理"  ← 父下发的 prompt
      { type: "tool_use",                       }  ← 子 Agent 的第一条 message
        id: "toolu_xxx",
        name: "task",
        input: {
          description: "搜索错误处理",
          prompt: "找出所有错误处理"  ────────→  （成为子 Agent 的第一条 user message）
        }
      }
    ]
  },
                                                { role: "assistant",
                                                  content: [{ type: "tool_use", name: "grep", ... }]
                                                },
                                                { role: "user",
                                                  content: [{ type: "tool_result", content: "50行匹配" }]
                                                },
                                                ... （子 Agent 的多轮工具调用，父 Agent 看不见）
                                                { role: "assistant",
                                                  content: [{ type: "text", text: "错误处理在5个文件..." }]
                                                }  ← 子 Agent 的最终文本
  { role: "user",
    content: [                                    
      { type: "tool_result",          ←────────  （子 Agent 的最终文本作为 tool_result）

      }
    ]
  },
  ... （父 Agent 继续推理）

    6.2 父通过 tool_use 传 prompt¶

    父 Agent 通信出来的方式：在 tool_use 的 input.prompt 字段里写下任务指令。

    {
  type: "tool_use",
  name: "task",
  input: {
    description: "搜索错误处理代码",
    prompt: "在项目里找出所有处理错误的代码，总结错误处理的风格。"  // ← 这就是下发的任务
  }
}

    prompt 字段的内容由模型生成——模型决定给子 Agent 什么指令。模型要根据用户的请求，把任务"分解"出一个合适的子任务，写成一段清晰的指令。

    什么是一个好的 prompt：

    • 清晰：明确说清要子 Agent 做什么。"找出所有处理错误的代码"比"看看错误"好。
    • 有边界：说清范围和结束条件。"找出所有"比"找一些"好——子 Agent 知道什么时候搜完了。
    • 不要太长：prompt 会占子 Agent 的上下文，太长浪费 token。

    什么是一个坏的 prompt：

    • 模糊："看看这个项目"——子 Agent 不知道看什么、看到什么程度。
    • 太大："理解整个代码库"——这不是一个子任务，这是一个项目。子 Agent 20 轮干不完。
    • 和主 Agent 的任务完全一样："帮我分析项目"——如果子 Agent 做的事和主 Agent 一样，为什么要 spawn 子 Agent？

    6.3 子通过返回文本作为 tool_result¶

    子 Agent 通信回来的方式：executeTask 的返回值，作为 tool_result.content 加到父 Agent 的 messages。

    // 子 Agent 返回
return "错误处理在 5 个文件里，风格是用 try-catch，没有统一日志。";

// 父 Agent 收到
toolResults.push({
  type: "tool_result",
  tool_use_id: block.id,
  content: "错误处理在 5 个文件里，风格是用 try-catch，没有统一日志。",
});

    父 Agent 在下一轮推理时，会看到这个 tool_result，知道子 Agent 的结论。

    子 Agent 应该返回什么：

    • 结论，不是过程：返回"错误处理在 5 个文件里，风格是 try-catch"，不返回"我先 grep 了 catch，找到 50 行，然后我 read 了第一个文件，发现……"——父 Agent 不关心过程。
    • 简洁：总结性的一段话，不是一篇论文。父 Agent 还要继续推理，太长的返回浪费上下文。
    • 可操作：返回的信息要能让父 Agent 继续工作。"错误处理在 5 个文件里"比"我搜了一下"有用——父 Agent 可以接着说"那帮它们都加上日志"。

    6.4 子的中间过程对父不可见¶

    这是通信协议最重要的一点：子 Agent 的中间工具调用、中间结果，父 Agent 完全看不见。

    子 Agent 的 subMessages 里有：
  - grep 的 50 行输出
  - read 的 200 行代码
  - read 的 150 行代码
  - ... 10 个文件的内容

父 Agent 的 messages 里只有：
  - tool_result: "错误处理在 5 个文件里，风格是 try-catch"

    那 50 行、200 行、150 行——父 Agent 不知道它们存在过。这是上下文隔离的体现，也是子 Agent 的价值所在。

    好处：父 Agent 的上下文干净，注意力集中。

    坏处：如果子 Agent 的结论有问题，父 Agent 很难调试——它不知道子 Agent 中间做了什么。这是子 Agent 的代价：可调试性下降。

    怎么缓解：日志。subagent.ts 里的 console.log 就是干这个的：

    console.log(`\n  [子智能体启动] ${input.description}`);
// ...
console.log(`    [子工具] ${block.name}`);
// ...
console.log(`  [子智能体完成] ${input.description}`);

    用户看日志能知道子 Agent 干了什么（启动了、调了哪些工具、完成了），虽然看不到工具的具体结果。这是在"上下文隔离"和"可观测性"之间的折中。

    七、串行 vs 并行¶

    7.1 本章的串行 spawn¶

    本章的 executeTask 是串行的：主 Agent 一次只 spawn 一个子 Agent，等它干完再继续。

    主 Agent → spawn 子 Agent A → 等 A 完成 → 收到 A 的结果 → 继续推理

    主 Agent 的循环里，调 task 工具是一个 await：

    const result = await executeTask(client, model, maxTokens, block.input, perm);
// ← 主 Agent 在这里等，直到子 Agent 返回

    await 会阻塞主 Agent 的循环，直到 executeTask 返回。主 Agent 不能同时 spawn 多个子 Agent。

    7.2 串行的限制¶

    串行在某些场景下效率低。看这个例子：

    用户问："帮我看看 src/、tests/、docs/ 三个目录的代码风格是不是一致。"

    串行做法：

    主 Agent → spawn 子 Agent A 分析 src/    （10 秒）
         → 等 A 完成
         → spawn 子 Agent B 分析 tests/   （10 秒）
         → 等 B 完成
         → spawn 子 Agent C 分析 docs/    （10 秒）
         → 等 C 完成
         → 综合三个结果
总时间: 30 秒

    三个子 Agent 干的是独立的事——分析 src/ 不依赖 tests/ 的结果。串行让它们一个一个干，浪费了 20 秒。

    并行做法：

    主 Agent → 同时 spawn A、B、C
         → 三个子 Agent 同时干
         → 三个都完成
         → 综合三个结果
总时间: 10 秒

    并行把 30 秒压到 10 秒。

    7.3 并行需要什么¶

    并行 spawn 需要几个东西：

    1. 同时发起多个 executeTask

    // 串行
const resultA = await executeTask(taskA);
const resultB = await executeTask(taskB);
const resultC = await executeTask(taskC);

// 并行
const [resultA, resultB, resultC] = await Promise.all([
  executeTask(taskA),
  executeTask(taskB),
  executeTask(taskC),
]);

    用 Promise.all 同时发起多个 executeTask，等它们全部完成。

    2. 主 Agent 一次生成多个 task tool_use

    串行时，主 Agent 的响应里只有一个 tool_use（调一次 task），等结果回来再决定是否调下一个。并行时，主 Agent 的响应里要有多个 tool_use（同时调多个 task）——这需要模型支持在单个响应里输出多个 tool_use。Claude 模型支持这个，但需要在 prompt 里引导模型"你可以同时 spawn 多个子 Agent"。

    3. 结果收集和错误处理

    const results = await Promise.allSettled([
  executeTask(taskA),
  executeTask(taskB),
  executeTask(taskC),
]);

for (const r of results) {
  if (r.status === "fulfilled") {
    // r.value 是子 Agent 的返回文本
  } else {
    // r.reason 是错误
  }
}

    Promise.allSettled 而不是 Promise.all——Promise.all 只要有一个失败就全失败，allSettled 允许部分失败。子 Agent 可能个别失败，不应该拖垮全部。

    4. token 预算分配

    并行 spawn N 个子 Agent，每个子 Agent 都在调 API，token 消耗是 N 倍。需要有预算机制防止单次并行 spawn 烧太多 token。

    7.4 为什么本章用串行¶

    三个原因：

    1. 简单：串行的代码简单，一个 await 搞定。并行要处理 Promise.allSettled、结果顺序、部分失败、token 预算——复杂度陡增。教学上先讲串行，把"子 Agent 是独立 agent loop"这个核心概念讲透，再讲并行。

    2. 大多数场景串行够用：用户问"分析项目错误处理"，spawn 一个子 Agent 就够了。需要并行的场景（同时分析多个目录、同时审查多个 PR）是少数。

    3. 并行引入的新问题需要单独章节：并行 spawn 涉及结果收集、错误处理、token 预算、spawn 数量限制、模型引导（让模型一次输出多个 tool_use）——每一个都值得单独讨论。本章聚焦"子 Agent 是什么"，不分散注意力。

    7.5 Claude Code 怎么做的¶

    真实 Claude Code 支持并行 spawn，最多同时 10 个：

    主 Agent → 同时 spawn 最多 10 个子 Agent
         → 10 个子 Agent 并行干
         → 结果按完成顺序收集
         → 全部完成（或达到超时）后继续

    具体实现：

    • 模型在一个响应里输出多个 tool_use（最多 10 个 task 调用）。
    • 主循环用 Promise.allSettled 同时执行所有 executeTask。
    • 每个子 Agent 有独立的 token 预算，总 token 消耗有上限。
    • 有超时机制，单个子 Agent 超时不影响其他。

    本章的串行 spawn 是 Claude Code 并行 spawn 的"退化版"（并行数 = 1）。理解了串行，并行只是"把 await 换成 Promise.all"——核心概念（独立 messages、工具排除、迭代上限）都一样。

    八、子智能体的 system prompt 设计¶

    8.1 子 Agent 的 system prompt¶

    const SUBAGENT_SYSTEM_PROMPT = `你是一个子智能体，负责完成父智能体分配的特定任务。

## 规则
- 专注于完成分配的任务，不要偏离主题
- 使用提供的工具完成任务
- 完成后用简洁的语言总结结果
- 不要执行破坏性操作`;

    四条规则，逐条解释：

    "专注于完成分配的任务，不要偏离主题"

    子 Agent 的任务来自父 Agent 的 prompt，不是来自用户的自由对话。子 Agent 不应该"发散"——看到错误处理的代码，顺便评价一下命名规范，再建议一下性能优化……不。父 Agent 让你干什么就干什么，干完返回。

    为什么这条重要？因为子 Agent 有迭代上限（20 轮），每一轮都很宝贵。偏离主题浪费迭代，可能导致子 Agent 在 20 轮内没干完正事。

    "使用提供的工具完成任务"

    提醒子 Agent 它有工具。这听起来多余（模型当然知道有工具），但实际上模型有时会"忘记"用工具，直接用文本回答。比如被问"项目里有哪些 TypeScript 文件"，模型可能直接猜一个答案，而不是去 glob。这条提醒促使模型用工具。

    "完成后用简洁的语言总结结果"

    这是对返回格式的约束。子 Agent 的返回是给父 Agent 看的，要简洁、要结论、不要过程。"简洁"防止子 Agent 返回一篇长文浪费父 Agent 的上下文。

    "不要执行破坏性操作"

    安全约束。虽然权限系统会拦截危险操作，但 system prompt 里也说一句——双保险。而且权限系统只拦"危险命令"，不拦"不危险但不合适"的操作（比如子 Agent 在探索时 write_file 写了个临时文件——不危险，但不该做）。

    8.2 和主 Agent system prompt 的对比¶

    主 Agent 的 system prompt（简化）：

    你是一个代码助手，帮助用户完成软件工程任务。

## 工具使用规则
- 读取单个文件用 read_file，搜索代码用 grep
- 修改文件优先用 edit_file
- 执行命令前思考是否必要

## 代码风格
- 不添加多余注释
- 遵循项目现有代码风格

## 安全约束
- 不执行 rm -rf
- 不修改 .git

## 环境信息
- 工作目录: /home/user/project
- ...

    子 Agent 的 system prompt：

    你是一个子智能体，负责完成父智能体分配的特定任务。

## 规则
- 专注于完成分配的任务
- 使用提供的工具
- 完成后简洁总结
- 不要执行破坏性操作

    三点不同：

    1. 身份不同

    • 主 Agent："你是用户的代码助手"——对用户负责。
    • 子 Agent："你是子智能体"——对父 Agent 负责。

    身份决定行为：主 Agent 会解释、会问权限、会等待用户确认；子 Agent 不解释、不问权限（权限由主 Agent 把关）、直接干。

    2. 工具使用指导不同

    • 主 Agent：详细指导每个工具怎么用（"读取用 read_file，搜索用 grep"）。
    • 子 Agent：只说"使用提供的工具"。

    为什么子 Agent 的指导这么粗？因为子 Agent 的工具集是按职责定制的——探索型子 Agent 只有 {read, glob, grep}，它不需要被告知"修改用 edit_file"，它根本没有 edit_file。工具集本身就是指导。

    3. 环境信息不同

    • 主 Agent：包含工作目录、项目名称、操作系统、Git 信息等。
    • 子 Agent：没有环境信息。

    为什么子 Agent 不要环境信息？因为子 Agent 继承主 Agent 的工作目录（process.cwd() 是进程级的，子 Agent 自动继承）。而且子 Agent 的任务通常不涉及"了解项目背景"——父 Agent 已经了解背景，把具体任务下发给子 Agent，子 Agent 只管执行。

    8.3 不同类型子 Agent 的 system prompt¶

    真实 Claude Code 有多种 subagent_type，每种有不同的 system prompt。举几个例子：

    探索型（explore）：

    你是一个探索型子智能体。你的职责是快速搜索代码、回答关于代码库的问题。
- 优先用 glob 和 grep，少用 read_file（read 慢且占上下文）
- 找到答案就返回，不要深入
- 返回时给出文件路径和行号

    代码审查型（code-reviewer）：

    你是一个代码审查型子智能体。你的职责是审查代码质量。
- 关注：可读性、正确性、安全性、性能
- 指出问题时给出具体位置和修改建议
- 不要自己改代码，只指出问题

    通用型（general）：

    你是一个通用子智能体。完成父智能体分配的任务。
- 可以执行多步骤任务
- 完成后总结结果

    每种 system prompt 都针对子 Agent 的职责定制——探索型强调"快"，审查型强调"指出问题不改代码"，通用型强调"多步骤"。

    本章只有一个通用子 Agent，system prompt 是通用的。在练习里会让你加 subagent_type 支持。

    九、常见陷阱¶

    9.1 递归 spawn¶

    症状：子 Agent spawn 子子 Agent，子子 Agent spawn 子子子 Agent，无限递归，栈溢出或 OOM。

    原因：子 Agent 的工具集包含了 task。

    修复：工具集排除 task：

    const subTools = tools.filter(t => t.name !== "task");

    验证：在子 Agent 的 system prompt 里也加一句"不要 spawn 子 Agent"——双保险。但主要靠工具排除，不靠 prompt。

    9.2 无限循环¶

    症状：子 Agent 一直 grep 不同的关键词，永远不返回。

    原因：模型陷入循环，while(true) 没有退出条件。

    修复：迭代上限：

    const maxIterations = 20;
while (iteration < maxIterations) {
  // ...
}

    验证：日志里看到子 Agent 跑了 20 轮还没完成，说明可能陷入循环。调整 maxIterations 或优化 prompt。

    9.3 上下文泄漏¶

    症状：子 Agent 的工具结果出现在主 Agent 的上下文里。

    原因：subMessages 不是局部变量，而是主 messages 的引用。

    错误代码：

    async function badExecuteTask(input, messages) {  // ← 传入主 messages
  messages.push({ role: "user", content: input.prompt });
  // ... 子 Agent 的工具结果都 push 进 messages
}

    修复：subMessages 必须是局部变量：

    async function executeTask(input) {
  const subMessages = [{ role: "user", content: input.prompt }];  // ← 局部
  // ...
}

    验证：在子 Agent 执行后，检查主 Agent 的 messages 长度——不应该包含子 Agent 的工具结果。

    9.4 子 Agent 失败处理¶

    症状：子 Agent 抛异常，主 Agent 崩掉。

    原因：executeTask 里没有 try-catch，异常冒到主 Agent。

    错误代码：

    async function badExecuteTask(input) {
  // 没有 try-catch
  const response = await client.messages.create({ ... });  // ← 网络错误会抛
  // ...
}

    修复：try-catch 包住，返回错误字符串：

    async function executeTask(input) {
  try {
    // ...
  } catch (err: any) {
    return `子智能体错误: ${err.message}`;  // ← 返回字符串，不抛
  }
}

    为什么返回字符串而不是抛异常：返回字符串，主 Agent 收到一个"子 Agent 错误"的 tool_result，可以决定怎么处理（重试、告诉用户、换方案）。抛异常，主 Agent 的循环可能崩掉——一个子任务失败不应该搞垮整个会话。

    9.5 子 Agent 滥用¶

    症状：主 Agent 什么任务都 spawn 子 Agent，连"读一个文件"都 spawn。

    原因：task 工具的 description 太宽泛，模型在不需要时也调。

    影响：每次 spawn 都有额外开销（新的 messages、新的 system prompt、至少一轮 API 调用）。简单任务 spawn 子 Agent 比直接做更慢、更费 token。

    修复：在 task 工具的 description 里明确适用场景：

    description: "启动一个子智能体来处理子任务。子智能体有独立的上下文，不会污染主对话。适用于需要多步骤探索的复杂子任务。"
//                                                                          ↑ 强调"多步骤""复杂"

    "多步骤探索的复杂子任务"——这引导模型在简单任务（读一个文件、grep 一次）时不调 task，在复杂任务（多步探索、需要读很多文件）时才调。

    验证：日志里看 spawn 频率。如果主 Agent 频繁 spawn 子 Agent 做简单任务，说明 description 没引导好，要调整措辞。

    十、与真实 Claude Code 对比¶

    10.1 subagent_type¶

    本章：只有一个通用的子 Agent，没有类型区分。

    Claude Code：有多种 subagent_type，每种有不同的工具集、system prompt、甚至不同模型：

    subagent_type: "explore"        → 探索型，工具集 {read, glob, grep}，强调快速搜索
subagent_type: "general"        → 通用型，工具集 {read, write, edit, bash, glob, grep}，能读能写
subagent_type: "code-reviewer"  → 审查型，工具集 {read, glob, grep}，强调指出问题不改代码
subagent_type: "bug-fixer"      → 修 bug 型，工具集 {read, write, edit, bash, glob, grep}，强调定位和修复
...

    主 Agent 调 task 工具时要指定 subagent_type：

    {
  name: "task",
  input: {
    subagent_type: "explore",    // ← 指定类型
    description: "搜索错误处理",
    prompt: "找出所有处理错误的代码",
  }
}

    executeTask 根据 subagent_type 选择对应的工具集和 system prompt：

    function getSubagentConfig(type: string) {
  switch (type) {
    case "explore":
      return { tools: [readTool, globTool, grepTool], systemPrompt: EXPLORE_PROMPT };
    case "code-reviewer":
      return { tools: [readTool, globTool, grepTool], systemPrompt: REVIEWER_PROMPT };
    // ...
  }
}

    10.2 并行¶

    本章：串行，一次一个子 Agent。

    Claude Code：支持最多 10 个并行：

    主 Agent → 同时 spawn 最多 10 个子 Agent
         → Promise.allSettled 等全部完成
         → 结果按完成顺序收集

    并行的实现细节：

    • 模型在一个响应里输出多个 tool_use（最多 10 个 task 调用）。
    • 主循环用 Promise.allSettled 同时执行。
    • 每个子 Agent 有独立超时，单个超时不影响其他。
    • 总 spawn 数有上限（10），防止模型一次 spawn 100 个。

    10.3 独立工具集配置¶

    本章：所有子 Agent 用同一个工具集（tools 减 task）。

    Claude Code：每种 subagent_type 有独立配置的工具集：

    const SUBAGENT_CONFIGS = {
  explore: {
    tools: ["read_file", "glob", "grep"],           // 只读
    systemPrompt: EXPLORE_PROMPT,
    maxIterations: 10,                               // 探索型 10 轮够了
  },
  "code-reviewer": {
    tools: ["read_file", "glob", "grep"],           // 只读
    systemPrompt: REVIEWER_PROMPT,
    maxIterations: 30,                               // 审查可能要看很多文件
  },
  "bug-fixer": {
    tools: ["read_file", "write_file", "edit_file", "bash", "glob", "grep"],  // 能读能写能执行
    systemPrompt: BUG_FIXER_PROMPT,
    maxIterations: 50,                               // 修 bug 可能要多轮
  },
};

    工具集、system prompt、迭代上限都按类型配置——不同类型的子 Agent 有不同的"人设"和"能力"。

    10.4 独立 token 预算¶

    本章：用迭代次数（20）限制，没有 token 预算。

    Claude Code：每个子 Agent 有独立的 token 预算：

    const SUBAGENT_CONFIGS = {
  explore: {
    tokenBudget: 10000,   // 探索型 10000 token
    // ...
  },
  "bug-fixer": {
    tokenBudget: 50000,   // 修 bug 型 50000 token
    // ...
  },
};

    子 Agent 每轮 API 调用后，累加 token 消耗，超过预算就强制结束。比迭代次数更精确——10 轮可能消耗 1000 token（每轮很短），也可能消耗 100000 token（每轮很长），迭代次数区分不了，token 预算能区分。

    10.5 上下文压缩¶

    本章：子 Agent 不做上下文压缩。20 轮内一般不会超上下文限制。

    Claude Code：子 Agent 也有上下文压缩——接近限制时压缩历史，和主 Agent 的压缩机制一样。因为复杂子任务（修 bug）可能跑 50 轮，不压缩会超限。

    10.6 对比表¶

    方面 本章 Claude Code
    subagent_type 无分类 explore, general, code-reviewer, bug-fixer 等
    并行 串行 支持最多 10 个并行
    工具集 排除 task 按 subagent_type 配置不同工具集
    system prompt 通用 按 subagent_type 定制
    迭代限制 20 次迭代 token 预算 + 迭代次数
    上下文压缩 无 有
    错误处理 返回错误字符串 重试 + 降级 + 上报
    spawn 深度 无限制（但工具排除防递归） 有深度限制
    子 Agent 恢复 不支持 支持（task_id 恢复之前的会话）

    Claude Code 的子智能体系统更复杂、更精细。本章展示的是编排本质——独立 messages、独立循环、结果回传。这些本质不因并行、类型、预算而改变。

    11.2 subagent.ts 完整代码¶

    import Anthropic from "@anthropic-ai/sdk";
import { tools, executeTool, type Tool } from "./tools/index.js";
import { PermissionManager } from "./permission.js";

type MessageParam = Anthropic.MessageParam;

const SUBAGENT_SYSTEM_PROMPT = `你是一个子智能体，负责完成父智能体分配的特定任务。

## 规则
- 专注于完成分配的任务，不要偏离主题
- 使用提供的工具完成任务
- 完成后用简洁的语言总结结果
- 不要执行破坏性操作`;

export const taskTool: Tool = {
  name: "task",
  description:
    "启动一个子智能体来处理子任务。子智能体有独立的上下文，不会污染主对话。适用于需要多步骤探索的复杂子任务。",
  input_schema: {
    type: "object" as const,
    properties: {
      description: {
        type: "string",
        description: "子任务的简短描述（3-5个词）",
      },
      prompt: {
        type: "string",
        description: "给子智能体的详细任务指令",
      },
    },
    required: ["description", "prompt"],
  },
};

export async function executeTask(
  client: Anthropic,
  model: string,
  maxTokens: number,
  input: { description: string; prompt: string },
  perm: PermissionManager
): Promise<string> {
  console.log(`\n  [子智能体启动] ${input.description}`);

  const subMessages: MessageParam[] = [
    { role: "user", content: input.prompt },
  ];

  const subTools = tools.filter(
    (t) => t.name !== "task"
  );

  let iteration = 0;
  const maxIterations = 20;

  while (iteration < maxIterations) {
    iteration++;

    try {
      const response = await client.messages.create({
        model,
        max_tokens: maxTokens,
        system: SUBAGENT_SYSTEM_PROMPT,
        messages: subMessages,
        tools: subTools,
      });

      subMessages.push({ role: "assistant", content: response.content });

      if (response.stop_reason === "tool_use") {
        const toolResults: Anthropic.ToolResultBlockParam[] = [];

        for (const block of response.content) {
          if (block.type === "tool_use") {
            console.log(`    [子工具] ${block.name}`);

            const allowed = await perm.checkTool(block.name, block.input);
            if (!allowed) {
              toolResults.push({
                type: "tool_result",
                tool_use_id: block.id,
                content: "[用户拒绝了此操作]",
              });
              continue;
            }

            const result = await executeTool(block.name, block.input);
            toolResults.push({
              type: "tool_result",
              tool_use_id: block.id,
              content: result,
            });
          }
        }

        subMessages.push({ role: "user", content: toolResults });
      } else {
        const text = (response.content as Anthropic.TextBlock[])
          .filter((b) => b.type === "text")
          .map((b) => b.text)
          .join("");

        console.log(`  [子智能体完成] ${input.description}`);
        return text || "(子智能体未返回文本)";
      }
    } catch (err: any) {
      return `子智能体错误: ${err.message}`;
    }
  }

  return `子智能体达到最大迭代次数 (${maxIterations})，强制终止`;
}

    十二、设计哲学回顾¶

    12.1 正交性¶

    子智能体是一个正交的功能——它不修改任何现有代码，只新增 subagent.ts 和在 main.ts 加两行。工具注册、权限确认、上下文压缩、流式输出——这些现有功能完全不用改。

    正交性的好处：

    • 可移除：删掉 subagent.ts、删掉 main.ts 的两行，回到第七章。功能完全独立。
    • 可测试：executeTask 是独立函数，可以单独测试。
    • 可演进：加 subagent_type、加并行、加 token 预算——都在 subagent.ts 内改，不影响其他模块。

    12.2 复用而非复制¶

    executeTask 里的循环结构和主 Agent 的循环结构一样，但不是复制粘贴——它复用了 executeTool、perm.checkTool 等现有函数。只是 messages、system、tools 三个参数不同。

    复用的好处：

    • 工具执行逻辑只维护一份。executeTool 改了，主 Agent 和子 Agent 都跟着改。
    • 权限逻辑只维护一份。perm 的行为对主 Agent 和子 Agent 一致。

    12.3 隔离而非共享¶

    子 Agent 的 subMessages 是局部变量，不和主 Agent 共享。这是有意的隔离——即使共享更简单（传 messages 引用进去），也不共享。

    隔离的好处：

    • 上下文不污染。
    • 子 Agent 崩了不影响主 Agent 的 messages。
    • 子 Agent 返回后，中间结果自动垃圾回收。

    隔离的代价：

    • 可调试性下降（主 Agent 看不到子 Agent 的中间过程）。
    • 子 Agent 不能"继承"主 Agent 的对话历史——每次从零开始。

    这个代价是值得的。上下文隔离是子 Agent 的核心价值，不能为了"方便"而放弃。

    12.4 结构而非说服¶

    防递归靠工具集排除（结构上的不可能），不靠 system prompt 里说"不要 spawn"（说服模型）。权限确认靠代码里的 if（结构上的拦截），不靠 system prompt 里说"不要干危险的事"（说服模型）。

    能靠结构解决的，不靠说服。结构是强制的，说服是不可靠的。这是贯穿整个系列的设计哲学。

    练习一：加子 Agent 超时¶

    当前 executeTask 没有超时——如果 API 调用很慢（网络问题），子 Agent 会一直等。加一个超时：如果单次 API 调用超过 30 秒，返回错误。

    参考答案：

    function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  return Promise.race([
    promise,
    new Promise<T>((_, reject) =>
      setTimeout(() => reject(new Error("超时")), ms)
    ),
  ]);
}

const response = await withTimeout(

  30000
);

    练习二：加子 Agent 失败重试¶

    当前 executeTask 的 try-catch 直接返回错误。加一个重试：API 调用失败时重试最多 3 次，每次间隔 1 秒。

    要求：

    • API 调用失败（网络错误、rate limit）时重试。
    • 最多重试 3 次。
    • 每次重试间隔 1 秒。
    • 3 次都失败才返回错误。

    提示：在 try-catch 外面包一层重试循环。

    参考答案：

    async function withRetry<T>(
  fn: () => Promise<T>,
  maxRetries: number = 3,
  delayMs: number = 1000
): Promise<T> {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i === maxRetries - 1) throw err;
      await new Promise(r => setTimeout(r, delayMs));
    }
  }
  throw new Error("unreachable");
}

// 在 executeTask 里：
try {
  const response = await withRetry(() =>
    client.messages.create({ ... })
  );
  // ...
} catch (err: any) {
  return `子智能体错误（重试 3 次后仍失败）: ${err.message}`;
}
